Chapter One

What protected Really Means

The protected modifier sits between private and public — strict enough to keep outsiders out, lenient enough to let subclasses in.

Formal Definition

A member declared as protected in a Java class can be accessed by: (1) the class itself, (2) any subclass, whether in the same or a different package, and (3) any other class in the same package. It cannot be accessed by unrelated classes outside the package.

A Real-World Analogy

Think of a family business. The owner has personal documents (private) — only they see them. The business has internal documents (default) — only people working in the same office see them. The family inheritance documents (protected) — only the owner, family members in different cities, and trusted office staff can access them. The public-facing brochures (public) — anyone can read.

Example One — Credit Card Hierarchy

The CreditCard Domain

A payment platform handles multiple card types — Visa, MasterCard, AmericanExpress. Each shares core logic but applies its own fees and rewards. Where should protected fit in?

Scenario
Building a flexible card hierarchy
We need VisaCard and MasterCard to access the parent CreditCard's balance for charging — but outsiders must not touch it directly.
Without protected — using private

Subclasses Cannot Access Parent State

CreditCard.java (Wrong design) 
public class CreditCard {
    // private blocks subclass access
    private String cardNumber;
    private double balance;
    private double creditLimit;

    public CreditCard(String num, double limit) {
        this.cardNumber  = num;
        this.creditLimit = limit;
        this.balance     = 0.0;
    }
}

public class VisaCard extends CreditCard {
    public VisaCard(String num) {
        super(num, 100000);
    }

    public void charge(double amount) {
        // Visa adds 2% surcharge
        double fee = amount * 0.02;

        this.balance += amount + fee;
        // COMPILE ERROR:
        // balance has private access in CreditCard

        if (this.balance > this.creditLimit) {
        // COMPILE ERROR — same reason
    }
}
The Problem The subclass VisaCard cannot read or modify the parent's balance and creditLimit. The only workaround is to expose public getters and setters — but that defeats encapsulation entirely, allowing any random class to manipulate sensitive card data.
With protected — proper design

Subclasses Access Internal State Safely

CreditCard.java (Correct design) 
public class CreditCard {
    // protected allows subclass access
    protected String cardNumber;
    protected double balance;
    protected double creditLimit;

    public CreditCard(String num, double limit) {
        this.cardNumber  = num;
        this.creditLimit = limit;
        this.balance     = 0.0;
    }

    protected boolean canCharge(double amount) {
        return (balance + amount) <= creditLimit;
    }
}

public class VisaCard extends CreditCard {
    public VisaCard(String num) {
        super(num, 100000);
    }

    public void charge(double amount) {
        double fee = amount * 0.02;

        if (canCharge(amount + fee)) {
            balance += amount + fee;
            System.out.println("Charged " + amount);
        } else {
            System.out.println("Limit exceeded");
        }
    }
}
The Benefit The subclass can read balance, update it, and call the parent's helper method canCharge() — but no unrelated class can. Encapsulation is preserved at the public boundary while inheritance works as intended.

Why this works

By marking balance as protected, you signal a clear design intent: "this field is internal to the inheritance hierarchy." Visa, MasterCard, and AmericanExpress subclasses share access. Code in the marketing module, the email service, or any unrelated class cannot touch it. The compiler enforces this boundary automatically.

Example Two — Bank Account Hierarchy

Savings vs Current Accounts

A bank's SavingsAccount and CurrentAccount must both extend a base BankAccount and access shared transaction history — but only within the inheritance tree.

Scenario
Sharing a transaction log between account types
Both account types need to record transactions in a shared list — but the list itself should never be exposed to UI code or external services.
Without protected — using default access

Cross-Package Subclasses Are Blocked

com/bank/core/BankAccount.java 
package com.bank.core;
import java.util.ArrayList;
import java.util.List;

public class BankAccount {
    // default (package-private) access
    String accountNumber;
    List<String> transactionLog = new ArrayList<>();
    double balance;

    public BankAccount(String num, double opening) {
        this.accountNumber = num;
        this.balance       = opening;
    }
}

// In a DIFFERENT package:
package com.bank.savings;
import com.bank.core.BankAccount;

public class SavingsAccount extends BankAccount {
    private double interestRate;

    public SavingsAccount(String num, double opening) {
        super(num, opening);
        this.interestRate = 3.5;
    }

    public void addInterest() {
        double interest = balance * interestRate / 100;
        // COMPILE ERROR: balance not visible
        transactionLog.add("Interest credited");
        // COMPILE ERROR: transactionLog not visible
    }
}
The Problem Default (package-private) access only works within the same package. The moment you place subclasses in different packages — which is standard for modular code — the inheritance breaks. Developers often end up making everything public, which destroys encapsulation.
With protected — cross-package inheritance works

Subclasses Across Packages Inherit Cleanly

com/bank/core/BankAccount.java 
package com.bank.core;
import java.util.ArrayList;
import java.util.List;

public class BankAccount {
    protected String accountNumber;
    protected List<String> transactionLog = new ArrayList<>();
    protected double balance;

    public BankAccount(String num, double opening) {
        this.accountNumber = num;
        this.balance       = opening;
    }

    protected void recordTransaction(String entry) {
        transactionLog.add(entry);
    }
}

// In a DIFFERENT package:
package com.bank.savings;
import com.bank.core.BankAccount;

public class SavingsAccount extends BankAccount {
    private double interestRate;

    public SavingsAccount(String num, double opening) {
        super(num, opening);
        this.interestRate = 3.5;
    }

    public void addInterest() {
        double interest = balance * interestRate / 100;
        balance += interest;
        recordTransaction("Interest: " + interest);
        // All accesses succeed
    }
}
The Benefit Even though SavingsAccount lives in a different package, it can still access protected fields and methods of BankAccount. The bank's marketing service, UI module, and external partners still cannot — encapsulation holds.

A common mistake

Developers often use default access thinking "it's almost like protected." It is not. Default blocks cross-package subclasses, while protected explicitly permits them. In real-world enterprise code where modules are split into many packages, this distinction matters enormously.

Example Three — HR System

Employee, Manager, and Intern

An HR application has a base Employee class. Specialised types — Manager, Intern, Contractor — extend it. Where should salary calculation logic live?

Scenario
Base salary calculation as a protected helper
All employee types need to call a shared salary computation method. Outsiders (PayrollReport, EmailService) should not invoke this internal calculation directly.
Without protected — public method exposes internals

Anyone Can Call Internal Logic

Employee.java (public exposes too much) 
public class Employee {
    protected double basicSalary;

    public Employee(double basic) {
        this.basicSalary = basic;
    }

    // Internal helper made public so subclasses can use it
    public double computeNet(double tax) {
        return basicSalary - (basicSalary * tax);
    }
}

public class Manager extends Employee {
    public Manager(double basic) { super(basic); }

    public double totalSalary() {
        return computeNet(0.20) + 15000;
    }
}

// PROBLEM: any code can now call computeNet()
public class PayrollReport {
    public void generate() {
        Manager m = new Manager(80000);

        double leaked = m.computeNet(0.05);
        // Outside code uses internal tax logic!
        // Wrong tax rate applied — silent bug.
    }
}
The Problem Making computeNet() public lets any class invoke it with arbitrary parameters. A reporting service might pass the wrong tax rate, an export module might bypass approval checks. The internal salary logic leaks into the public API surface.
With protected — keep internal logic internal

Only Subclasses Can Use the Helper

Employee.java (protected helper) 
public class Employee {
    protected double basicSalary;

    public Employee(double basic) {
        this.basicSalary = basic;
    }

    // Internal helper for subclasses only
    protected double computeNet(double tax) {
        return basicSalary - (basicSalary * tax);
    }

    // Public API — controlled
    public double getMonthlySalary() {
        return computeNet(0.18);
    }
}

public class Manager extends Employee {
    public Manager(double basic) { super(basic); }

    public double getMonthlySalary() {
        return computeNet(0.20) + 15000;
        // Subclass uses protected helper
    }
}

public class PayrollReport {
    public void generate() {
        Manager m = new Manager(80000);

        double leaked = m.computeNet(0.05);
        // COMPILE ERROR — protected blocks this

        double salary = m.getMonthlySalary();
        // Only the public API is reachable
    }
}
The Benefit computeNet() is reusable for subclasses but unreachable from PayrollReport. The class exposes a deliberate public surface (getMonthlySalary()) while keeping internals safe from misuse.

The encapsulation insight

protected methods are part of the inheritance contract, not the public contract. You can change their signature, behaviour, or remove them when refactoring, as long as your subclasses adapt. Public methods, once published, are nearly impossible to change without breaking external consumers.

Chapter Four

Rules, Best Practices, and Common Mistakes

A consolidated set of guidelines for using protected effectively in real Java codebases.

When to Choose protected

  1. Designing for inheritance. When a class is intended to be extended and the children need internal access. If your class is final or sealed, protected serves no purpose.
  2. Cross-package subclasses. When subclasses live in different packages — protected is the only modifier (besides public) that supports this scenario.
  3. Sharing helper methods. Methods that subclasses must call but external code must not — protected gives precisely this scope.
  4. Exposing parent state to children. Fields that need direct access in subclass methods, where forcing getters/setters would be needlessly verbose.
  5. Template Method pattern. When a base class defines an algorithm skeleton and lets subclasses override specific steps marked as protected.

When NOT to Use protected

  1. Anything genuinely external. If outside code must use the method, mark it public.
  2. Pure internal state. If no subclass ever needs it, keep it private. Default to private and relax only when needed.
  3. Final classes. A class that cannot be extended has no subclasses, so protected behaves like default — confusing readers.
  4. Configuration constants. Use public static final or place in a constants class — protected adds no value here.
  5. To avoid writing setters. If you find yourself making fields protected just so subclasses can write to them freely, reconsider — you may be missing a proper method abstraction.

Common Mistakes Developers Make

  1. Confusing protected with package-private. Default access only works within the same package. protected adds cross-package subclass access on top of that.
  2. Marking everything protected by default. This expands the inheritance contract and locks you in. Start private; promote to protected only when a subclass needs it.
  3. Using protected on static methods of singletons. Static methods don't participate in inheritance the same way — protected static is rarely meaningful and often signals a design issue.
  4. Accessing protected members across unrelated classes in the same package. While technically allowed, this couples your code in ways that are easy to miss when refactoring.
  5. Forgetting that protected fields can be modified by any subclass. If you mark a field protected, every subclass author can change it freely — design accordingly.
Final Word
Protected is a deliberate design choice, not a default.

Reach for it when you have a genuine inheritance relationship and want to share internal API with descendants. In every other case, prefer private for true encapsulation, default for tight package-level cohesion, or public for explicit contracts. The clearest Java code uses each access modifier with intention — not by habit.
