Chapter 1 · Introduction
01

What Are These 4 Tools? (Simple Explanation)

Forget complex jargon. Here is what each tool does in one sentence, with a simple real-life comparison anyone can understand.

01

JUnit

Writes mini "check" programs that verify your code does what you expect. Like a teacher checking homework answers automatically.

02

Mockito

Creates pretend objects that act like real ones. Like using a toy phone instead of a real phone while practising calls.

03

JaCoCo

Counts how much of your code is checked by tests. Like a teacher saying "you only studied 60% of the syllabus".

04

SpotBugs

Reads your code looking for common mistakes. Like a spell-checker but for bugs instead of typos.

Why do we need each one?

→
JUnit: "Did my change break anything?"

You write a username validator. You change a tiny rule. Without tests, you must manually try 20 usernames every time. With JUnit, you write 20 small test methods once. Run them in 2 seconds. Instant proof nothing broke.

→
Mockito: "I can't test this because it needs something I don't have"

Your code calls a payment gateway. You can't make real test payments. Mockito creates a fake gateway that says "success" or "fail" exactly when you want, so you can test your logic without real money.

→
JaCoCo: "Are my tests actually checking everything?"

You wrote 50 tests. Feels safe. JaCoCo shows you only 40% of code lines were tested. The other 60% could fail silently. JaCoCo points to exact lines that need more tests.

→
SpotBugs: "Find sneaky bugs before users do"

You compare two passwords with == instead of .equals(). Code compiles fine. Tests might even pass by coincidence. But in production, users can't log in. SpotBugs catches this at build time.

How they work together

The complete quality pipeline
  You write code (UserValidator.java)
            |
            v
  [ SpotBugs ]  ── scans your code for sneaky bugs
            |
            v
  [ JUnit ]     ── runs your test methods to check correctness
            |
            v
  [ Mockito ]   ── inside JUnit tests, mocks external dependencies
            |
            v
  [ JaCoCo ]    ── measures: did your tests cover everything?
            |
            v
    BUILD PASSES   if all good
    BUILD FAILS    if any issue found

Two important rules

Rule 1: Test file name MUST end with Test.java (e.g., CalculatorTest.java). Maven only runs files ending in Test.
Rule 2: Test files go inside src/test/java, NOT inside src/main/java.

Chapter 3 · JUnit 5

JUnit 5 — 12 Simple Examples

A JUnit test is just a small method that calls your code and checks if the answer is what you expected. We'll learn this through 12 simple examples — starting with the easiest.

The 3 essential rules of every test

★
Every JUnit test follows the same pattern (AAA)

A — Arrange: Set up your object or input data.
A — Act: Call the method you want to test.
A — Assert: Check if the result is what you expected.

Most important annotations

AnnotationMeaning (simple)
@Test"This method is a test — run it"
@BeforeEach"Run this method BEFORE every test (to set things up)"
@AfterEach"Run this method AFTER every test (to clean up)"
@DisplayName"Show this readable name in test report"
@ParameterizedTest"Run the same test with different inputs"
@CsvSource"Here are the inputs and expected outputs in CSV form"
@ValueSource"Here is a list of simple values to test with"
@Disabled"Skip this test for now"

Most important assertions

AssertionWhat it checks
assertEquals(expected, actual)The two values are equal
assertTrue(condition)The condition is true
assertFalse(condition)The condition is false
assertNull(object)The object is null
assertNotNull(object)The object is NOT null
assertThrows(Exception.class, () -> ...)The code throws an exception
assertArrayEquals(expected, actual)Two arrays have same elements

05Username Validation
Real-world

Why this example? Validators have many rules. Each rule needs its own test. This is the bread and butter of real-world testing.

UsernameValidator.javajava
public class UsernameValidator {

    public boolean isValid(String username) {
        if (username == null) return false;
        if (username.length() < 4) return false;
        if (username.length() > 15) return false;
        if (!username.matches("[a-zA-Z0-9_]+")) return false;
        return true;
    }
}
UsernameValidatorTest.javajava
class UsernameValidatorTest {

    private final UsernameValidator validator = new UsernameValidator();

    @Test
    @DisplayName("Valid username should pass")
    void validUsername() {
        assertTrue(validator.isValid("alice_99"));
    }

    @Test
    @DisplayName("Null username should fail")
    void nullUsername() {
        assertFalse(validator.isValid(null));
    }

    @Test
    @DisplayName("Too short (less than 4) should fail")
    void tooShort() {
        assertFalse(validator.isValid("ab"));
    }

    @Test
    @DisplayName("Too long (more than 15) should fail")
    void tooLong() {
        assertFalse(validator.isValid("abcdefghijklmnopqr"));
    }

    @Test
    @DisplayName("Special characters not allowed")
    void specialChars() {
        assertFalse(validator.isValid("alice@99"));
    }

    @Test
    @DisplayName("Space in username not allowed")
    void withSpace() {
        assertFalse(validator.isValid("alice 99"));
    }

    @Test
    @DisplayName("Underscore is allowed")
    void underscoreAllowed() {
        assertTrue(validator.isValid("user_name"));
    }
}
06Password Validation
Real-world

Why this example? Same pattern as username but with more rules. Practice writing one test per rule.

PasswordValidator.javajava
public class PasswordValidator {

    public boolean isStrong(String password) {
        if (password == null || password.length() < 8) return false;
        if (!password.matches(".*[A-Z].*")) return false;     // uppercase
        if (!password.matches(".*[a-z].*")) return false;     // lowercase
        if (!password.matches(".*[0-9].*")) return false;     // digit
        if (!password.matches(".*[!@#$%^&*].*")) return false; // special
        return true;
    }
}

    @Test
    void tooShort() {
        assertFalse(validator.isStrong("Ab1!"));   // only 4 chars
    }

    @Test
    void missingUppercase() {
        assertFalse(validator.isStrong("abcd1234!"));
    }

    @Test
    void missingLowercase() {
        assertFalse(validator.isStrong("ABCD1234!"));

assertThrows

CalculatorTest.javajava
class CalculatorTest {

    private final Calculator calc = new Calculator();

    @Test
    void divideByZeroThrowsException() {
        // Pattern: assertThrows(ExceptionClass, lambda-that-throws)
        ArithmeticException exception = assertThrows(
            ArithmeticException.class,
            () -> calc.divide(10, 0)
        );

        // We can also check the error message
        assertEquals("Cannot divide by zero", exception.getMessage());

    void normalDivisionWorks() {
        assertEquals(5, calc.divide(10, 2));
    }
}

10Testing CRUD on a List (no database)
In-memory CRUD

Why this example? CRUD = Create, Read, Update, Delete. Most apps do these. We do them with just an ArrayList — no database needed.

TaskList.java (in-memory CRUD)java
import java.util.*;

public class TaskList {

    private final List<String> tasks = new ArrayList<>();

    public void add(String task) {            // CREATE
        if (task == null || task.isBlank())
            throw new IllegalArgumentException("Empty task not allowed");
        tasks.add(task);
    }

    public String get(int index) {         // READ
        return tasks.get(index);
    }

    public void update(int index, String newTask) {  // UPDATE
        tasks.set(index, newTask);
    }

    public void delete(int index) {            // DELETE
        tasks.remove(index);
    }

    public int size() {
        return tasks.size();
    }
}
TaskListTest.javajava
class TaskListTest {

    private TaskList list;

    @BeforeEach
    void setUp() {
        list = new TaskList();
    }

    // ===== CREATE =====
    @Test
    void addOneTaskIncreasesSize() {
        list.add("Buy milk");
        assertEquals(1, list.size());
    }

    @Test
    void addMultipleTasks() {
        list.add("Task A");
        list.add("Task B");
        list.add("Task C");
        assertEquals(3, list.size());
    }

    @Test
    void addEmptyTaskThrows() {
        assertThrows(IllegalArgumentException.class,
                     () -> list.add(""));
    }

    @Test
    void addNullTaskThrows() {
        assertThrows(IllegalArgumentException.class,
                     () -> list.add(null));
    }

    // ===== READ =====
    @Test
    void getReturnsAddedTask() {
        list.add("Read book");
        assertEquals("Read book", list.get(0));
    }

    // ===== UPDATE =====
    @Test
    void updateChangesTask() {
        list.add("Old name");
        list.update(0, "New name");
        assertEquals("New name", list.get(0));
        assertEquals(1, list.size());  // size unchanged
    }

    // ===== DELETE =====
    @Test
    void deleteReducesSize() {
        list.add("Task A");
        list.add("Task B");
        list.delete(0);
        assertEquals(1, list.size());
        assertEquals("Task B", list.get(0));
    }

    // ===== STATE =====
    @Test
    void newListIsEmpty() {
        assertEquals(0, list.size());
    }
}

12Bank Account (deposit, withdraw, transfer)
Object state

Why this example? Tests an object's state changing over time. Multiple methods affect the balance — verify each works correctly.

BankAccount.javajava
public class BankAccount {

    private double balance;

    public BankAccount(double initial) {
        if (initial < 0)
            throw new IllegalArgumentException("Initial cannot be negative");
        this.balance = initial;
    }

    public void deposit(double amount) {
        if (amount <= 0)
            throw new IllegalArgumentException("Deposit must be positive");
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount > balance)
            throw new IllegalStateException("Insufficient balance");
        balance -= amount;
    }

    public double getBalance() { return balance; }
}
BankAccountTest.javajava
class BankAccountTest {

    private BankAccount account;

    @BeforeEach
    void setUp() {
        account = new BankAccount(1000);
    }

    @Test
    void initialBalanceIsCorrect() {
        assertEquals(1000, account.getBalance());
    }

    @Test
    void depositIncreasesBalance() {
        account.deposit(500);
        assertEquals(1500, account.getBalance());
    }

    @Test
    void withdrawDecreasesBalance() {
        account.withdraw(300);
        assertEquals(700, account.getBalance());
    }

    @Test
    void multipleDepositsAndWithdraws() {
        account.deposit(200);   // 1200
        account.withdraw(100);  // 1100
        account.deposit(50);    // 1150
        account.withdraw(150);  // 1000
        assertEquals(1000, account.getBalance());
    }

    @Test
    void negativeInitialBalanceThrows() {
        assertThrows(IllegalArgumentException.class,
                     () -> new BankAccount(-100));
    }

    @Test
    void zeroDepositThrows() {
        assertThrows(IllegalArgumentException.class,
                     () -> account.deposit(0));
    }

    @Test
    void withdrawMoreThanBalanceThrows() {
        assertThrows(IllegalStateException.class,
                     () -> account.withdraw(5000));
    }
}

Chapter 4 · Mockito
04

Mockito — 11 Simple Examples

Mockito creates "fake" objects. You tell the fake what to return when called. Then you check your code reacted correctly. We'll learn this through 11 simple examples.

The 3-step pattern for every Mockito test

★
Pattern: WHEN → ACT → VERIFY

WHEN: Tell the fake what to return. (e.g., "when getUser('alice') is called, return this fake user")
ACT: Call the real method you want to test.
VERIFY: Check the result, AND verify the fake was used correctly.

Most important Mockito methods

MethodWhat it does (simple)
mock(MyClass.class)"Create a fake of this class"
@MockShortcut to create a fake (cleaner syntax)
@InjectMocks"Create my real class and give it the fakes"
when(fake.method()).thenReturn(value)"When this is called, return this value"
when(fake.method()).thenThrow(exception)"When this is called, throw this exception"
verify(fake).method()"Check this method was called"
verify(fake, never()).method()"Check this method was NEVER called"
verify(fake, times(3)).method()"Check this method was called exactly 3 times"
any(), anyString(), anyInt()"Match any value of this type"

The 11 Examples

01Your First Mock — Pretend the Method Returns Something
when/thenReturn

Why this example? The simplest possible mock — fake a method that returns a value. This is 80% of what you'll do.

Production code (interface + service)java
// An interface representing an external service
public interface PriceService {
    double getPrice(String productId);
}

// Our class that uses PriceService
public class CartCalculator {

    private final PriceService priceService;

    public CartCalculator(PriceService priceService) {
        this.priceService = priceService;
    }

    public double getTotalForOneItem(String productId) {
        return priceService.getPrice(productId);
    }
}
CartCalculatorTest.javajava
import static org.mockito.Mockito.*;
import static org.junit.jupiter.api.Assertions.*;

class CartCalculatorTest {

    @Test
    void getTotalUsesPriceService() {
        // Step 1: Create a fake PriceService
        PriceService fake = mock(PriceService.class);

        // Step 2: Tell the fake what to return
        when(fake.getPrice("BOOK-1")).thenReturn(99.50);

        // Step 3: Use the fake in our real class
        CartCalculator calc = new CartCalculator(fake);

        // Step 4: Test it
        double total = calc.getTotalForOneItem("BOOK-1");
        assertEquals(99.50, total);
    }
}
02Cleaner Syntax with @Mock and @InjectMocks
Annotations

Why this example? Writing mock() by hand gets repetitive. Annotations make it cleaner and easier to read.

CartCalculatorTest.java (cleaner version)java
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.InjectMocks;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)  // REQUIRED for @Mock to work
class CartCalculatorTest {

    @Mock           // auto-creates a fake PriceService
    PriceService priceService;

    @InjectMocks   // auto-creates CartCalculator and passes the fake
    CartCalculator calc;

    @Test
    void cleanerVersion() {
        when(priceService.getPrice("PEN-1")).thenReturn(25.0);

        assertEquals(25.0, calc.getTotalForOneItem("PEN-1"));
    }
}

11Complete Real-World Test (Login Flow)
Putting it all together

Why this example? Combines everything you've learned: multiple mocks, when/thenReturn, verify, never(), and exception handling. This is what real tests look like.

Production code — login with audit + lock-outjava
public interface CredentialStore {
    boolean isValid(String username, String password);
}
public interface AuditLog {
    void record(String event);
}
public interface AccountLocker {
    void lock(String username);
    int  getFailedAttempts(String username);
}

public class LoginManager {

    private final CredentialStore store;
    private final AuditLog         audit;
    private final AccountLocker   locker;

    public LoginManager(CredentialStore s, AuditLog a, AccountLocker l) {
        this.store = s; this.audit = a; this.locker = l;
    }

    public String login(String username, String password) {
        if (store.isValid(username, password)) {
            audit.record("SUCCESS: " + username);
            return "Welcome";
        } else {
            audit.record("FAILED: " + username);
            if (locker.getFailedAttempts(username) >= 3) {
                locker.lock(username);
                return "Account locked";
            }
            return "Invalid credentials";
        }
    }
}
LoginManagerTest.javajava
@ExtendWith(MockitoExtension.class)
class LoginManagerTest {

    @Mock CredentialStore store;
    @Mock AuditLog         audit;
    @Mock AccountLocker   locker;
    @InjectMocks LoginManager login;

    @Test
    void validLoginReturnsWelcomeAndAuditsSuccess() {
        when(store.isValid("alice", "pwd")).thenReturn(true);

        assertEquals("Welcome", login.login("alice", "pwd"));

        verify(audit).record("SUCCESS: alice");
        verify(locker, never()).lock(anyString());
    }

    @Test
    void invalidLoginButUnderAttemptLimitJustFails() {
        when(store.isValid(anyString(), anyString())).thenReturn(false);
        when(locker.getFailedAttempts("alice")).thenReturn(1);

        assertEquals("Invalid credentials", login.login("alice", "bad"));

        verify(audit).record("FAILED: alice");
        verify(locker, never()).lock("alice");
    }

    @Test
    void threeFailedAttemptsLocksAccount() {
        when(store.isValid(anyString(), anyString())).thenReturn(false);
        when(locker.getFailedAttempts("alice")).thenReturn(3);

        assertEquals("Account locked", login.login("alice", "bad"));

        verify(audit).record("FAILED: alice");
        verify(locker).lock("alice");  // MUST be called
    }
}

C

"5 of 6 classes tested = 83%"

Enforce a minimum coverage threshold

You can make Maven fail the build if coverage drops below a threshold. Add this to JaCoCo plugin:

pom.xml — add a check executionxml
<execution>
  <id>check-coverage</id>
  <goals><goal>check</goal></goals>
  <configuration>
    <rules><rule>
      <element>BUNDLE</element>
      <limits><limit>
        <counter>LINE</counter>
        <value>COVEREDRATIO</value>
        <minimum>0.80</minimum>   <!-- 80% minimum -->
      </limit></limits>
    </rule></rules>
  </configuration>
</execution>

Now mvn verify will fail if line coverage is below 80%.

Bug categories

CategoryExamples
CorrectnessNull pointer risk, comparing objects with ==, infinite loop

Common bugs SpotBugs catches (with fixes)

01Comparing Strings with ==
ES_COMPARING_STRINGS_WITH_EQ

The bug: Using == compares object references, not text content. Two strings with the same text can fail this check unexpectedly.

Bugjava
public boolean isActive(String status) {
    return status == "ACTIVE";   // BUG! Returns false for new String("ACTIVE")
}
Fixjava
public boolean isActive(String status) {
    return "ACTIVE".equals(status);   // Compares text, null-safe
}
02Possible Null Pointer Dereference
NP_NULL_ON_SOME_PATH

The bug: Using a variable without checking if it could be null first.

Bugjava
public int getNameLength(String name) {
    return name.length();   // BUG! Crashes if name is null
}
Fixjava
public int getNameLength(String name) {
    return name == null ? 0 : name.length();
}
03Empty Catch Block (Hidden Errors)
DE_MIGHT_IGNORE

The bug: Silently swallowing exceptions hides real problems. Bugs become invisible.

Bugjava
try {
    fileReader.read();
} catch (IOException e) {
    // BUG! Silently ignored - the file error disappears
}
Fixjava
try {
    fileReader.read();
} catch (IOException e) {
    log.error("Failed to read file: " + e.getMessage(), e);
    throw new RuntimeException("File read failed", e);
}
04Integer Object Comparison
RC_REF_COMPARISON

The bug: Java caches Integer values from -128 to 127. Using == works for small numbers but FAILS for larger ones. Very sneaky.

Bugjava
public boolean sameQty(Integer a, Integer b) {
    return a == b;   // Works for 1..127, FAILS for 128+
}
// sameQty(150, 150) returns FALSE because of Integer caching!
Fixjava
public boolean sameQty(Integer a, Integer b) {
    return Objects.equals(a, b);   // Works for all values, null-safe
}
05Resource Leak (File Not Closed)
OBL_UNSATISFIED_OBLIGATION

The bug: Opening a file without closing it. On Windows, the file becomes locked. Memory leaks. Eventually app crashes.

Bugjava
public String readFile(String path) throws IOException {
    FileReader reader = new FileReader(path);
    return new BufferedReader(reader).readLine();
    // BUG! reader is never closed
}
Fix (try-with-resources)java
public String readFile(String path) throws IOException {
    try (BufferedReader reader =
            new BufferedReader(new FileReader(path))) {
        return reader.readLine();
    }
    // Auto-closes when block exits, even if exception thrown
}
06SQL Injection
SQL_NONCONSTANT_STRING_PASSED_TO_EXECUTE

The bug: Building SQL with string concatenation lets attackers inject malicious queries.

Bugjava
public User findUser(String username) {
    String sql = "SELECT * FROM users WHERE name = '" + username + "'";
    return jdbc.query(sql);
    // Attacker sends: name="'; DROP TABLE users; --"
}
Fix (parameterized query)java
public User findUser(String username) {
    String sql = "SELECT * FROM users WHERE name = ?";
    return jdbc.query(sql, username);   // ? prevents injection
}
07Returning Internal Mutable State
EI_EXPOSE_REP

The bug: Returning the internal list/array directly lets outside code modify your class's state. Encapsulation broken.

Bugjava
public class ShoppingCart {
    private List<String> items = new ArrayList<>();

    public List<String> getItems() {
        return items;   // BUG! Caller can add/remove items directly
    }
}
Fixjava
public List<String> getItems() {
    return Collections.unmodifiableList(items);
    // Caller can read but cannot modify
}
