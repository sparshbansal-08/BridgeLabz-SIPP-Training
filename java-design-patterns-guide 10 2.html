What Are Design Patterns?

Design patterns are reusable solutions to common software design problems. They're not code you copy-paste — they're proven blueprints that experienced developers apply when they recognise familiar problems.

Think of design patterns like cooking recipes. A chef doesn't reinvent how to make a stew every time — they use a proven recipe and adapt it. Similarly, when you need ONE database connection for the whole app, you use the Singleton recipe. When you need flexible object creation, you reach for Factory. These patterns save you from common mistakes and make your code easier for other developers to understand.

01
Creational Pattern · Critical

Singleton Pattern

One instance, accessible everywhere — for shared resources.

Definition

The Singleton pattern ensures a class has only ONE instance during the entire program execution, and provides a global access point to that instance. The class itself controls its instantiation.

🏛️ Real-World Analogy

A country has only ONE president (or prime minister) at a time. Any minister, citizen, or media reporter who wants to talk to "the president" refers to the same person. You can't accidentally create a second president — the constitution prevents it. That's exactly what Singleton does for objects.

✅ When to USE Singleton

  • Database connection pools — one shared pool for the app
  • Logger — one logger that writes to one log file
  • Configuration manager — app-wide settings
  • Cache — one in-memory cache shared by all services
  • Thread pools, print spoolers, hardware drivers

❌ When NOT to USE Singleton

  • When you need different instances with different configurations
  • For business entities like User, Order, Product — they should have many instances
  • When testing — singletons make unit tests hard (global state)
  • In multi-threaded apps without proper locking — race conditions
  • Just because you want "global access" — that's not a good reason alone
With vs Without Singleton

Scenario: Your app needs a database connection. Compare both approaches.

❌

WITHOUT Singleton — Multiple DB Connections

Without — wasteful 
public class DatabaseConnection {
    private Connection conn;

    public DatabaseConnection() {
        // Each `new` opens a fresh connection
        conn = DriverManager.getConnection(URL);
        System.out.println("NEW connection opened");
    }

    public Connection getConn() { return conn; }
}

// USAGE — disaster!
public class App {
    public static void main(String[] args) {
        DatabaseConnection db1 = new DatabaseConnection();
        DatabaseConnection db2 = new DatabaseConnection();
        DatabaseConnection db3 = new DatabaseConnection();
        // → 3 separate connections opened!
        // → 3x memory, 3x CPU, 3x DB load
        // → DB connection limit hits quickly
    }
}
Problems: Memory waste, connection limit exhaustion, inconsistent state across copies, slower performance.
✅

WITH Singleton — ONE Shared Connection

With — efficient 
public class DatabaseConnection {
    private static DatabaseConnection instance;
    private Connection conn;

    // PRIVATE constructor — no external `new`
    private DatabaseConnection() {
        conn = DriverManager.getConnection(URL);
        System.out.println("Connection opened");
    }

    // Public access method
    public static synchronized DatabaseConnection getInstance() {
        if (instance == null) {
            instance = new DatabaseConnection();
        }
        return instance;
    }

    public Connection getConn() { return conn; }
}

// USAGE — clean!
public class App {
    public static void main(String[] args) {
        DatabaseConnection db1 = DatabaseConnection.getInstance();
        DatabaseConnection db2 = DatabaseConnection.getInstance();
        // db1 == db2 → SAME instance, ONE connection
    }
}
Benefits: One connection saves memory, prevents limit issues, consistent state, faster app startup.

Key Takeaway

Use Singleton when you have a truly shared resource that should NEVER be duplicated — database connections, loggers, config managers. Don't use it just for "convenience" — it creates hidden global state that makes testing painful.

02
Creational Pattern · Critical

Factory Pattern

Centralised object creation — hide the complexity, expose a clean API.

Definition

The Factory pattern provides a centralised method for creating objects, allowing the calling code to request an object by type or parameter without knowing the exact class being created. The factory decides which concrete class to instantiate.

🏭 Real-World Analogy

When you order a pizza at Domino's, you say "I want a Margherita" or "I want a Pepperoni." You don't open the oven, make the dough, slice cheese, and bake it yourself. The pizzeria's kitchen (the factory) handles all that complexity. You give a simple input ("Margherita") and get a finished pizza. Factory pattern works the same way in code.

✅ When to USE Factory

  • You have multiple subclasses and the choice depends on input/config
  • Object creation logic is complex (validation, multiple steps)
  • You want to hide concrete class names from clients
  • You expect to add new types frequently — Factory makes this easy
  • Frameworks: Spring beans, JDBC drivers, Logger factories

❌ When NOT to USE Factory

  • When there's only ONE class to create — use new directly
  • Object creation is trivial (just constructor parameters)
  • You'll never add more types — over-engineering
  • For very simple value objects (DTOs, POJOs)
With vs Without Factory

Scenario: You need to create different shapes (Circle, Square, Triangle) in your drawing app.

❌

WITHOUT Factory — Direct Instantiation

Without — coupled 
interface Shape { void draw(); }
class Circle   implements Shape { public void draw(){System.out.println("Circle");} }
class Square   implements Shape { public void draw(){System.out.println("Square");} }
class Triangle implements Shape { public void draw(){System.out.println("Triangle");} }

public class DrawingApp {
    public void drawShape(String type) {
        Shape shape;
        // Logic scattered everywhere
        if (type.equals("circle")) {
            shape = new Circle();
        } else if (type.equals("square")) {
            shape = new Square();
        } else if (type.equals("triangle")) {
            shape = new Triangle();
        } else {
            throw new RuntimeException();
        }
        shape.draw();
    }
    // If you add Star, you must change THIS class AND
    // every other place that creates shapes!
}
Problems: DrawingApp directly depends on Circle, Square, Triangle. Adding a new shape requires editing existing code. Logic duplicated wherever shapes are created.
✅

WITH Factory — Centralised Creation

With — decoupled 
interface Shape { void draw(); }
class Circle   implements Shape { /* draw() */ }
class Square   implements Shape { /* draw() */ }
class Triangle implements Shape { /* draw() */ }

// THE FACTORY
public class ShapeFactory {
    public static Shape create(String type) {
        switch (type.toLowerCase()) {
            case "circle":   return new Circle();
            case "square":   return new Square();
            case "triangle": return new Triangle();
            default: throw new RuntimeException();
        }
    }
}

public class DrawingApp {
    public void drawShape(String type) {
        Shape shape = ShapeFactory.create(type);  // clean!
        shape.draw();
    }
    // To add Star: only change ShapeFactory, NOT DrawingApp
}
Benefits: DrawingApp only knows about Shape interface. Adding a new shape requires only editing the factory. All creation logic in ONE place.

Key Takeaway

Factory is the backbone of most Java frameworks — Spring's BeanFactory, JDBC's DriverManager, Logger factories all use this pattern. Use it whenever you have multiple implementations and want to keep creation logic isolated.

03
Behavioral Pattern · Important

Observer Pattern

When something changes, automatically notify everyone who cares.

Definition

The Observer pattern defines a one-to-many dependency between objects. When one object (the Subject) changes state, all dependent objects (Observers) are automatically notified. The Subject doesn't need to know who's listening or what they do.

📰 Real-World Analogy

A YouTube channel publishes a new video. The channel doesn't manually call each subscriber — it just publishes, and YouTube automatically notifies all subscribers via the bell icon. The channel is the Subject; subscribers are Observers. When you unsubscribe, you stop receiving notifications — but the channel doesn't change.

✅ When to USE Observer

  • One change should trigger updates in many places (event-driven systems)
  • GUI event listeners — button click triggers many handlers
  • Stock market apps — price change notifies all watchers
  • Pub/Sub systems — Kafka, RabbitMQ, MQTT
  • Real-time dashboards, chat applications, notification systems

❌ When NOT to USE Observer

  • Only one component needs to react to changes — use direct call
  • Order of notifications matters — Observer doesn't guarantee order
  • Synchronous flow where you need return values
  • You need a strict chain of responsibility — use Chain pattern instead
With vs Without Observer

Scenario: A YouTube channel posts a new video; subscribers should get notified.

❌

WITHOUT Observer — Manual Notification

Without — fragile 
public class YouTubeChannel {
    public void postVideo(String title) {
        System.out.println("New video: " + title);

        // MUST manually call each subscriber
        Subscriber sub1 = new Subscriber("Rahul");
        sub1.sendNotification(title);

        Subscriber sub2 = new Subscriber("Priya");
        sub2.sendNotification(title);

        EmailService email = new EmailService();
        email.sendEmail(title);

        PushNotification push = new PushNotification();
        push.send(title);

        // New subscriber? You MUST edit this method!
        // Forget to update? They miss the notification.
    }
}
Problems: Channel must know every subscriber. Adding/removing subscribers requires changing the channel class. Tight coupling. Brittle code.
✅

WITH Observer — Automatic Notification

With — flexible 
interface Observer { void update(String video); }

public class YouTubeChannel {
    private List<Observer> subscribers = new ArrayList<>();

    public void subscribe(Observer o)   { subscribers.add(o); }
    public void unsubscribe(Observer o) { subscribers.remove(o); }

    public void postVideo(String title) {
        System.out.println("New video: " + title);
        // Notify ALL — no hardcoded list
        for (Observer o : subscribers) {
            o.update(title);
        }
    }
}

class EmailSubscriber implements Observer {
    public void update(String v) { System.out.println("📧 "+v); }
}
class PushSubscriber implements Observer {
    public void update(String v) { System.out.println("🔔 "+v); }
}

// USAGE
YouTubeChannel ch = new YouTubeChannel();
ch.subscribe(new EmailSubscriber());
ch.subscribe(new PushSubscriber());
ch.postVideo("Java Patterns");
// → Both get notified automatically
Benefits: Channel knows nothing about specific subscribers. Add or remove subscribers at runtime. New subscriber types don't require channel changes.

Observer pattern is the foundation of event-driven programming. Java's built-in listeners (Swing, JavaFX), Spring's ApplicationEventPublisher, and messaging systems like Kafka all use this pattern.

04
Behavioral Pattern · Critical

Strategy Pattern

Pick the algorithm at runtime — no more giant if/else chains.

Definition

The Strategy pattern defines a family of algorithms (or behaviors), encapsulates each one as a separate class, and makes them interchangeable at runtime. The client picks which strategy to use without changing the code that uses it.

🗺️ Real-World Analogy

When you open Google Maps to navigate from A to B, it asks: drive, walk, public transport, or bike? Each option uses a different algorithm to calculate the route. The Maps app itself doesn't change — you just plug in a different strategy. That's exactly how the Strategy pattern works.

✅ When to USE Strategy

  • Multiple ways to do the same task — payment, sorting, validation
  • You have a large if/else or switch deciding behaviour
  • Algorithm should be selectable at runtime
  • New algorithms might be added in the future
  • Compression formats, encryption methods, pricing rules

❌ When NOT to USE Strategy

  • Only one algorithm — no need for switching
  • The algorithm rarely changes
  • The strategies share no common interface (forcing one is awkward)
  • Performance is critical and indirection has measurable cost
With vs Without Strategy

Scenario: Your e-commerce app accepts multiple payment methods — Credit Card, UPI, Wallet.

❌

WITHOUT Strategy — if/else Conditional

Without — rigid 
public class PaymentService {
    public void processPayment(String method, double amount) {
        if (method.equals("creditcard")) {
            System.out.println("Processing card ₹" + amount);
            // Validate card number, CVV
            // Call card gateway API
            // Charge card
        } else if (method.equals("upi")) {
            System.out.println("Processing UPI ₹" + amount);
            // Validate UPI ID
            // Send UPI collect request
            // Wait for approval
        } else if (method.equals("wallet")) {
            System.out.println("Processing wallet ₹" + amount);
            // Check wallet balance
            // Deduct from wallet
        } else {
            throw new RuntimeException("Unknown method");
        }
    }
    // Add CryptoPayment? Edit this method.
    // Add BNPL? Edit this method.
    // Violates Open/Closed Principle
}
Problems: Class grows uncontrollably. Adding a new method means editing existing code (risky). Testing each branch separately is hard. Violates Single Responsibility & Open/Closed principles.
✅

WITH Strategy — Pluggable Algorithms

With — flexible 
// The Strategy interface
interface PaymentStrategy { void pay(double amount); }

// Each algorithm is its OWN class
class CreditCardPayment implements PaymentStrategy {
    public void pay(double a) {
        System.out.println("💳 Card: ₹" + a);
    }
}
class UPIPayment implements PaymentStrategy {
    public void pay(double a) {
        System.out.println("📱 UPI: ₹" + a);
    }
}
class WalletPayment implements PaymentStrategy {
    public void pay(double a) {
        System.out.println("👛 Wallet: ₹" + a);
    }
}

// The Context — uses the chosen strategy
public class PaymentService {
    private PaymentStrategy strategy;

    public void setStrategy(PaymentStrategy s) { this.strategy = s; }

    public void checkout(double amount) {
        strategy.pay(amount);
    }
}

// USAGE
PaymentService svc = new PaymentService();
svc.setStrategy(new UPIPayment());
svc.checkout(500);
// To add Crypto: just create new class — no edits!
Benefits: Each algorithm in its own class. Add new payment methods without touching PaymentService. Easy to test each strategy independently. Follows Open/Closed Principle.

Key Takeaway

If you ever write a switch/if-else that picks BEHAVIOUR based on a type, Strategy is almost always the right pattern. It transforms unstable code (where every new option breaks existing logic) into stable code (where you add a class and walk away).

05
Creational Pattern · Important

Builder Pattern

Build complex objects step by step — readable, flexible, immutable.

Definition

The Builder pattern constructs a complex object step by step, allowing optional fields and clear method chaining. Especially useful when an object has many constructor parameters, some of which are optional.

🍔 Real-World Analogy

At Subway, you build your sandwich step by step — pick the bread, then the protein, then veggies, then sauces. Each step is optional and you control the order. Compare that to a fixed menu where you must order a "Combo #5" with no customisation — that's a constructor with required positional parameters.

✅ When to USE Builder

  • Object has 4+ constructor parameters
  • Many parameters are optional or have defaults
  • You want immutable objects with readable construction
  • Object construction has multiple steps or validation
  • SQL query builders, HTTP request builders, document creators

❌ When NOT to USE Builder

  • Object has only 1-3 simple parameters — constructor is fine
  • Object is mutable and small — setters work
  • For simple DTOs or POJOs
  • When you want to enforce all fields are required at construction
With vs Without Builder

Scenario: Creating a Pizza with many optional toppings.

❌

WITHOUT Builder — Telescoping Constructor

Without — unreadable 
public class Pizza {
    private String size;
    private String crust;
    private boolean cheese, pepperoni, mushroom, onion, olives, jalapeno;

    // Many constructors for many combinations — UGH
    public Pizza(String s, String c) {
        this(s, c, false, false, false, false, false, false);
    }
    public Pizza(String s, String c, boolean cheese) {
        this(s, c, cheese, false, false, false, false, false);
    }
    public Pizza(String s, String c, boolean cheese,
                 boolean pep, boolean mush, boolean onion,
                 boolean olives, boolean jal) {
        this.size=s; this.crust=c;
        this.cheese=cheese; this.pepperoni=pep;
        this.mushroom=mush; this.onion=onion;
        this.olives=olives; this.jalapeno=jal;
    }
}

// USAGE — what do these booleans mean?!
Pizza p = new Pizza("Large", "Thin",
    true, false, true, false, true, false);
// Was mushroom 3rd or 4th? Confusing!
Problems: Unreadable. Easy to swap parameters by mistake. Many constructor overloads. Cannot easily skip optional fields.
✅

WITH Builder — Fluent & Readable

With — clean 
public class Pizza {
    private final String size, crust;
    private final boolean cheese, pepperoni, mushroom;

    private Pizza(Builder b) {
        this.size = b.size;
        this.crust = b.crust;
        this.cheese = b.cheese;
        this.pepperoni = b.pepperoni;
        this.mushroom = b.mushroom;
    }

    public static class Builder {
        private String size, crust;
        private boolean cheese, pepperoni, mushroom;

        public Builder size(String s)         { this.size = s; return this; }
        public Builder crust(String c)        { this.crust = c; return this; }
        public Builder addCheese()             { this.cheese = true; return this; }
        public Builder addPepperoni()          { this.pepperoni = true; return this; }
        public Builder addMushroom()           { this.mushroom = true; return this; }

        public Pizza build() { return new Pizza(this); }
    }
}

// USAGE — reads like English!
Pizza p = new Pizza.Builder()
    .size("Large")
    .crust("Thin")
    .addCheese()
    .addMushroom()
    .build();
Benefits: Reads like English. No parameter confusion. Optional fields are obvious. Object is immutable. Easy to extend.
Key Takeaway

Use Builder whenever your class has more than 3-4 parameters, especially if some are optional. Real-world examples: StringBuilder, Stream.builder(), Lombok's @Builder, JPA Criteria API.

06
Structural Pattern · Useful

Decorator Pattern

Add features to an object without changing its class.

Definition

The Decorator pattern lets you add new behavior to an object by wrapping it with another object that has the same interface. Multiple decorators can be stacked to combine behaviors.

☕ Real-World Analogy

At Starbucks, you start with a basic coffee (₹100). Add milk (+₹20), add caramel syrup (+₹30), add whipped cream (+₹40). Each addition is a "decorator" that wraps the previous order, adding cost and description without redesigning the coffee from scratch.

✅ When to USE Decorator

  • Add responsibilities dynamically without subclassing
  • Behaviors can be combined in many ways
  • Java I/O Streams (BufferedReader wraps FileReader)
  • Adding logging, caching, encryption to existing services
  • UI components — borders, scrollbars on a window

❌ When NOT to USE Decorator

  • Behavior never changes — just put it in the class
  • Only one or two combinations needed — subclassing is simpler
  • The base class is already complex
  • It creates many small classes that confuse developers
With vs Without Decorator

Scenario: Adding milk and sugar to a coffee.

❌

WITHOUT Decorator — Subclass Explosion

Without 
class Coffee                  { /* ₹100 */ }
class CoffeeWithMilk          extends Coffee           { /* ₹120 */ }
class CoffeeWithSugar         extends Coffee           { /* ₹110 */ }
class CoffeeWithMilkAndSugar  extends Coffee           { /* ₹130 */ }
class CoffeeWithMilkSugarCream extends Coffee           { /* ₹160 */ }
class CoffeeWithMilkCream     extends Coffee           { /* ₹150 */ }
// 2^n classes for n additions — explodes quickly!
// Add caramel? 12 more subclasses needed.
Problems: Class explosion. Adding one new ingredient doubles the class count. Hard to maintain.
✅

WITH Decorator — Wrap Layers

With 
interface Coffee { double cost(); String desc(); }

class BasicCoffee implements Coffee {
    public double cost() { return 100; }
    public String desc() { return "Coffee"; }
}

abstract class Decorator implements Coffee {
    protected Coffee coffee;
    public Decorator(Coffee c) { this.coffee = c; }
}

class Milk extends Decorator {
    public Milk(Coffee c) { super(c); }
    public double cost() { return coffee.cost() + 20; }
    public String desc() { return coffee.desc() + " + Milk"; }
}

class Sugar extends Decorator {
    public Sugar(Coffee c) { super(c); }
    public double cost() { return coffee.cost() + 10; }
    public String desc() { return coffee.desc() + " + Sugar"; }
}

// USAGE — combine layers like Lego
Coffee order = new Sugar(new Milk(new BasicCoffee()));
System.out.println(order.desc() + " = ₹" + order.cost());
// → Coffee + Milk + Sugar = ₹130
Benefits: Mix and match endlessly with just 1 class per addition. New options don't break existing combinations.
Key Takeaway

Decorator is everywhere in Java's java.io package — new BufferedReader(new InputStreamReader(new FileInputStream(file))) stacks decorators. Use it when you have many optional behaviours that combine in different ways.

Summary & Priority Guide

Which patterns to master first, and where each one shines.

Pattern Category Importance Use When Real Examples
Singleton Creational CRITICAL One shared instance for entire app DB connections, Logger, Config, Cache
Factory Creational CRITICAL Multiple subclasses, runtime choice Spring beans, JDBC drivers, Shape factories
Strategy Behavioral CRITICAL Multiple ways to do same thing Payment methods, sort algorithms, validators
Observer Behavioral IMPORTANT One change → many reactions Event listeners, Pub/Sub, Notifications
Builder Creational IMPORTANT Object with many optional params StringBuilder, HTTP requests, Lombok @Builder
Decorator Structural USEFUL Stack behaviors dynamically Java I/O Streams, GUI components, middleware

Which to Learn First?

If you have limited time: Master Singleton, Factory, and Strategy first. These three appear in almost every Java codebase you'll encounter, every Spring application, and every interview.

Next-level (after the basics): Learn Observer for event-driven systems and Builder for complex object construction. These come up in framework code and modern Java APIs.

Eventually: Explore Decorator, Adapter, Facade, Template Method, and Command. These are powerful but more situational.

Final Wisdom

Design patterns are tools, not laws. The goal is always cleaner, more maintainable code — not to use a pattern just because you know it. The best developers recognise when NOT to use a pattern: when simple code is good enough. Master the patterns, but use them sparingly and intentionally.
