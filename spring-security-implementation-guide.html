Before you begin

How this guide works

This guide builds a complete, secure Spring Boot REST API concept by concept. Each concept adds one new idea. Before every concept, you will see why the previous step is not enough and what problem the new step solves. After every concept you will run the application and test it with Postman to confirm the idea works before moving on.

The application is a simple online banking system with three endpoints that grow more secure at each step:

EndpointWho should access it
GET /homeAnyone — public, no login needed
GET /accountAny logged-in user
GET /adminOnly users with the ADMIN role
One rule above all

Do not skip ahead. Each concept depends on what was built before it. If you skip concept 3, concept 4 will not work. If you skip concept 5, concept 6 will not work. Build in order, test after each one.

Start here

Project Creation and Default Spring Security Behaviour

Before we start — state of the application

Where we are: Nothing exists yet. We are creating the project from scratch.
What we are doing: Adding Spring Security for the very first time and watching what it does before we configure anything.
Why this matters: Understanding the default behaviour shows us what Spring Security protects automatically, and why we must then customise it.

1 · The idea

When you add the Spring Security dependency to a Spring Boot project, it immediately locks down every URL, generates a random password, and shows a login form — all without a single line of your code. This is the safe default: everything is protected until you say otherwise.

2 · What we are going to add
  1. Create the Spring Boot project with the spring-boot-starter-security dependency.
  2. Add a temporary controller with one endpoint so we have something to test.
  3. Run the application and observe the automatic behaviour.
Concept 1: every request is blocked and redirected to the login page. No configuration written yet.

6 · What just happened

The moment you added spring-boot-starter-security, Spring automatically inserted a filter chain in front of every endpoint. That chain has one rule by default: nobody gets through without a valid username and password. When you provided the generated credentials, the chain verified them against an in-memory user called user and allowed the request. The entire login form, session, and password generation happened without you writing a single line of security code.

7 · What is still missing

Spring locked everything, including our public home page. We need to open some URLs and restrict others based on roles. We do that next by defining our own security rules.

2
Access rules

SecurityFilterChain — Taking Control of Access Rules

Depends on concept 1

Where we are: Spring Security is active and locks everything.
What is missing: We cannot open /home to the public, and we have no way to say "/admin needs the ADMIN role." The default locks everything equally.
What we are adding: A SecurityFilterChain bean that lets us write our own URL rules: open, login-required, or role-required.

1 · The idea

A SecurityFilterChain is a configuration object that defines which URLs are public, which require a login, and which require a specific role. Defining one replaces Spring's lock-everything default with your own rules.

2 · What we are going to add
  1. Create SecurityConfig.java with URL rules.
  2. Expand TestController.java with all three endpoints.
Concept 2 adds: the SecurityFilterChain (amber) with three URL rules. Right side shows the result for each path.
3 · Step-by-step implementation

Step 1. Create the security configuration class.

src/main/java/com/banking/config/SecurityConfig.java 
package com.banking.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
// @Configuration: tells Spring this class provides setup beans.
//   Mandatory for any class that contains @Bean methods Spring should use.

@EnableWebSecurity
// @EnableWebSecurity: activates Spring Security for the web layer and
//   tells it to use OUR SecurityFilterChain instead of the default.
//   Without this, Spring ignores our filterChain bean.

public class SecurityConfig {

    @Bean
    // @Bean: tells Spring to manage the object returned by this method.
    //   Without @Bean, Spring never picks up this SecurityFilterChain.
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/home").permitAll()
                // permitAll(): anyone can access /home, no login needed
                .requestMatchers("/account").authenticated()
                // authenticated(): must be logged in, any role
                .requestMatchers("/admin").hasRole("ADMIN")
                // hasRole("ADMIN"): must be logged in AND have ROLE_ADMIN
                .anyRequest().authenticated()
                // anyRequest(): everything else also needs a login
            )
            .httpBasic(org.springframework.security.config.Customizer.withDefaults());
            // httpBasic: allow username+password in the Authorization header.
            //   This keeps testing simple. We will replace this with JWT in concept 6.
        return http.build();
    }
}

7 · What is still missing

We are still using Spring's auto-generated in-memory user. A real app has many users stored in a database. Next we connect Spring Security to our own database.

3
Real users

UserDetails & UserDetailsService — Connecting to a Database

Builds on concept 2

Where we are: We have access rules (concept 2), but only one hardcoded in-memory user with a generated password. Every restart changes the password.
What is missing: Real users stored in a database. Spring Security does not know your table structure, so it cannot load them on its own.
What we are adding: A UserDetailsService — a bridge that loads your User from your database and hands it to Spring Security in the shape it understands.

1 · The idea

UserDetailsService is an interface with one method: given a username, return the user's security details. You implement it so Spring Security can look up users in your database during every login attempt.

2 · What we are going to add
  1. Add H2 (in-memory database) and JPA dependencies to pom.xml.
  2. Create the User entity.
  3. Create UserRepository.
  4. Create CustomUserDetailsService implementing UserDetailsService.
  5. Update SecurityConfig to use our service.
  6. Add application.properties settings for H2.
  7. Add data.sql with a test user (plain-text password for now — we fix this in concept 4).
Concept 3 adds: the UserDetailsService (teal) which queries the H2 database. Authentication now loads real users instead of the in-memory default.

Step 3. Create the User entity (the database table definition).

src/main/java/com/banking/model/User.java 
package com.banking.model;

import jakarta.persistence.*;

@Entity
// @Entity: tells JPA this class maps to a database table. Mandatory for stored objects.
@Table(name = "users")
// @Table(name="users"): the actual table name in the database. Optional; defaults to class name.
public class User {

    @Id
    // @Id: marks this field as the primary key (the unique identifier for each row).
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    // @GeneratedValue: the database auto-generates the id (1, 2, 3...). We never set it.
    private Long id;

    @Column(unique = true, nullable = false)
    // @Column: fine-tunes the column. unique=true prevents duplicate usernames.
    private String username;

    private String password;  // stored as plain text for now; we fix this in concept 4

    // getters and setters
    public Long getId() { return id; }
    public String getUsername() { return username; }
    public void setUsername(String u) { this.username = u; }
    public String getPassword() { return password; }
    public void setPassword(String p) { this.password = p; }
}

Step 4. Create the repository (the database query interface).

src/main/java/com/banking/repository/UserRepository.java 
package com.banking.repository;

import com.banking.model.User;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

public interface UserRepository extends JpaRepository<User, Long> {
    // JpaRepository gives us findAll, save, delete, etc. for free.
    // We only need to add the specific query Spring Security requires:
    Optional<User> findByUsername(String username);
    // Spring Data reads the method name and writes the SQL automatically:
    //   SELECT * FROM users WHERE username = ?
    // No implementation needed from us.
}

Step 5. Create the bridge: CustomUserDetailsService.

src/main/java/com/banking/service/CustomUserDetailsService.java 
package com.banking.service;

import com.banking.repository.UserRepository;
import org.springframework.security.core.userdetails.*;
import org.springframework.stereotype.Service;
import java.util.Collections;

@Service
// @Service: marks this as a business logic component. Spring manages it and
//   we can inject it with @Autowired. Mandatory for Spring to find and use it.
public class CustomUserDetailsService implements UserDetailsService {
    // Implementing UserDetailsService is the contract that connects us to Spring Security.
    //   There is exactly one method to implement: loadUserByUsername.

    private final UserRepository userRepository;

    public CustomUserDetailsService(UserRepository userRepository) {
        this.userRepository = userRepository;
        // Constructor injection: Spring automatically provides the UserRepository.
    }

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        // Spring Security calls this method on every login attempt.
        //   It passes the username entered on the login form.
        com.banking.model.User user = userRepository.findByUsername(username)
            .orElseThrow(() -> new UsernameNotFoundException("User not found: " + username));
        // If no user is found, we throw UsernameNotFoundException. Spring Security
        //   catches this and returns a 401 Unauthorized response automatically.

        return new org.springframework.security.core.userdetails.User(
            user.getUsername(),
            user.getPassword(),  // plain text for now; fixed in concept 4
            Collections.emptyList()  // no roles yet; we add them in concept 5
        );
        // We return Spring's built-in User class (which implements UserDetails).
        //   It carries the username, password, and list of roles for this request.
    }
}

Step 6. Tell SecurityConfig to use our service. Add this method to SecurityConfig.java.

src/main/java/com/banking/config/SecurityConfig.java (add this method) 
// Add this import at the top of SecurityConfig.java:
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;

// Add this method inside the SecurityConfig class:
@Bean
public DaoAuthenticationProvider authenticationProvider(
        CustomUserDetailsService userDetailsService) {

    DaoAuthenticationProvider provider = new DaoAuthenticationProvider();
    provider.setUserDetailsService(userDetailsService);
    // Tell the provider to use our CustomUserDetailsService to load users.
    provider.setPasswordEncoder(
        org.springframework.security.crypto.password.NoOpPasswordEncoder.getInstance());
    // NoOpPasswordEncoder: compares passwords as plain text. ONLY for temporary testing.
    //   We replace this with BCrypt in concept 4. Never use this in production.
    return provider;
}

6 · What just happened

When the request arrived with alice's credentials, Spring Security called our loadUserByUsername("alice") method. That method used UserRepository to query the H2 database, found alice's row, and returned a UserDetails object with her username and password. 7 · What is still missing

Alice's password is stored as plain text in the database. If the database is ever leaked, every password is immediately visible. We fix this now in concept 4.

4
Password safety

Password Encoding with BCrypt

Builds on concept 3

Where we are: Users load from a real database (concept 3). But passwords are stored as plain text. One database leak exposes everyone's passwords immediately.
What we are adding: BCryptPasswordEncoder — a one-way hashing algorithm. From this point forward, no plain password is ever stored.
Why now: Every password written from this concept onward must be a BCrypt hash. If we add more users later with plain text, they will not work.

1 · The idea

BCrypt takes a plain password and produces a scrambled, irreversible string (a hash). Spring Security never stores or compares plain passwords — it hashes the login attempt and compares the two hashes. The original is never needed again.

2 · What we are going to change
  1. Replace NoOpPasswordEncoder with BCryptPasswordEncoder in SecurityConfig.
  2. Update data.sql to store a BCrypt hash instead of plain text.
3 · Step-by-step implementation

Step 1. Replace the password encoder bean in SecurityConfig. Find the line with NoOpPasswordEncoder and change the entire authenticationProvider method.

src/main/java/com/banking/config/SecurityConfig.java (updated authenticationProvider) 
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
    // BCryptPasswordEncoder: hashes passwords using the BCrypt algorithm.
    //   We declare it as a @Bean so it can be injected anywhere that needs it.
    //   We never call encode() ourselves at login; Spring does that automatically.
}

@Bean
public DaoAuthenticationProvider authenticationProvider(
        CustomUserDetailsService userDetailsService,
        PasswordEncoder passwordEncoder) {
    DaoAuthenticationProvider provider = new DaoAuthenticationProvider();
    provider.setUserDetailsService(userDetailsService);
    provider.setPasswordEncoder(passwordEncoder);
    // We now tell the provider to use BCrypt for password comparison.
    //   At login, Spring calls passwordEncoder.matches(rawPassword, storedHash).
    //   If they match, login succeeds. The raw password is never stored.
    return provider;
}

7 · What is still missing

Every logged-in user can reach /admin, because all users have the same level. We need to attach roles to users and enforce them — that is concept 5.

5
Access levels

Roles and Authorisation — Controlling What Each User Can Do

Builds on concepts 3 and 4

Where we are: Authentication works (concept 3) with safe passwords (concept 4). But all users are equal — any logged-in user could reach /admin.
What is missing: Roles. Our SecurityConfig already says hasRole("ADMIN"), but no user carries a role yet, so the rule never matches.
What we are adding: A role field on the User entity and wiring it into UserDetailsService as a GrantedAuthority (the technical term for a role or permission in Spring Security).

1 · The idea

Roles are labels stored on the user record. When the user logs in, loadUserByUsername() includes their role. Spring Security reads that role from the Security Context on every request and compares it to the access rules in SecurityConfig.

2 · What we are going to change
  1. Add a role field to the User entity.
  2. Update data.sql with two users: one ROLE_USER and one ROLE_ADMIN.
  3. Update CustomUserDetailsService to include the role in the returned UserDetails.
Concept 5 adds: the role flows from the database through UserDetails into the Security Context. The filter chain now enforces role-based access.

Step 1. Add the role field to the User entity.

6 · What just happened

When bob logged in, loadUserByUsername("bob") returned a UserDetails object with one GrantedAuthority: ROLE_ADMIN. Spring Security stored that in the Security Context. When bob's request hit /admin, the filter chain read the context, found ROLE_ADMIN, matched it against the hasRole("ADMIN") rule, and allowed the request. Alice's context held ROLE_USER, which did not satisfy the rule, so her request was blocked with 403.

7 · What is still missing

Authentication still uses session cookies. Every request after login sends a cookie that the server uses to remember the session. This does not work well for REST APIs or microservices. In concept 6 we replace sessions with JWT tokens.

6
Stateless auth

JWT — Stateless Authentication

Builds on concepts 2, 3, 4, and 5

Where we are: Full role-based authentication and authorisation work with sessions. A session cookie is created at login and sent with every request.
What is missing: For a REST API, session cookies are problematic — mobile apps do not handle cookies naturally, and multiple servers cannot share one session store without extra infrastructure.
What we are adding: JWT (JSON Web Token) — a signed self-contained ticket issued at login. The server stores nothing. Every request proves its own identity by sending the token.

1 · The idea

At login, the server creates a JWT containing the username and role, signs it with a secret key, and returns it. On every future request, the client sends the token in the Authorization header. A filter verifies the signature and writes the identity to the Security Context — the same context from concept 3, just populated differently.

JWT has six sub-steps with dependencies between them. Read the dependency note before each one.

Steps 6a through 6f must be built in order. Each step explains what the previous step cannot do on its own.

2 · Step 6b — Create JwtService

Depends on: the jjwt library (6a). JwtService is responsible for two things only: creating a token and verifying one. Nothing else touches JWT logic.

src/main/java/com/banking/security/JwtService.java 
package com.banking.security;

import io.jsonwebtoken.*;
import io.jsonwebtoken.security.Keys;
import org.springframework.stereotype.Service;
import java.security.Key;
import java.util.Date;

@Service
public class JwtService {

    private static final String SECRET_KEY =
        "my-very-secret-key-that-is-at-least-32-bytes!!";
    // The secret key signs the token. Anyone who knows this key can forge tokens.
    //   Keep it in environment variables or a secrets manager in production.
    //   Must be at least 32 bytes (256 bits) for HS256 signing.

    private static final long EXPIRATION_MS = 1000 * 60 * 60;
    // Token expiry: 1 hour (in milliseconds). After this, the token is rejected.
    //   Expiry is critical: if a token is stolen, it only works until it expires.

    private Key getSigningKey() {
        return Keys.hmacShaKeyFor(SECRET_KEY.getBytes());
        // Creates a cryptographic key from our secret string.
        //   HS256 (HMAC-SHA256) is the signing algorithm: fast and sufficient for most APIs.
    }

    public String generateToken(String username, String role) {
        return Jwts.builder()
            .subject(username)
            // subject: the "who is this token for?" field (the username)
            .claim("role", role)
            // claim: a custom field we add. We store the role so the JWT filter can read it.
            .issuedAt(new Date())
            // issuedAt: when the token was created
            .expiration(new Date(System.currentTimeMillis() + EXPIRATION_MS))
            // expiration: when the token stops being valid
            .signWith(getSigningKey())
            // signWith: creates the signature using our secret key. This is what prevents forgery.
            .compact();
            // compact(): produces the final token string: header.payload.signature
    }

    public String extractUsername(String token) {
        return parseClaims(token).getSubject();
        // Reads the username (the "subject") out of the token payload.
    }

    public String extractRole(String token) {
        return parseClaims(token).get("role", String.class);
        // Reads our custom "role" claim out of the token payload.
    }

    public boolean isTokenValid(String token) {
        try {
            parseClaims(token);
            // If this does not throw, the token has a valid signature and is not expired.
            return true;
        } catch (JwtException e) {
            return false;
            // JwtException covers: invalid signature, expired token, malformed token.
        }
    }

    private Claims parseClaims(String token) {
        return Jwts.parser()
            .verifyWith(Keys.hmacShaKeyFor(SECRET_KEY.getBytes()))
            .build()
            .parseSignedClaims(token)
            .getPayload();
        // Verifies the signature with our key, then extracts the payload (claims).
        //   If the signature is wrong, this throws a SignatureException.
        //   If the token is expired, this throws an ExpiredJwtException.
    }
}
2 · Step 6c — Create JwtAuthFilter

Depends on: JwtService (6b) to verify tokens, and the Security Context from concept 3 to store identity. This filter runs on every request and populates the context if a valid token is found.

src/main/java/com/banking/security/JwtAuthFilter.java 
package com.banking.security;

import jakarta.servlet.*;
import jakarta.servlet.http.*;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import java.io.IOException;
import java.util.List;

@Component
// @Component: registers this filter as a Spring-managed bean so it can be
//   injected into SecurityConfig. Mandatory for Spring to find it.
public class JwtAuthFilter extends OncePerRequestFilter {
    // OncePerRequestFilter: guarantees this filter runs exactly once per request.
    //   We extend it so we only need to implement doFilterInternal().

    private final JwtService jwtService;

    public JwtAuthFilter(JwtService jwtService) {
        this.jwtService = jwtService;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                      HttpServletResponse response,
                                      FilterChain filterChain)
                                throws ServletException, IOException {

        String authHeader = request.getHeader("Authorization");
        // Read the Authorization header. Valid JWT requests look like:
        //   Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            // No token present. Pass the request to the next filter without authenticating.
            //   The next filter (authorisation) will block it if the URL requires login.
            return;
        }

        String token = authHeader.substring(7);
        // Remove "Bearer " (7 characters) to get just the token string.

        if (jwtService.isTokenValid(token)) {
            String username = jwtService.extractUsername(token);
            String role     = jwtService.extractRole(token);

            UsernamePasswordAuthenticationToken authentication =
                new UsernamePasswordAuthenticationToken(
                    username, null,
                    List.of(new SimpleGrantedAuthority(role))
                );
            // UsernamePasswordAuthenticationToken: the standard object that represents
            //   "this user is authenticated." We pass username, no credentials (null),
            //   and the role. Spring Security reads the role for authorisation checks.

            SecurityContextHolder.getContext().setAuthentication(authentication);
            // Write the authenticated identity into the Security Context.
            //   This is the SAME Security Context from concept 3.
            //   From this point, every part of the request knows who the user is.
        }

        filterChain.doFilter(request, response);
        // Pass the request on to the next filter in the chain, then to the controller.
    }
}

2 · Step 6e — Create AuthService

Depends on: AuthenticationManager from concept 2 (which knows how to verify credentials using UserDetailsService from concept 3 and BCrypt from concept 4), and JwtService from 6b (which creates the token).

src/main/java/com/banking/service/AuthService.java 
package com.banking.service;

import com.banking.security.JwtService;
import org.springframework.security.authentication.*;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Service;

@Service
public class AuthService {

    private final AuthenticationManager authenticationManager;
    // AuthenticationManager: the coordinator built in concept 2.
    //   It delegates to DaoAuthenticationProvider, which uses our UserDetailsService
    //   (concept 3) and BCryptPasswordEncoder (concept 4).

    private final JwtService jwtService;

    public AuthService(AuthenticationManager authenticationManager,
                       JwtService jwtService) {
        this.authenticationManager = authenticationManager;
        this.jwtService = jwtService;
    }

    public String login(String username, String password) {
        Authentication auth = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(username, password)
        );
        // authenticate() either succeeds and returns an Authentication object,
        //   or throws BadCredentialsException if the password is wrong.
        //   Internally it calls loadUserByUsername() and BCrypt.matches() for us.

        UserDetails userDetails = (UserDetails) auth.getPrincipal();
        // getPrincipal(): the authenticated user as a UserDetails object.
        //   We cast it to UserDetails so we can read the username and roles.

        String role = userDetails.getAuthorities().iterator().next().getAuthority();
        // getAuthorities(): the list of roles. We take the first one (users have one role here).
        //   getAuthority() returns the string e.g. "ROLE_ADMIN".

        return jwtService.generateToken(userDetails.getUsername(), role);
        // Generate and return the JWT. This is the string the client must store
        //   and send with every future request in the Authorization header.
    }
}
2 · Step 6f — Update SecurityConfig for JWT

Depends on: JwtAuthFilter (6c) to add to the chain, and the AuthenticationManager which now needs to be exposed as a bean.

src/main/java/com/banking/config/SecurityConfig.java (full updated version) 
package com.banking.config;

import com.banking.security.JwtAuthFilter;
import com.banking.service.CustomUserDetailsService;
import org.springframework.context.annotation.*;
import org.springframework.security.authentication.*;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    private final JwtAuthFilter jwtAuthFilter;
    public SecurityConfig(JwtAuthFilter jwtAuthFilter) {
        this.jwtAuthFilter = jwtAuthFilter;
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            // csrf.disable(): safe for stateless JWT APIs. The browser never sends the
            //   JWT automatically (unlike session cookies), so CSRF attacks are not possible.
            //   NEVER disable CSRF on a form-login, session-based application.

            .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            // STATELESS: tells Spring Security to create NO sessions.
            //   Every request must carry its own JWT. Nothing is remembered between requests.

            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/login").permitAll()
                // The login endpoint must be public, otherwise nobody could ever log in.
                .requestMatchers("/home").permitAll()
                .requestMatchers("/account").authenticated()
                .requestMatchers("/admin").hasRole("ADMIN")
                .anyRequest().authenticated()
            )

            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
            // addFilterBefore: insert our JwtAuthFilter BEFORE Spring's default login filter.
            //   This ensures the token is read and the identity is set BEFORE
            //   the authorisation check runs. Order matters.

        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

    @Bean
    public DaoAuthenticationProvider authenticationProvider(
            CustomUserDetailsService userDetailsService) {
        DaoAuthenticationProvider p = new DaoAuthenticationProvider();
        p.setUserDetailsService(userDetailsService);
        p.setPasswordEncoder(passwordEncoder());
        return p;
    }

    @Bean
    public AuthenticationManager authenticationManager(
            AuthenticationConfiguration config) throws Exception {
        return config.getAuthenticationManager();
        // Expose the AuthenticationManager as a bean so AuthService can inject it.
        //   Without this @Bean, AuthService cannot get hold of the manager.
    }
}

6 · What just happened (the invisible flow)

When alice logged in, AuthService called AuthenticationManager.authenticate(), which used CustomUserDetailsService to load alice from the database and BCryptPasswordEncoder to verify the password. On success, JwtService.generateToken() created a signed token containing alice's username and role, which was returned to the client. On every subsequent request, JwtAuthFilter read the token from the header, called jwtService.isTokenValid() to verify the signature, extracted the username and role, and wrote an Authentication object into the SecurityContextHolder. The filter chain then read alice's role from the context and compared it to the access rules — exactly as it did in concept 5, just with the identity arriving via a token rather than a session.

API hygiene

CSRF and CORS — The Two Issues Every REST API Hits

Builds on concept 6

Where we are: A fully working JWT REST API (concept 6).
What is missing: CSRF is already handled (disabled in 6f). CORS needs explaining and configuring so a browser front-end can call our API.
What we are adding: A clear understanding of why CSRF is safe to disable here, and a global CORS configuration for a front-end running on a different address.

Part A — CSRF: why we disabled it and when that is safe

CSRF (Cross-Site Request Forgery) is an attack where a malicious website tricks your logged-in browser into sending a request to your bank. It works because the browser automatically includes your session cookie with every request to that domain.

CSRF attack requires

The browser automatically attaching the credential (a session cookie). The malicious site does not need the cookie value — the browser sends it silently.

Why JWT is safe without CSRF

JWT is sent in the Authorization header, not a cookie. The browser never sends headers automatically to other sites. A malicious site cannot make a request with your JWT because it does not have it.

When you must NOT disable CSRF

If your application uses session cookies and a browser login form (like a traditional web app), CSRF protection is essential. Only disable it for stateless JWT APIs where credentials are sent via headers, never cookies.

Part B — CORS: what it is and why the browser blocks you

CORS (Cross-Origin Resource Sharing) is a browser security rule. When a web page at http://localhost:3000 tries to call an API at http://localhost:8080, the browser notices these are different origins (different ports count) and blocks the request by default. The API must explicitly say "I allow requests from localhost:3000."

Add a global CORS configuration inside SecurityConfig.filterChain():

src/main/java/com/banking/config/SecurityConfig.java (add inside filterChain, before return) 
import org.springframework.web.cors.*;
import org.springframework.web.filter.CorsFilter;

// Add inside filterChain(), after the .addFilterBefore(...) line and before return:
http.cors(cors -> cors.configurationSource(request -> {
    CorsConfiguration config = new CorsConfiguration();
    config.addAllowedOrigin("http://localhost:3000");
    // Allow requests from the React dev server. Add your production domain here too.
    config.addAllowedMethod("*");
    // Allow all HTTP methods: GET, POST, PUT, DELETE, etc.
    config.addAllowedHeader("*");
    // Allow all headers, including our Authorization header which carries the JWT.
    config.setAllowCredentials(true);
    // Allow the browser to include credentials (needed if you ever use cookies alongside JWT).
    return config;
}));

6 · What just happened

The browser always sends a CORS "preflight" OPTIONS request before the real request to ask "will you accept a request from my origin?" Our configuration returned the Access-Control-Allow-Origin header with our allowed origin. The browser saw this, considered it safe, and proceeded with the actual request. Without this configuration, the browser would have silently swallowed the response and shown a CORS error in the console, even though the API itself returned 200.

What we built

The complete flow, in plain words

Every HTTP request enters the SecurityFilterChain (concept 2). The JwtAuthFilter (concept 6c) runs first: it reads the Authorization header, calls JwtService.isTokenValid() to verify the signature, and if valid, writes the username and role into the Security Context as a trusted Authentication object. The chain then checks the URL against the access rules: /home is public (passes immediately), /account requires an authenticated identity in the context, and /admin requires the context to hold ROLE_ADMIN. If the rules are not met, the request is blocked with 401 or 403 before the controller is ever called. At login (POST /auth/login), the AuthService (concept 6e) calls the AuthenticationManager, which uses CustomUserDetailsService (concept 3) to load the user from H2 and BCryptPasswordEncoder (concept 4) to compare the submitted password against the stored hash. On success, JwtService (concept 6b) creates a signed token containing the username and role, which the client stores and sends with every future request. CSRF protection is safely disabled because JWT travels in a header (not a cookie), and a CORS configuration (concept 7) tells the browser which front-end origins are permitted to call the API.
