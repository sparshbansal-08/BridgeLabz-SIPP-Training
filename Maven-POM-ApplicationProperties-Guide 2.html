1. Maven Basics

Q1. What is Maven?
Maven is a build and dependency management tool for Java projects. It compiles your code, runs tests, packages the app into a JAR or WAR file, and automatically downloads the libraries (JAR files) your project needs.
Why this matters: Without Maven you would download every library by hand and fix version clashes yourself. Maven does this for you.
Q2. Why do we need Maven?
  • Dependency management: list a library once and Maven downloads it and everything it depends on.
  • Standard build: every Maven project builds the same way with mvn clean package.
  • Standard folder layout: code in src/main/java, tests in src/test/java.
  • Repeatable: the same build works on your machine, a teammate's machine, and the build server.
Q3. What is a Maven repository?
A storage location for libraries. There are three levels:
  • Local — a folder on your machine called .m2 where downloaded libraries are cached.
  • Central — the public online repository Maven downloads from by default.
  • Remote — a company's private repository (for example Nexus or Artifactory).
Example: The first time you build, Maven downloads libraries from Central into .m2. The next build reuses them from .m2, so it is faster.

2. POM - What and Why

Q1. What does POM stand for?
POM stands for Project Object Model. It is the "model" (description) of your project, written in a file named pom.xml.
Q2. What is pom.xml?
It is the central configuration file of a Maven project. It tells Maven the project's name, version, Java version, the libraries it needs (dependencies), and how to build it (plugins).
Q3. Why do we need a POM?
Because it is the single place where Maven reads everything it needs to build the project: which libraries to download, which Java version to use, and how to package the app. No POM means Maven cannot build the project.
Why this question is asked: Interviewers want to confirm you understand that the POM is the "control center" of a Maven build, not just a random config file.
Q4. What are the most important parts of a POM?
ElementWhat it does
<modelVersion>The POM format version. Always 4.0.0 for modern Maven.
<parent>A parent POM we inherit settings and versions from.
<groupId>The organization/group that owns the project (e.g. com.springboot).
<artifactId>The project's own name (e.g. coolapp).
<version>The project's version (e.g. 0.0.1-SNAPSHOT).
<properties>Reusable values, such as <java.version>21</java.version>.
<dependencies>The list of libraries the project needs.
<build> / <plugins>Tools that run during the build, such as the Spring Boot plugin.
Q5. What are GAV coordinates?
GAV = GroupId, ArtifactId, Version. Together they uniquely identify any project or library in the Maven world, like a postal address.
Example: In the shared POM, the app's address is com.springboot : coolapp : 0.0.1-SNAPSHOT.
Q6. What does SNAPSHOT mean in the version?
SNAPSHOT means the project is still in development (not a final release). Maven treats snapshot versions as changeable, so it can pick up the latest build.

3. The Parent and Spring Boot Starter Parent

From the shared pom.xml<parent> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-parent</artifactId> <version>4.0.6</version> <relativePath/> </parent>
Q1. What is a parent in Maven?
A parent is another POM that your project inherits from. Your project automatically gets the parent's settings, dependency versions, and plugin configuration, so you do not have to repeat them.
Q2. What is the Spring Boot starter parent?
spring-boot-starter-parent is a special parent POM provided by Spring Boot. It gives your project:
  • Tested, compatible versions for hundreds of libraries (so you do not write versions yourself).
  • Sensible defaults for the Java compiler, UTF-8 encoding, and common plugins.
  • Plugin configuration such as the Spring Boot Maven plugin settings.
Why it is important: This is why most dependencies in the POM have no <version> tag — the parent already decides the correct version, keeping all libraries compatible.
Q3. Why do most dependencies have no version number?
Because the Spring Boot parent's dependency management already defines the right version for them. You only write a version when you use a library the parent does not manage.
Example from the POM: spring-boot-starter-data-jpa has no version (managed by the parent), but spring-boot-starter-validation has <version>4.1.0-M4</version> because a specific version was forced.
Q4. What does <relativePath/> mean in the parent?
An empty <relativePath/> tells Maven not to look for the parent POM in a local folder, and instead download it from the repository. The comment in the file says exactly this: "lookup parent from repository".
Q5. Can I build a Spring Boot app without the starter parent?
Yes, but then you must import Spring Boot's dependency versions yourself using a BOM (Bill of Materials) inside <dependencyManagement>. The parent is simply the easiest way.

4. Dependencies in the POM (Explained)

Q1. What is a dependency?
A dependency is a library (JAR file) your project needs to work. You list it once in the POM and Maven downloads it for you.
Q2. What is a "starter" dependency?
A starter is a bundle of related libraries grouped under one name, so you add many things in one line.
Example: spring-boot-starter-data-jpa brings in JPA, Hibernate, and the database connection libraries together.
Q3. What does each dependency in the shared POM do?
DependencyPurpose
spring-boot-starter-webmvcBuild web apps and REST APIs; includes Spring MVC and an embedded Tomcat server.
spring-boot-devtoolsDeveloper convenience: automatic restart and live reload while coding.
spring-boot-starter-thymeleafThymeleaf template engine to build HTML pages on the server.

Q4. What is the Spring Boot Maven plugin (in <build>)?
It packages the app into a single runnable "fat JAR" that contains your code, all libraries, and the embedded server, so you can run it with java -jar app.jar.

5. Dependency Scope (Deep Dive)

Q1. What is a dependency scope?
A scope tells Maven when a dependency is needed — while compiling, while testing, while running, or all of these. It controls where the library is available and whether it is shipped in the final package.
Q2. Why do we use scope? (commonly asked)
To keep the build correct and the final package small. For example, testing libraries should not be shipped inside your production JAR, and a database driver is only needed when the app runs, not when it compiles.
Example from the POM: mysql-connector-j uses runtime scope (needed to run, not to compile), and spring-boot-starter-webmvc-test uses test scope (only for tests).
Q3. What values can scope take?
ScopeAvailable duringShipped in JAR?Example
compile (default)Compile, test, runYesSpring Web, most libraries
providedCompile, testNo (the server provides it)Servlet API on an external server
runtimeTest, runYesMySQL driver
testTest onlyNoJUnit, Mockito
systemCompile, testNoA local JAR given by a fixed path (rarely used)
importDependency management onlyNoImporting a BOM in <dependencyManagement>
Q4. What is the default scope if I do not write one?
The default is compile. It means the library is available everywhere (compile, test, run) and is included in the final package.
Example: In the shared POM, spring-boot-starter-validation explicitly writes <scope>compile</scope>, which is the same as the default.
Q5. Difference between provided and runtime?
  • provided: needed to compile, but NOT packaged because the runtime environment already supplies it.
  • runtime: NOT needed to compile, but needed to run (and it is packaged).
Simple way to remember: A database driver is runtime (your code talks to interfaces at compile time, the driver is only needed when running). A servlet API on an external Tomcat is provided (compile against it, but the server brings its own at runtime).

6. Other Dependency Parameters

Q1. Besides scope, what other tags can a dependency have?
TagWhat it does
<groupId>The library's group/owner.
<artifactId>The library's name.
<version>The library's version (optional if a parent/BOM manages it).
<scope>When the library is needed (compile, test, runtime, etc.).
<optional>If true, the dependency is not passed on to projects that use yours.
<exclusions>Remove an unwanted library that comes in through this dependency.
<type>The package type, default jar (can be pom, war, etc.).
<classifier>Picks a specific variant of an artifact (e.g. sources, javadoc).
Q2. What is an exclusion and when do you use it?
An exclusion removes a library that is pulled in automatically by another dependency, usually to avoid a conflict or to swap it for a different one.
Example: exclude default logging to use another<dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> <exclusions> <exclusion> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-logging</artifactId> </exclusion> </exclusions> </dependency>
Q3. What is a transitive dependency?
A dependency that comes in automatically because a library you added needs it. You did not list it, but Maven downloads it for you.
Example: Adding spring-boot-starter-data-jpa also brings Hibernate, even though you never listed Hibernate yourself.

7. Maven Lifecycle and Commands

Q1. What is the Maven build lifecycle?
A fixed sequence of build steps called phases. When you run a phase, Maven also runs every phase before it, in order.
PhaseWhat it does
validateChecks the project is correct and complete.
compileCompiles the source code into .class files.
testRuns unit tests (JUnit).
packageBundles compiled code into a JAR or WAR.
verifyRuns checks on integration test results.
installCopies the JAR into your local .m2 repository.
deployUploads the package to a remote repository for others.
Q2. What does mvn clean do, and why combine it with package?
clean deletes the target folder (old build output). We often run mvn clean package so the build starts fresh and then creates a new JAR.
Q3. Difference between package and install?
  • package creates the JAR inside the project's target folder.
  • install does everything package does, then also copies the JAR into your local .m2 repository so other local projects can use it.

8. Maven Scenario-Based Questions

Q1. Your build fails with "'dependencies.dependency.version' is missing". What is wrong?
The dependency has no version and nothing is managing it. Either add a <version> tag, or make sure a parent/BOM (like the Spring Boot parent) manages that library.
Q2. Two libraries pull in different versions of the same JAR. How do you fix it?
Let the Spring Boot parent or a BOM manage the version centrally, or set the version once in <properties>, or use <exclusions> to remove the unwanted one.
Q3. Your JAR is large and includes test libraries. What is the fix?
Check the scopes: give test-only libraries test scope and the database driver runtime scope, so they are not shipped where they are not needed.
Q4. You changed the Java version. Where do you set it?
In <properties>, for example <java.version>21</java.version> (which the Spring Boot parent reads to set the compiler).
Q5. A new library is not downloading. What do you check?
Check the GAV spelling, your internet/proxy settings, that the version exists in the repository, and try mvn clean install -U to force an update of dependencies.
Q6. Your teammate's build works but yours fails with "cannot find symbol". What could be wrong?
Your local libraries may be outdated or half-downloaded. Run mvn clean install -U to force-update dependencies, and confirm you both use the same Java version. A corrupted file in .m2 can also cause this — deleting that library folder and rebuilding fixes it.
Q7. The app runs in your IDE but java -jar app.jar fails with "no main manifest attribute". Why?
The Spring Boot Maven plugin was not used to package the JAR, so it is a plain JAR without a runnable manifest. Make sure the spring-boot-maven-plugin is in <build><plugins>, then rebuild with mvn clean package.
Q8. You want to skip tests during a quick build. How?
Run mvn clean package -DskipTests (compiles tests but does not run them) or -Dmaven.test.skip=true (does not even compile them).
Tip: Skipping tests is fine for a quick local check, but never skip them in the real build pipeline.
Q9. Two team members get different results from the same build. How does Maven help avoid this?
Maven uses the same POM, the same fixed dependency versions, and the same standard folder layout for everyone, so builds are repeatable. Locking versions (via the parent/BOM) is what removes "works on my machine" problems.
Q10. How do you see the full list of libraries your project actually uses (including transitive ones)?
Run mvn dependency:tree. It prints a tree showing every direct dependency and the transitive ones each pulls in — very useful to spot duplicate or conflicting versions.
Q11. You added a dependency but the IDE still says "class not found". What do you do?
Reload/refresh the Maven project (so the IDE re-reads the POM), confirm the dependency downloaded into .m2, and check the scope is not test when you need it in main code.

Q1. What is application.properties?
It is the main configuration file of a Spring Boot app, kept in src/main/resources. It holds settings as key=value pairs, so you can change behavior without editing Java code.

Spring Boot follows "convention over configuration". By default it looks for a file named exactly application.properties (or application.yml) on the classpath, so it loads automatically with no extra setup.

10. SQL Dialect, ddl-auto, Logging Q&A

Q1. What is a SQL dialect?
A dialect tells Hibernate which database's SQL flavor to generate. Different databases have small differences in their SQL (data types, functions, pagination). The dialect makes Hibernate produce SQL that the chosen database understands.
Example: org.hibernate.dialect.MySQLDialect makes Hibernate write MySQL-friendly SQL. For PostgreSQL you would use PostgreSQLDialect instead.
Q2. Do I always need to set the dialect?
Usually no — modern Hibernate can detect it automatically from the database connection. You set it manually when you want to be explicit or override the detected one.
Q3. What values can ddl-auto take?
ValueWhat Hibernate does
noneDoes nothing to the schema (safest for production).
validateChecks that tables match your entities, but changes nothing.
updateCreates missing tables/columns and updates the schema to match entities.
createDrops and re-creates the schema every time the app starts.
create-dropLike create, and also drops the schema when the app stops.
Tip: Use update while learning. Use validate or none in production so the app never changes your tables by accident.
Q4. What is the difference between show-sql and the Hibernate SQL log level?
  • spring.jpa.show-sql=true simply prints SQL to the console.
  • logging.level.org.hibernate.SQL=trace routes the SQL through the logging system, giving more control (format, destination, level).
Q5. What do logging levels mean?
From least to most detailed: ERROR → WARN → INFO → DEBUG → TRACE. Setting a level shows that level and everything more severe than it.
Example: logging.level.root=warn hides routine info messages and shows only warnings and errors, keeping the console clean.
Q6. How do I see the actual values inside the SQL (the "?" parameters)?
Turn on trace logging for the parameter binder. The correct package in modern Hibernate is org.hibernate.orm.jdbc.bind:
Show bound parameter valueslogging.level.org.hibernate.orm.jdbc.bind=trace
Note: The shared file uses org.orm.jdbc.bind, which is a small typo; the working package name is org.hibernate.orm.jdbc.bind.
Q7. How do I change the server port and why would I?
Set server.port=8088 (any free port). You change it to avoid clashing with another app already using the default 8080, or to match a required environment.
Example: With server.port=8088, you open the app in a browser at http://localhost:8088.

11. More Frequently Asked Maven Questions

Q1. What is the difference between a JAR and a WAR?
A JAR (Java ARchive) packs Java classes and resources; a Spring Boot app is usually a runnable "fat JAR" with an embedded server. A WAR (Web ARchive) is meant to be deployed inside an external server like Tomcat.
Beginner tip: With Spring Boot you normally build a JAR and just run java -jar app.jar — no separate server to install.
Q2. What is the .m2 folder?
It is your local Maven repository on your computer (usually in your user home folder). Every library Maven downloads is cached here so future builds are faster and can work offline.
Q3. What is settings.xml?
A Maven configuration file (inside .m2) where you set machine-wide things like proxy settings, mirror repositories, and login credentials for private repositories. The POM describes the project; settings.xml describes your environment.
Q4. What is a BOM (Bill of Materials)?
A special POM that only lists versions of related libraries. You import it so all those libraries use compatible versions without writing each version yourself.
Example: The Spring Boot parent works like a BOM — that is why most dependencies in your POM need no version number.
Q5. What are <properties> used for?
They store reusable values in one place. You define a value once and reference it as ${name} elsewhere, so updating it is a single change.
Reusing a property<properties> <java.version>21</java.version> </properties>
Q6. What does mvn validate do?
It checks that the project structure and POM are correct and that all needed information is available, without compiling anything. It is the very first phase of the build.
Q7. Difference between dependencies and dependencyManagement?
  • <dependencies>: libraries that are actually added to the project.
  • <dependencyManagement>: only declares versions to use if a dependency is added; it does not add anything by itself. Great for keeping versions consistent across modules.
Q8. What is a multi-module Maven project?
A parent project that groups several sub-projects (modules), each with its own POM. The parent lists the modules and shared settings, so you build them all together.
Example: A project split into user-service, order-service, and a shared common module.
Q9. What is the packaging element in a POM?
It tells Maven what to build: jar (default), war, or pom (for a parent/aggregator project that builds no code of its own).
Q10. How do you run a Spring Boot app with Maven during development?
Use mvn spring-boot:run. It compiles and starts the app directly without first building a JAR, which is handy while coding.

12. Maven Plugins, Goals & Profiles

Q1. What is a Maven plugin?
A plugin is a tool that adds work to the build, such as compiling code, running tests, or packaging a JAR. Maven itself is small; plugins do the real tasks.
Q2. What is a goal?
A goal is a single task a plugin can perform. You write it as plugin:goal.
Example: spring-boot:run — the run goal of the Spring Boot plugin. dependency:tree — the tree goal of the dependency plugin.
Q3. What is the difference between a phase and a goal?
A phase is a step in the lifecycle (like compile or package). A goal is a specific task. Phases run the goals bound to them. For example, the package phase runs the goal that builds the JAR.
Q4. What does the Spring Boot Maven plugin do exactly?
It repackages the normal JAR into an executable "fat JAR" that bundles all dependencies and the embedded server, and it provides the spring-boot:run goal to start the app during development.
Q5. What is a Maven profile?
A profile is a set of settings you can switch on for a situation, such as dev, test, or prod. It lets one POM behave differently in different environments.
A simple profile<profiles> <profile> <id>dev</id> <properties> <env>development</env> </properties> </profile> </profiles>
Run it with: mvn package -Pdev (the -P flag activates a profile).

13. More Dependency & Scope Scenarios

Q1. Scenario: your JAR works but is missing the MySQL driver at runtime. What scope should the driver have?
runtime. The driver is not needed to compile (your code uses JDBC/JPA interfaces), but it must be present and packaged so the app can connect at run time. This matches mysql-connector-j in the shared POM.
Q2. Scenario: JUnit appears in your production JAR. How do you stop that?
Give it test scope. Test libraries should only be available while running tests and must not be shipped in the final package.
Q3. Scenario: you deploy a WAR to an external Tomcat that already has the Servlet API. What scope avoids a conflict?
provided. You compile against the Servlet API, but the server supplies it at runtime, so it is not packaged in your WAR.
Q4. Scenario: two libraries bring two different Hibernate versions. How do you control which one wins?
Let the Spring Boot parent/BOM decide the version, or pin the version yourself in <dependencyManagement>, or use <exclusions> to drop the unwanted copy. Use mvn dependency:tree to see where each version comes from.
Q5. Scenario: you only want a library while developing (like devtools), not in production. What helps?
Mark it <optional>true</optional> so it is not passed on to other projects, and Spring Boot automatically disables devtools in a packaged production run. In the shared POM, spring-boot-devtools is exactly this kind of developer-only helper.
Q6. Scenario: how do you add a library that is not in the parent's managed list?
Add it with an explicit <version>. In the shared POM this is why spring-boot-starter-validation includes its own <version>4.1.0-M4</version>.
Q7. Scenario: you need a library only to read a local JAR file by path. Which scope (rarely used)?
system, combined with a <systemPath> to the JAR. It is discouraged because the build then depends on a fixed file path, but it exists for special cases.

14. More application.properties Questions

Q1. Where exactly does this file live, and can it be YAML instead?
It lives in src/main/resources. Yes — you can use application.yml instead, which uses indentation instead of dots. Both do the same job; pick one style.
Q2. What does createDatabaseIfNotExist=true in the URL do?
It tells MySQL to create the database (here home) automatically if it does not already exist, so you do not have to create it by hand first. It is convenient for learning, but in production the database is usually created in advance.
Q3. Is it safe to keep the database password in this file?
For learning it is fine. For real projects, avoid hard-coding secrets — use environment variables or a secrets manager. Spring can read them like spring.datasource.password=${DB_PASSWORD}.
Q4. How do I reference an environment variable inside the file?
Use ${VARIABLE_NAME}. Spring replaces it with the value from the environment at startup.
Reading values from the environmentspring.datasource.username=${DB_USER} spring.datasource.password=${DB_PASSWORD}
Q5. How can I add my own custom property and read it in code?
Add any key=value line, then read it in Java with @Value.
application.propertiesapp.welcome-message=Hello from config // In a Spring bean @Value("${app.welcome-message}") private String welcomeMessage;
Q6. What happens if two properties set the same key?
The last one wins within the same file. Across sources, more specific sources (like command-line arguments or environment variables) override the file, following Spring Boot's property order.
Q7. What does spring.main.banner-mode=off actually change?
It hides the big Spring logo printed in the console at startup. It has no effect on how the app works — it just keeps the console output clean.
Q8. How do I turn off SQL logging once I am done debugging?
Set spring.jpa.show-sql=false and raise the log levels back (for example remove the trace lines or set them to warn), so the console is not flooded with SQL.

15. Profiles & Multiple Environments

Q1. How do I keep different settings for development and production?
Use profile-specific files: application-dev.properties and application-prod.properties, plus the shared application.properties. Spring loads the shared file always, then the file for the active profile.
Q2. How do I choose which profile is active?
Set spring.profiles.active=dev in application.properties, or pass it at startup: java -jar app.jar --spring.profiles.active=prod.
Q3. Scenario: dev uses a local database, prod uses a company server. How do you organize this?
Put the local database URL in application-dev.properties and the company URL in application-prod.properties. Keep common settings (like logging format) in the shared application.properties. Switch with the active profile.
Q4. Why are profiles useful for beginners to know?
Because they avoid editing the same file every time you move between your laptop and a server. You set values once per environment and just switch the active profile.
