Test-Driven Development (TDD)

TDD is a way of writing software where you write the test BEFORE the code. It feels backwards at first — but for banking software where every rupee matters, it is the safest approach known.

What it is

TDD is a software development methodology where automated tests are written before the production code itself. The developer first describes the expected behaviour as a test, watches it fail, then writes just enough code to make it pass, and finally cleans up the code.

Why it matters

In banking, every line of code that handles money must be trustworthy. TDD ensures every behaviour — depositing, withdrawing, calculating interest — is verified by an executable test. If a future developer changes the code in a way that breaks deposit logic, the test catches it immediately. No bug reaches production undetected.

Where it is used

  • Core banking systems (transaction processing, ledger entries, balance updates)
  • Payment gateways and UPI integrations
  • Interest calculation engines for loans, fixed deposits, recurring deposits
  • Fraud detection and transaction validation services
  • Mobile banking apps where one wrong move can lose customer trust

How to use it — step by step

  1. Write a failing test that describes one tiny behaviour (e.g., "deposit of ₹1000 should increase balance by ₹1000")
  2. Run it — confirm it FAILS (this is the "Red" phase)
  3. Write the SMALLEST piece of production code that makes the test pass (the "Green" phase)
  4. Run it — confirm it PASSES
  5. Refactor the code if needed, keeping the test passing (the "Refactor" phase)
  6. Repeat for the next behaviour

The Red-Green-Refactor Cycle

The heart of TDD is a simple three-stage loop. Every new feature follows the same rhythm:

1. RED

Write a test for behaviour that doesn't exist yet. Run it. It fails. This proves your test is actually checking something.

2. GREEN

Write the minimum code to make the test pass. Don't add anything extra. Don't optimize yet. Just turn red into green.

3. REFACTOR

Clean up the code while keeping tests green. Improve names, remove duplication, simplify logic. Tests remain your safety net.

Detailed notes — TDD explained with a bank analogy

Imagine you are designing a bank vault. You wouldn't just throw money inside and hope it stays safe. You would first define the safety requirements — "the vault must withstand X impact, Y heat, Z time of break-in attempts" — and then build the vault to meet those requirements. TDD works the same way:

  • The test = the safety requirement ("deposits must always be positive amounts")
  • The failing test = the empty vault site before construction begins
  • The minimum passing code = the first wall of the vault
  • Refactoring = polishing and reinforcing the structure
  • Continuous test runs = security audits checking the vault still meets requirements

Step-by-Step Usage Guide — Applying TDD

Pick one tiny behaviour — not a whole feature. Example: "deposit increases balance by exact amount". Not "build the deposit feature".

Write the test in the test folder (src/test/java). Name it descriptively (depositIncreasesBalance).

Run the test. Confirm it FAILS. If it passes by accident, your test is wrong.

Write the smallest possible code in src/main/java to make the test pass. Do NOT add extra features.

Run the test again. Confirm it PASSES. If not, fix the code (not the test).

Refactor. Rename variables, extract methods, remove duplication. Tests must stay green.

Pick the next behaviour. Repeat. Each cycle should take 5–15 minutes — not hours.

Section Summary — TDD

  • TDD writes tests first, then code, then refactor. The Red-Green-Refactor cycle is the heartbeat.
  • In banking, every behaviour (deposit, withdraw, transfer, interest, daily limits) gets a test before implementation.
  • Edge cases like zero amounts, negatives, insufficient balance, daily limits are caught early — not in production.
  • Refactoring is safe because tests catch any regression instantly.
  • Each TDD cycle should be small — 5 to 15 minutes per behaviour. Tiny steps, fast feedback.

JUnit 5 — Java's Testing Engine

JUnit is the framework that runs your tests. It provides the annotations to mark tests, the assertions to check results, and the lifecycle hooks to set up and tear down test data.

What it is

JUnit 5 is the de-facto standard Java testing framework. A "test" is just a method annotated with @Test. JUnit discovers all such methods in your test classes, runs them, and reports which passed and which failed.

Why it matters

Without JUnit, you would have to write a main() method, manually call your code, manually print results, and manually check correctness. JUnit automates all of this. One command — mvn test — runs hundreds of test cases and shows you which (if any) fail.

Where it is used

  • Every Java project at every bank — Citi, HDFC, ICICI, SBI, JP Morgan, Goldman Sachs
  • CI/CD pipelines that block bad code from being merged
  • Pre-commit hooks that ensure no regression escapes the developer's laptop
  • Test reports that auditors review during compliance checks

How to use it — step by step

  1. Add the JUnit 5 dependency to your pom.xml
  2. Create test class in src/test/java with name ending in Test
  3. Write methods annotated with @Test
  4. Use assertions like assertEquals, assertTrue, assertThrows
  5. Run with mvn test or click the green ▶ in your IDE

Mockito — Faking External Dependencies

Mockito lets you create fake versions of services your code depends on. In banking — payment gateways, SMS senders, fraud detection APIs, audit loggers — these external services would be slow, expensive, or impossible to test against directly.

What it is

Mockito is a Java mocking framework that creates fake (mock) implementations of interfaces or classes. You control exactly what the mock returns when its methods are called, and you can verify that the mock was used correctly afterwards.

Why it matters

Imagine testing a "transfer money" feature. The real implementation calls a payment gateway that charges real money, an SMS service that sends real texts, and a database. With real services, your tests would be slow, flaky, and expensive. With mocks, the tests are fast, deterministic, and free.

Where it is used

  • Mocking payment gateways (Razorpay, Stripe, PayPal) so tests don't make real charges
  • Mocking SMS / email services so tests don't spam customers
  • Mocking fraud detection APIs to simulate "fraud detected" responses
  • Mocking database repositories to test logic without a running DB
  • Mocking core banking system calls (CBS) that are too costly to run

How to use it — step by step

  1. Add Mockito dependency (mockito-junit-jupiter)
  2. Annotate test class with @ExtendWith(MockitoExtension.class)
  3. Declare dependencies as @Mock
  4. Declare your class under test as @InjectMocks
  5. Use when(mock.method()).thenReturn(...) to control behaviour
  6. Use verify(mock).method(...) to confirm correct calls

The Mockito mental model

★
WHEN → ACT → VERIFY

WHEN: Configure the mock — tell it what to return for specific inputs.
ACT: Call the real method you want to test. It uses the mocks internally.
VERIFY: Check the result AND verify the mock was called the way you expected.

Essential Mockito methods

@MockCreate a fake object of this type
@InjectMocksBuild the class under test and inject all @Mocks

verify(mock).x()"Check that x() was called"

JaCoCo — Measuring Test Coverage

JaCoCo answers one question every bank's audit team asks: "Did your tests actually run all the code that handles money?" It produces colour-coded HTML reports showing which lines are tested (green) and which are dangerously untested (red).

What it is

JaCoCo (Java Code Coverage) is a tool that watches your tests execute and records exactly which lines, branches, methods, and classes of your production code were actually run by the tests. It then generates HTML reports with percentages and visual highlights.

Why it matters

You can have 100 tests and still cover only 40% of your code. Untested lines are landmines — they will fail in production. In banking, an untested line in the interest calculator could mean millions of rupees miscalculated. JaCoCo shows you exactly where the gaps are so you can write tests to fill them.

Where it is used

  • Every CI/CD pipeline at major banks — Maven, Gradle, Jenkins, GitLab CI
  • Quality gates that fail the build if coverage drops below a threshold (e.g., 80%)
  • Regulatory compliance — auditors require evidence that critical code paths are tested
  • Code review tools (SonarQube, Codacy) that show coverage on every pull request
  • Identifying dead code that no test exercises — often safe to remove

How to use it — step by step

  1. Add the JaCoCo Maven plugin to your pom.xml
  2. Run mvn clean test — JaCoCo silently records coverage
  3. Open target/site/jacoco/index.html in a browser
  4. Click into packages → classes → see line-by-line colours
  5. Write new tests for the red (untested) lines

Coverage types JaCoCo measures

Line
Line Coverage

% of code lines that executed at least once. "85 of 100 lines = 85%"

Branch
Branch Coverage

% of if/else paths tested. Both branches of an if must be tested for 100%.

Method
Method Coverage

% of methods called by at least one test. Untouched methods stand out.

Class
Class Coverage

% of classes used by tests. Whole untested classes are alarms.

Detailed notes — the bank vault analogy

Imagine your banking software is a vault with 100 locks. Tests are the keys you check. If you only test 60 of 100 locks, JaCoCo says "60% coverage". The 40 locks you never tested could be jammed, broken, or wide open. JaCoCo highlights exactly which locks need attention:

  • Green line = lock tested and works
  • Yellow line = lock partially tested (only one branch verified)
  • Red line = lock never tested — potential disaster waiting to happen

SpotBugs — Catching Hidden Bugs in Bytecode

SpotBugs scans your compiled bytecode (.class files) looking for over 400 known bug patterns. It catches sneaky mistakes that compile fine, even pass tests, but explode in production.

What it is

SpotBugs is a static analysis tool that examines compiled Java bytecode for patterns known to cause bugs — null pointer dereferences, incorrect string comparisons, resource leaks, thread safety issues, and security vulnerabilities like SQL injection.

Why it matters

Some banking bugs only appear under specific conditions — a customer's name happens to be null, two account numbers happen to compare with == instead of .equals(), a connection isn't closed. Tests might not catch these. SpotBugs reads the code and warns about them before they ever execute.

Where it is used

  • Build pipelines that block merges if bugs are detected
  • Pre-commit checks on developer machines
  • Security audits — SpotBugs has a security-focused FindSecBugs plugin
  • Code review automation (SonarQube integrates with SpotBugs)
  • Banking compliance — proving due diligence in detecting known bug patterns

How to use it — step by step

  1. Add the SpotBugs Maven plugin to pom.xml
  2. Compile your code first: mvn compile
  3. Run mvn spotbugs:check — fails build if bugs found
  4. Or generate report: mvn spotbugs:spotbugs
  5. Open the GUI: mvn spotbugs:gui to browse findings visually

PMD — Catching Source-Code Smells

PMD reads your .java source files (not bytecode like SpotBugs) and flags common programming flaws — unused variables, empty catch blocks, overly complex methods, duplicated code, and many more.

What it is

PMD (Programming Mistake Detector) is a static source code analyzer for Java and other languages. It uses rule sets to detect "code smells" — things that are not exactly bugs but reduce maintainability, readability, and reliability.

Why it matters

Banking codebases live for decades. Code written in 2010 still runs in 2026. If that code is full of unused variables, magic numbers, and bloated methods, every change becomes risky. PMD enforces cleanliness so future developers can safely modify deposit, withdrawal, and interest logic.

Where it is used

package com.bank.model;

import java.math.BigDecimal;
import java.util.*;

/** A bank account holding balance, owner and transaction history. */
public class Account {

    public static final BigDecimal MIN_BALANCE = new BigDecimal("500");

    private final String accountNumber;
    private final String ownerName;
    private BigDecimal balance;
    private boolean frozen;
    private final List<Transaction> history;

    public Account(String accountNumber, String ownerName) {
        this.accountNumber = Objects.requireNonNull(accountNumber);
        this.ownerName     = Objects.requireNonNull(ownerName);
        this.balance       = BigDecimal.ZERO;
        this.history       = new ArrayList<>();
    }

    public void deposit(BigDecimal amount) {
        if (frozen) {
            throw new IllegalStateException("Account is frozen");
        }
        if (amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("Deposit must be positive");
        }
        balance = balance.add(amount);
        history.add(Transaction.deposit(amount));
    }

    public void withdraw(BigDecimal amount) {
        if (frozen) {
            throw new IllegalStateException("Account is frozen");
        }
        if (amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("Withdrawal must be positive");
        }
        BigDecimal newBalance = balance.subtract(amount);
        if (newBalance.compareTo(MIN_BALANCE) < 0) {
            throw new IllegalStateException("Insufficient funds");
        }
        balance = newBalance;
        history.add(Transaction.withdraw(amount));
    }

    public BigDecimal getBalance()       { return balance; }
    public String     getAccountNumber() { return accountNumber; }
    public String     getOwnerName()     { return ownerName; }
    public boolean    isFrozen()         { return frozen; }
    public void       freeze()           { frozen = true; }

    public List<Transaction> getHistory() {
        return Collections.unmodifiableList(history);
    }
}

package com.bank.service;

import com.bank.dao.AccountDao;
import com.bank.model.Account;
import java.math.BigDecimal;

public class DepositService {

    private final AccountDao dao;
    private final FraudDetector fraud;
    private final NotificationService notifier;
    private final AuditLog audit;

    public DepositService(AccountDao dao, FraudDetector fraud,
                          NotificationService notifier, AuditLog audit) {
        this.dao      = dao;
        this.fraud    = fraud;
        this.notifier = notifier;
        this.audit    = audit;
    }

    public String deposit(String accId, BigDecimal amount) {
        Account account = dao.findById(accId);
        if (account == null) {
            return "NOT_FOUND";
        }
        if (fraud.isFraudulent(accId, amount)) {
            audit.log("FRAUD_BLOCKED", accId, amount);
            return "FRAUD_BLOCKED";
        }

        account.deposit(amount);
        dao.save(account);
        audit.log("DEPOSIT", accId, amount);
        notifier.sendSms(accId, "Deposited Rs." + amount);
        return "SUCCESS";
    }
}
04TransferService — atomic transfer

package com.bank.service;

import com.bank.dao.AccountDao;
import com.bank.model.Account;
import java.math.BigDecimal;

public class TransferService {

    private final AccountDao dao;
    private final AuditLog audit;

    public TransferService(AccountDao dao, AuditLog audit) {
        this.dao   = dao;
        this.audit = audit;
    }

    public String transfer(String fromId, String toId, BigDecimal amt) {
        if (fromId.equals(toId)) return "SAME_ACCOUNT";

        Account from = dao.findById(fromId);
        Account to   = dao.findById(toId);
        if (from == null || to == null) return "NOT_FOUND";

        try {
            from.withdraw(amt);   // throws if insufficient
            to.deposit(amt);
            dao.save(from);
            dao.save(to);
            audit.log("TRANSFER", fromId + "→" + toId, amt);
            return "SUCCESS";
        } catch (IllegalStateException e) {
            return "INSUFFICIENT_FUNDS";
        }
    }
}

    public BigDecimal simpleInterest(BigDecimal principal,
                                       BigDecimal rate,
                                       int years) {
        return principal.multiply(rate)
                        .multiply(BigDecimal.valueOf(years))
                        .divide(new BigDecimal("100"), 2, RoundingMode.HALF_UP);
