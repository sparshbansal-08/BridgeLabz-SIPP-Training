Copy Constructor

Making a real, independent duplicate of an object

📘
What is it?

A copy constructor is a special constructor that creates a NEW object by copying values from an EXISTING object of the same class. Think of it as a "duplicate maker."

In Java, you have to write it yourself (Java doesn't make one for you automatically).

💡
Why does it matter?

If you just write Account b = a;, you're NOT copying. Both a and b point to the SAME object in memory. Change one, the other also changes — which causes serious bugs in banking, HR, or e-commerce systems.

A copy constructor solves this by creating a truly separate object with the same values.

📅
When to use it?
  • Taking a backup of an account before risky transactions
  • Duplicating an order to create a refund version
  • Cloning an employee record for a similar new hire
  • Creating "what-if" copies you can modify safely
🏦 Real-World Analogy — Bank Locker Duplicate Key

When you ask the bank for a duplicate key to your locker, they don't give you the same key. They make a brand new key with the exact same shape. Both keys open the same locker, but losing one doesn't affect the other.

A copy constructor works exactly like this — it creates a fresh, independent object with the same data as the original.

🛠️ Syntax — How to Write It

Basic syntax
public class ClassName {
    private Type field1;

    // Regular constructor
    public ClassName(Type f1) { this.field1 = f1; }

    // ── COPY CONSTRUCTOR — takes another instance of THE SAME CLASS
    public ClassName(ClassName other) {
        this.field1 = other.field1;   // copy each field
    }
}

🏦 Real Scenario — Account Snapshot Before Transfer

Imagine SBI Bank wants to take a "snapshot" of an account before transferring money. If the transfer fails, they can compare with the snapshot to fix the problem.

BankAccount.java
public class BankAccount {
    private String accountNumber;
    private String holderName;
    private double balance;

    // ── Regular constructor
    public BankAccount(String accNo, String name, double bal) {
        this.accountNumber = accNo;
        this.holderName    = name;
        this.balance       = bal;
    }

    // ── COPY CONSTRUCTOR — creates a duplicate
    public BankAccount(BankAccount source) {
        this.accountNumber = source.accountNumber;
        this.holderName    = source.holderName;
        this.balance       = source.balance;
        System.out.println("📋 Snapshot created");
    }

    public void withdraw(double amount) { balance -= amount; }

    public void show() {
        System.out.println(accountNumber + " | " + holderName + " | ₹" + balance);
    }

    public static void main(String[] args) {
        BankAccount live = new BankAccount("SBI001", "Priya", 50000);

        // Take a backup using the copy constructor
        BankAccount backup = new BankAccount(live);

        // Withdraw from live account
        live.withdraw(45000);

        System.out.println("Live   : "); live.show();      // ₹5000
        System.out.println("Backup : "); backup.show();    // ₹50000 (untouched!)
    }
}

📝 Code Explanation — Step by Step

Step 1: We create a normal account called live with ₹50,000.

Step 2: new BankAccount(live) calls the COPY constructor (Java picks it because we passed another BankAccount object). It creates backup with the same values.

Step 3: When we withdraw from live, only live changes. The backup stays at ₹50,000 because they are two SEPARATE objects in memory.

✅ Benefits

✓
Independence: Original and copy work separately.
✓
Safety: Take backups before risky operations.
✓
Audit: Keep history while making changes.
✓
No Bugs: Avoids reference-sharing problems.
BeginnerPractice 1 — Order Refund Duplicate

Create a class Order for Flipkart with fields: orderId, customer, product, amount, and status (default "ACTIVE"). Write a copy constructor. In main, create an order, then a refund copy. Change the refund's status to "REFUNDED" and show that the original is still "ACTIVE".

Order.java — Solution
public class Order {
    private String orderId, customer, product, status;
    private double amount;

    public Order(String id, String cust, String prod, double amt) {
        this.orderId = id;
        this.customer = cust;
        this.product = prod;
        this.amount = amt;
        this.status = "ACTIVE";
    }

    // Copy constructor
    public Order(Order other) {
        this.orderId  = other.orderId + "-RFD";
        this.customer = other.customer;
        this.product  = other.product;
        this.amount   = other.amount;
        this.status   = other.status;
    }

    public void setStatus(String s) { this.status = s; }
    public void show() {
        System.out.println(orderId + " | " + customer + " | " + product + " | " + status);
    }

    public static void main(String[] a) {
        Order o1 = new Order("FK001", "Rahul", "iPhone", 79900);
        Order refund = new Order(o1);
        refund.setStatus("REFUNDED");
        o1.show();      // FK001 | Rahul | iPhone | ACTIVE
        refund.show();  // FK001-RFD | Rahul | iPhone | REFUNDED
    }
}

Method Overloading

Same method name, different inputs — flexible methods for different situations

📘
What is it?

Method overloading means writing MULTIPLE methods with the SAME NAME but DIFFERENT parameters in the SAME class. Java picks the correct one based on what you pass to it.

This is called compile-time polymorphism because Java decides which method to use while compiling your code.

💡
Why does it matter?

Imagine you have a calculator. You want add() to work with 2 numbers, 3 numbers, integers, or decimals. Without overloading, you'd need ugly names like add2Ints, add3Ints, add2Doubles... With overloading, you just call add() and Java figures out which version to use.

📞 Real-World Analogy — Restaurant Menu

At a restaurant, when you order "Pizza", the chef makes different pizzas based on what you add:

• "One pizza" → Margherita (default)
• "One pizza with mushroom" → Mushroom pizza
• "One pizza with mushroom and cheese" → Mushroom-cheese pizza

Same word "Pizza", different result based on what extras you mention. That's overloading!

⚙️ The 3 Ways to Overload

1. Different number of parameters

add(int, int) vs add(int, int, int)

2. Different parameter types

add(int, int) vs add(double, double)

3. Different order of parameters

display(String, int) vs display(int, String)

⚠️
What does NOT count as overloading?

Just changing the return type is NOT enough. int add(int, int) and double add(int, int) will give a compile error — Java can't tell which one to call.

🏦 Real Scenario — Bank Transfer Methods

BankService.java — Method overloading
public class BankService {

    // Version 1: Transfer using account number (string)
    public void transfer(String accountNo, double amount) {
        System.out.println("Sent ₹" + amount + " to account " + accountNo);
    }

    // Version 2: Transfer using UPI ID
    public void transfer(String upiId, double amount, String note) {
        System.out.println("UPI: ₹" + amount + " to " + upiId + " — " + note);
    }

    // Version 3: Transfer with scheduled date
    public void transfer(String accountNo, double amount, String date, boolean scheduled) {
        System.out.println("Scheduled ₹" + amount + " to " + accountNo + " on " + date);
    }

    public static void main(String[] args) {
        BankService b = new BankService();

        // Java picks the right version based on what you pass
        b.transfer("SBI001", 5000);                       // → Version 1
        b.transfer("rahul@upi", 200, "Lunch");             // → Version 2
        b.transfer("SBI002", 10000, "2026-06-01", true);    // → Version 3
    }
}

📝 Explanation

All three methods are named transfer, but each has DIFFERENT parameters. Java automatically picks the right one based on what you pass.

The user doesn't need to remember three different method names — just transfer() with the right inputs.

✅ Benefits

✓
Cleaner code: One method name instead of many.
✓
Flexible: Use the same method in many situations.
✓
Easy to read: Code reads more naturally.
✓
No confusion: Java picks the right version automatically.

Create a Calculator class with 4 versions of an add method:

  1. add(int a, int b) — adds 2 integers
  2. add(int a, int b, int c) — adds 3 integers
  3. add(double a, double b) — adds 2 doubles
  4. add(String a, String b) — concatenates 2 strings

public class Calculator {

    public int add(int a, int b)            { return a + b; }

    public int add(int a, int b, int c)     { return a + b + c; }

    public double add(double a, double b)   { return a + b; }

        System.out.println(c.add(1, 2, 3));               // 6
        System.out.println(c.add(2.5, 3.5));              // 6.0
        System.out.println(c.add("Hello", "World"));     // Hello World
    }
}

Method Overriding

Child class changes the behavior of a parent's method

📘
What is it?

Method overriding is when a CHILD class re-defines a method that already exists in its PARENT class. The child gives the method a NEW behavior — different from what the parent does.

This is called runtime polymorphism because Java decides which version to run while the program is actually running, based on the type of object.

👨‍👩‍👧 Real-World Analogy — Family Recipe

Your grandmother has a recipe for "pizza" using a traditional oven. Your mom uses the same recipe name "pizza" but bakes it in a modern oven with different temperature. You inherited the recipe name but added your own twist with a microwave.

Same recipe name (method), different way of making it (behavior) — that's overriding!

📋 Rules of Method Overriding

✓
Method name must be the SAME
✓
Parameters must be SAME (same count, same types)
✓
Return type must be SAME (or sub-type)
✓
Use @Override annotation (good practice)
✓
Must be in PARENT-CHILD relationship
✓
Cannot override private, static, or final methods

💳 Real Scenario — Different Payment Types

Payment system — Method overriding
// ── PARENT class with default behavior
public class Payment {
    protected double amount;

    public Payment(double amt) { this.amount = amt; }

    public void process() {
        System.out.println("Processing payment of ₹" + amount);
    }
}

// ── CHILD class overrides process() with UPI behavior
public class UPIPayment extends Payment {
    public UPIPayment(double amt) { super(amt); }

    @Override
    public void process() {
        System.out.println("💚 UPI Payment of ₹" + amount + " — instant!");
    }
}

// ── Another CHILD class with different behavior
public class CardPayment extends Payment {
    public CardPayment(double amt) { super(amt); }

    @Override
    public void process() {
        System.out.println("💳 Card Payment of ₹" + amount + " — OTP required");
    }
}

// ── In Main:
public class Main {
    public static void main(String[] args) {
        Payment p1 = new UPIPayment(500);
        Payment p2 = new CardPayment(25000);

        p1.process();   // 💚 UPI Payment of ₹500 — instant!
        p2.process();   // 💳 Card Payment of ₹25000 — OTP required
    }
}

Encapsulation — Pillar 1 of OOP

Protecting your data — hide what's inside, expose only what's needed

📘
What is it?

Encapsulation is the idea of WRAPPING data (fields) and methods (behaviors) together inside a class, AND HIDING the data so that outside code can't directly mess with it.

You make fields private, then provide controlled access through public get and set methods.

🏦 Real-World Analogy — Bank Vault & Teller

A bank keeps money inside a VAULT. Customers can't walk into the vault to take money themselves. They go to the TELLER, who:

1. Checks ID (validation)
2. Checks balance (business rule)
3. Hands over the requested amount
4. Records the transaction

The vault is your private field. The teller is your public method. That's encapsulation!

🛡️ Real Scenario — Customer Data Protection

Customer.java — Full encapsulation
public class Customer {
    // ── All fields are PRIVATE — no direct outside access
    private String name;
    private String email;
    private int    age;
    private double balance;

    public Customer(String name, String email, int age) {
        this.name = name;
        setEmail(email);    // goes through validation
        setAge(age);        // goes through validation
        this.balance = 0;
    }

    // ── GETTERS — read-only access
    public String getName()    { return name; }
    public String getEmail()   { return email; }
    public int    getAge()     { return age; }
    public double getBalance() { return balance; }

    // ── SETTERS — with VALIDATION rules
    public void setEmail(String email) {
        if (email == null || !email.contains("@")) {
            throw new IllegalArgumentException("Bad email!");
        }
        this.email = email;
    }

    public void setAge(int age) {
        if (age < 18 || age > 120) {
            throw new IllegalArgumentException("Age 18-120 only");
        }
        this.age = age;
    }

    // ── Methods — change data only through controlled actions
    public void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    public static void main(String[] args) {
        Customer c = new Customer("Priya", "priya@gmail.com", 28);

        // c.email = "hacker";        ← compile error: private!
        // c.balance = 999999;        ← compile error: private!

        c.deposit(5000);             // ✅ proper way
        System.out.println(c.getBalance());   // 5000
    }
}

✅ Benefits

✓
Security: Sensitive data can't be accessed directly.
✓
Validation: All changes pass through your rules.
✓
Control: You decide what is read-only or writable.
✓
Maintainable: Easy to change internal logic later.

Inheritance — Pillar 2 of OOP

Reusing code — building new classes on top of existing ones

📘
What is it?

Inheritance lets a NEW class (child) automatically get all the fields and methods of an EXISTING class (parent), and add new ones of its own.

You use the extends keyword to say "this child class inherits from that parent class."

👨‍👩‍👧 Real-World Analogy — Family Traits

You inherit your last name, eye color, and some habits from your parents. But you also have your OWN unique traits. You didn't have to start from scratch — you got many things "for free" from your parents.

In code, a SavingsAccount inherits everything from BankAccount (account number, holder, balance, deposit, withdraw) AND adds its own things (interest rate, minimum balance).

🏦 Real Scenario — Bank Account Hierarchy

Inheritance — Bank accounts
// ── PARENT class (also called Super class / Base class)
public class BankAccount {
    protected String accountNo;
    protected String holderName;
    protected double balance;

    public BankAccount(String accNo, String name, double bal) {
        this.accountNo  = accNo;
        this.holderName = name;
        this.balance    = bal;
    }

    public void deposit(double amount) { balance += amount; }
    public void withdraw(double amount) { balance -= amount; }

    public void show() {
        System.out.println(accountNo + " | " + holderName + " | ₹" + balance);
    }
}

// ── CHILD class — SavingsAccount IS-A BankAccount + extras
public class SavingsAccount extends BankAccount {
    private double interestRate;

    public SavingsAccount(String accNo, String name, double bal, double rate) {
        super(accNo, name, bal);   // call parent's constructor
        this.interestRate = rate;
    }

    public void addInterest() {
        double interest = balance * interestRate / 100;
        balance += interest;
        System.out.println("Interest added: ₹" + interest);
    }
}

// ── Usage
public class Main {
    public static void main(String[] args) {
        SavingsAccount acc = new SavingsAccount("SBI001", "Priya", 50000, 5);

        // inherited methods work automatically
        acc.deposit(10000);     // from parent
        acc.addInterest();         // from child
        acc.show();                // from parent
        // SBI001 | Priya | ₹63000.0
    }
}

✓

✓

Polymorphism — Pillar 3 of OOP

One name, many forms — same call, different behavior

📘
What is it?

Polymorphism (Greek for "many forms") means ONE method or operation can behave DIFFERENTLY depending on the object it's called on.

It has 2 types: Compile-time (overloading) and Runtime (overriding) — both of which you've already learned!

🎙️ Real-World Analogy — "Speak" to Different Beings

When you say "speak" to different beings, you get different results:

• A baby says "Mama!"
• A dog barks "Woof!"
• A bird chirps
• A teacher gives a lecture

Same command, different output. That's polymorphism!

🛒 Real Scenario — E-Commerce Notification System

Polymorphism — One method, many forms
// ── PARENT class
public class Notification {
    protected String message;

    public Notification(String msg) { this.message = msg; }

    public void send() {
        System.out.println("Sending: " + message);
    }
}

// ── CHILD classes override send() differently
class EmailNotification extends Notification {
    public EmailNotification(String m) { super(m); }
    @Override public void send() {
        System.out.println("📧 Email: " + message);
    }
}

class SMSNotification extends Notification {
    public SMSNotification(String m) { super(m); }
    @Override public void send() {
        System.out.println("📱 SMS: " + message);
    }
}

class WhatsAppNotification extends Notification {
    public WhatsAppNotification(String m) { super(m); }
    @Override public void send() {
        System.out.println("💬 WhatsApp: " + message);
    }
}

// ── Polymorphism in action
public class Main {
    public static void main(String[] args) {

        // All stored as parent type — but each one acts differently
        Notification[] alerts = {
            new EmailNotification("Order shipped"),
            new SMSNotification("OTP: 123456"),
            new WhatsAppNotification("Order delivered!")
        };

        for (Notification n : alerts) {
            n.send();   // Java picks the right version!
        }
        /* Output:
           📧 Email: Order shipped
           📱 SMS: OTP: 123456
           💬 WhatsApp: Order delivered! */
    }
}

✅ Benefits

✓
Flexibility: Add new types without changing existing code.
✓
Less if/else: No need to check object type manually.
✓
Cleaner code: Common loop, different behavior.
✓
Easy to extend: Add WhatsApp, Push, Slack — no main() changes.

Abstraction — Pillar 4 of OOP

Hide complexity — show only what matters

📘
What is it?

Abstraction means hiding the COMPLEX details and showing only the SIMPLE, useful parts. You tell the user WHAT something does, but not HOW it does it.

In Java, you achieve abstraction using abstract classes and interfaces.

🚗 Real-World Analogy — Driving a Car

When you drive a car, you use the steering wheel, accelerator, and brake. You don't think about:

• How the engine combusts fuel
• How the wheels turn
• How the brake fluid flows

The car gives you a SIMPLE interface and HIDES all the engineering. That's abstraction!

🛠️ Two Ways to Achieve Abstraction

1. Abstract Class

A class declared with abstract keyword. Can have both regular methods AND abstract methods (no body). Cannot be instantiated directly.

2. Interface

A 100% pure contract — only method signatures, no implementation. Multiple interfaces can be implemented by one class.

🏦 Real Scenario — Payment System Abstraction

Payment.java — Abstract class
// ── ABSTRACT class — cannot be created directly
public abstract class Payment {
    protected double amount;

    public Payment(double amt) { this.amount = amt; }

    // ── ABSTRACT method — children MUST implement
    public abstract void processPayment();

    // ── REGULAR method — shared by all children
    public void printReceipt() {
        System.out.println("Receipt: ₹" + amount);
    }
}

// ── Concrete (real) child classes
class CreditCardPayment extends Payment {
    public CreditCardPayment(double amt) { super(amt); }

    @Override
    public void processPayment() {
        System.out.println("💳 Charging card for ₹" + amount);
        // real code (encryption, bank call) is HIDDEN from user
    }
}

class UPIPayment extends Payment {
    public UPIPayment(double amt) { super(amt); }

    @Override
    public void processPayment() {
        System.out.println("💚 UPI transfer of ₹" + amount);
    }
}

// ── Usage
public class Main {
    public static void main(String[] args) {
        // Payment p = new Payment(100);   ← ERROR! Abstract — can't instantiate

        Payment p1 = new CreditCardPayment(5000);
        Payment p2 = new UPIPayment(200);

        p1.processPayment();
        p1.printReceipt();
        p2.processPayment();
    }
}

The super Keyword

How a child class talks to its parent

📘
What is it?

The super keyword is used inside a CHILD class to refer to its PARENT class. You use it for 3 main things:

  • super(args) — call the parent's CONSTRUCTOR
  • super.methodName() — call the parent's METHOD
  • super.fieldName — access the parent's FIELD
📞 Real-World Analogy — Calling Mom for Help

When you (the child) are cooking and you don't know how to make grandma's special curry, you call your mom (the parent): "Mom, how did you make this?"

That call is super.makeCurry() — asking the parent class for its version of a method, then maybe adding your own twist after.

🛠️ Three Uses of super

Use 1: Call Parent's Constructor

super() — call parent constructor
class Vehicle {
    String brand;
    public Vehicle(String brand) {
        this.brand = brand;
        System.out.println("Vehicle " + brand + " created");
    }
}

class Car extends Vehicle {
    int wheels;
    public Car(String brand, int wheels) {
        super(brand);     // ← MUST be first line!
        this.wheels = wheels;
        System.out.println("Car has " + wheels + " wheels");
    }
}

// new Car("Toyota", 4); prints:
// Vehicle Toyota created
// Car has 4 wheels

Use 2: Call Parent's Method

super.method() — call parent method
class Employee {
    public double calculateSalary() {
        return 30000;   // basic salary
    }
}

class Manager extends Employee {
    @Override
    public double calculateSalary() {
        // First get parent's calculation, then add bonus
        double basic = super.calculateSalary();   // ← parent's version
        return basic + 15000;   // add bonus
    }
}

Manager m = new Manager();
System.out.println(m.calculateSalary());   // 45000.0

Use 3: Access Parent's Field

super.field — access parent field
class Animal {
    String color = "brown";
}

class Dog extends Animal {
    String color = "black";   // Dog has its own color

    public void showColors() {
        System.out.println("Dog color  : " + color);          // black
        System.out.println("Parent col : " + super.color);    // brown
    }
}

🏦 Full Real Scenario — Bank Account with super

SavingsAccount uses super

    protected double balance;

    public BankAccount(String owner, double balance) {
        this.owner   = owner;
        this.balance = balance;
    }

    public void show() {
        System.out.println("Owner: " + owner + " | Balance: ₹" + balance);

    private double interestRate;

    public SavingsAccount(String owner, double balance, double rate) {
        super(owner, balance);    // USE 1: parent constructor

    }

    @Override
    public void show() {
        super.show();                  // USE 2: parent method
        System.out.println("Interest Rate: " + interestRate + "%");
    }
}

Shallow Copy vs Deep Copy

Two ways to duplicate an object — and why the difference matters

📘
What is it?

When an object has fields that are OTHER objects inside it (called "nested objects"), copying it can be done two ways:

  • Shallow Copy: Only copies the top-level. Nested objects are SHARED.
  • Deep Copy: Copies everything — including all nested objects recursively. Truly independent.
📦 Real-World Analogy — Photocopying a Folder

Shallow Copy is like making a new folder cover but using THE SAME papers inside. If someone writes on the papers, both folders show the change because they share the papers.

Deep Copy is like making a new folder AND photocopying every paper inside. Now if someone writes on one paper, only that folder shows the change. They are completely independent.

🆚 Side-by-Side Comparison

🟡 Shallow Copy

  • Copies only primitive fields (int, double, etc.)
  • Nested objects are SHARED (same reference)
  • Change to nested object affects BOTH copies
  • Fast and uses less memory
  • Can cause unexpected bugs

🟢 Deep Copy

  • Copies everything — primitives AND nested objects
  • Nested objects are NEW copies
  • Changes are completely isolated
  • Slower, uses more memory
  • Safe — no shared state surprises

🏦 Real Scenario — Customer with Address

Shallow Copy Problem
class Address {
    String city;
    String street;

    public Address(String city, String street) {
        this.city = city;
        this.street = street;
    }
}

class Customer {
    String name;
    Address address;   // ← nested object!

    public Customer(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    // ── SHALLOW COPY — just copies the reference
    public Customer(Customer other) {
        this.name = other.name;
        this.address = other.address;   // ← BOTH point to SAME Address!
    }

    public void show() {
        System.out.println(name + " lives in " + address.city);
    }
}

// ── See the problem:
Address addr = new Address("Mumbai", "MG Road");
Customer c1 = new Customer("Priya", addr);
Customer c2 = new Customer(c1);   // shallow copy

// Change c2's address
c2.address.city = "Pune";

c1.show();   // Priya lives in Pune     ← OOPS! c1 also changed!
c2.show();   // Priya lives in Pune
⚠️
The Problem

Even though we made a "copy" of the customer, changing c2's address also changed c1's address. Why? Because the SAME Address object is shared between them. This is the shallow copy trap!

✅ Solution — Deep Copy

Deep Copy — true independence
class Address {
    String city, street;

    public Address(String city, String street) {
        this.city = city;
        this.street = street;
    }

    // ── Copy constructor for Address
    public Address(Address other) {
        this.city = other.city;
        this.street = other.street;
    }
}

class Customer {
    String name;
    Address address;

    public Customer(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    // ── DEEP COPY — also make a fresh copy of nested objects
    public Customer(Customer other) {
        this.name = other.name;
        this.address = new Address(other.address);   // ← fresh Address!
    }

    public void show() {
        System.out.println(name + " lives in " + address.city);
    }
}

// ── Now it works correctly:
Address addr = new Address("Mumbai", "MG Road");
Customer c1 = new Customer("Priya", addr);
Customer c2 = new Customer(c1);   // deep copy

c2.address.city = "Pune";

c1.show();   // Priya lives in Mumbai     ← UNCHANGED! ✅
c2.show();   // Priya lives in Pune

📊 Quick Decision Guide

SituationUse
Object has only primitives (int, double, String)Shallow (no difference)
Object has mutable nested objects you might changeDeep
Backup snapshots in bankingDeep
Read-only / immutable nested objectsShallow is fine
Performance is critical & you won't modify nested objectsShallow

✅ Benefits of Deep Copy

✓
True independence: Changes never leak between copies.
✓
Safe snapshots: Backups stay intact no matter what.
✓
Predictable code: No mysterious shared-state bugs.
✓
Easier testing: Each copy is its own little world.
AdvancedPractice 5 — Deep Copy an Employee with Department

Create class Department with name and location. Create class Employee with name, salary, and a Department field. Write a deep copy constructor for Employee. Test it: create an employee, copy it, change the copy's department location, and prove the original is unchanged.

class Department {
    String name;
    String location;

    public Department(String name, String location) {
        this.name = name;
        this.location = location;
    }

    // Copy constructor for Department
    public Department(Department other) {
        this.name = other.name;
        this.location = other.location;
    }
}

class Employee {
    String name;
    double salary;
    Department department;

    public Employee(String name, double salary, Department dept) {
        this.name = name;
        this.salary = salary;
        this.department = dept;
    }

    // DEEP copy constructor
    public Employee(Employee other) {
        this.name = other.name;
        this.salary = other.salary;
        this.department = new Department(other.department);   // fresh!
    }

    public void show() {
        System.out.println(name + " | ₹" + salary +
            " | " + department.name + " @ " + department.location);
    }
}

public class Main {
    public static void main(String[] args) {
        Department dept = new Department("IT", "Bangalore");
        Employee e1 = new Employee("Priya", 75000, dept);
        Employee e2 = new Employee(e1);   // deep copy

        // Change e2's department location
        e2.department.location = "Mumbai";

        e1.show();   // Priya | ₹75000 | IT @ Bangalore   ← unchanged ✅
        e2.show();   // Priya | ₹75000 | IT @ Mumbai
    }
}
