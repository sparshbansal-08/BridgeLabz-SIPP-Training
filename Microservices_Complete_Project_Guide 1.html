POINT 1

Eureka Server — Services Find Each Other by Name

Problem
Without Eureka, every service uses a hardcoded URL like http://localhost:8081. If the service moves, changes port, or scales to 3 copies, the calling service breaks.
Solution
Every service registers with Eureka using its name. Other services look up the name instead of the address. Eureka always returns a current, live address.
Simple analogy
Eureka is a hotel reception desk. Every department (service) registers its room number (address). Guests (other services) ask reception for a department — they never memorise internal room numbers.

Folder and File Structure

Project StructureSTRUCTURE
eureka-server/
  src/main/java/com/eureka/
    EurekaServerApplication.java   WHAT: main class — @EnableEurekaServer
                                   WHY:  one annotation turns this into a registry
                                   NEW:  yes — @EnableEurekaServer is new
  src/main/resources/
    application.properties         WHAT: port and server settings
  pom.xml                          WHAT: dependencies

No Entity. No Repository. No Service. No Controller.
This service has almost no code — it is configured, not programmed.

application.properties — Every Line Explained

server.port=8761
WHAT: Sets the port Eureka runs on.
WHY: Port 8761 is the industry standard for Eureka. All other services point here.
IF REMOVED: Gateway and all services cannot find Eureka — the whole system fails to discover services.
Example: If 8761 is taken, change to 8762 and update all other services.
spring.application.name=eureka-server
WHAT: The name this service registers under.
WHY: Shows up in dashboards and logs so you can identify this service.
IF REMOVED: Shows as UNKNOWN in monitoring tools.
eureka.client.register-with-eureka=false
WHAT: Tells the server NOT to register itself as a client.
WHY: Eureka Server is the registry — it should not register with itself.
IF REMOVED: Causes a confusing startup warning or error loop.
eureka.client.fetch-registry=false
WHAT: Tells the server NOT to fetch its own list.
WHY: The server IS the list — it does not need to fetch from itself.
IF REMOVED: Unnecessary startup delays and warning messages.

Eureka dashboard at http://localhost:8761 — shows no services registered yet

DependencyWhat It DoesFamiliar or NEW?If Missing

What Other Services Add to Register with Eureka

Every other service adds this one line to their application.properties:

eureka.client.service-url.defaultZone=http://localhost:8761/eureka/
WHAT: The address of the Eureka server.
WHY: Without this, the service does not know where to register — it starts but stays invisible to other services.
IF REMOVED: The service starts fine but is never registered. Other services cannot find it by name.
Section Summary: Eureka is the registry. It has almost no code — just one annotation and four properties lines. Every other service adds one line to point to it.
POINT 2

API Gateway — One Entry Point for All Services

Problem
Without a Gateway, every client must know every service port: 8081 for products, 8082 for orders, 8085 for auth. Add a new service and every client app needs updating.
Solution
The Gateway is the only address clients use: port 8080. It reads the URL and routes to the correct service automatically, using Eureka to find the current address.
Also does
The Gateway checks the JWT token on every request before forwarding it. One security checkpoint for all services.

No Entity. No Repository. No Service. No Controller.

application.properties — Every Line Explained

server.port=8080
WHAT: The single port all clients use.
WHY: 8080 is the industry convention for HTTP in development.
IF REMOVED: Gateway starts on a random or default port — clients cannot reliably reach it.
spring.application.name=api-gateway
WHAT: Name this service registers under in Eureka.
WHY: Used in logs and Eureka dashboard to identify the Gateway.
IF REMOVED: Shows as UNKNOWN in monitoring tools.
eureka.client.service-url.defaultZone=http://localhost:8761/eureka/
WHAT: Where Eureka is — so Gateway can look up service addresses.
WHY: Without this, lb://product-service cannot be resolved.
IF REMOVED: All routes with lb:// fail with: Unable to find instance for product-service.

Route Configuration — Every Line

spring.cloud.gateway.routes[0].id=product-service-route
WHAT: A unique name for this route.
WHY: Appears in logs when this route is matched — makes debugging easy.
IF REMOVED: Startup fails: Route id is required.
spring.cloud.gateway.routes[0].uri=lb://product-service
WHAT: Where to forward the request. lb:// means load-balanced via Eureka.
WHY: lb:// tells Spring Cloud LoadBalancer to ask Eureka for the current address. Automatically load-balances if multiple instances run.
IF REMOVED: Startup fails: URI is required. OR: requests go to a hardcoded address that breaks when the service moves.
spring.cloud.gateway.routes[0].predicates[0]=Path=/api/products/**
WHAT: The URL pattern that triggers this route.
WHY: Without a predicate, a route would match every request. The ** wildcard matches anything after /api/products/.
IF REMOVED: Route matches nothing — requests return 404.

POINT 3

Feign Client — One Service Calls Another

Problem
order-service needs the product price from product-service. Without Feign, you write RestTemplate code: build a URL string, call getForObject, pass the response type. This is verbose and breaks if the URL changes.
Solution
Feign: write one Java interface. Spring generates the entire HTTP call automatically. Uses Eureka to find the service — no hardcoded URL.
How simple it is
You write one interface with one method. That is the entire Feign client. No URL building. No HTTP code. Spring handles everything.

com/order/client/ProductClient.javaJAVA
@FeignClient(name = "product-service")
public interface ProductClient {

    @GetMapping("/api/products/{id}")

POINT 4

Spring Security + JWT — Protect Every API

Problem
Without security, anyone can call DELETE /api/products/1 with no login and delete real data. All APIs are completely open.
Solution
auth-service handles login and issues a JWT token. The API Gateway checks the token on every request. Services behind the Gateway trust all forwarded requests.
What JWT is
A JWT (JSON Web Token) is a signed string: header.payload.signature. The payload holds who the user is and when the token expires. The signature proves it has not been tampered with. Any service can verify it without calling auth-service again.

application.properties — auth-service (Every Line)

server.port=8085
WHAT: Port for auth-service.
WHY: Each service needs a unique port.
IF REMOVED: Conflict with another service on startup.
spring.application.name=auth-service
WHAT: Name registered in Eureka.
WHY: Gateway uses this name to route /auth/** to this service.
IF REMOVED: Gateway cannot find auth-service — login returns 503.
jwt.secret=mySecretKey404E635266556A586E3272357538782F413F4428
WHAT: The secret key used to sign and verify JWT tokens.
WHY: Must be the SAME value in both auth-service and api-gateway. They share it to verify tokens.
IF REMOVED: If different, every token fails validation with 401 — even valid tokens.
jwt.expiration=86400000
WHAT: How long a token is valid in milliseconds.
WHY: 86400000 ms = 24 hours. After this, the token expires and the user must log in again.
IF REMOVED: Token never expires — a security risk.

Public Routes — Routes That Do NOT Need a Token

Important: /auth/login and /auth/register MUST be public. If they require a token, nobody can ever log in — you need to call login to GET a token. This is the most common beginner deadlock.

POST /auth/loginNoMust log in to receive a token

POINT 5

Config Server + Client — One Place for All Configuration

Problem
The JWT secret is copied in auth-service AND api-gateway. The Eureka URL is in every service. When anything changes, you update and redeploy multiple services.
Solution
Config Server holds all properties in one folder. Each service fetches its own config from there at startup. Change once — all services see it.
Simple analogy
Config Server is a central library. Each service checks out its own book (properties file). There is only one copy of each book — no scattered photocopies to keep in sync.

BUILD ORDER

Step-by-Step Build and Run Order

Always start services in this order. Each service depends on the one before it being ready.

1
Start config-server (port 8888)

Why this order: Start Config Server first — all other services fetch their config here at startup.

Console message to look for: Started ConfigServerApplication

Test URL: GET http://localhost:8888/product-service/default

Expected result: Returns JSON with product-service configuration

Common error: config-repo folder not found → check the search-locations path in application.properties
2
Start eureka-server (port 8761)

Why this order: Start Eureka second — all other services register here.

Console message to look for: Started EurekaServerApplication

Test URL: Open http://localhost:8761 in browser

Expected result: Eureka dashboard loads. No services listed yet.

Common error: Port 8761 in use → check no other Eureka instance running
3
Start product-service (port 8081)

Why this order: Start product-service — nothing depends on it first.

Console message to look for: Started ProductServiceApplication

Test URL: GET http://localhost:8081/api/products

Expected result: Returns empty list []. Eureka shows PRODUCT-SERVICE: UP

Common error: Cannot connect to Eureka → wait 30 seconds and retry
4
Start order-service (port 8082)

Why this order: Start order-service — needs product-service registered in Eureka for Feign.

Console message to look for: Started OrderServiceApplication

Test URL: GET http://localhost:8082/api/orders

Expected result: Returns empty list []. Eureka shows ORDER-SERVICE: UP

Common error: ProductClient cannot be created → check @EnableFeignClients on main class
5
Start auth-service (port 8085)

Why this order: Start auth-service — needs Eureka to register and Config Server for JWT secret.

Console message to look for: Started AuthServiceApplication

Test URL: POST http://localhost:8085/auth/register with {email, password}

Expected result: User created. Returns 200 OK.

Common error: JWT secret not found → check config-repo/application.properties has jwt.secret
6
Start api-gateway (port 8080)

Why this order: Start Gateway LAST — needs all services registered in Eureka so it can route to them.

Console message to look for: Started ApigatewayApplication

Test URL: GET http://localhost:8080/api/products (no token)

Expected result: 401 Unauthorized — security is working

Common error: Spring MVC on classpath → remove spring-boot-starter-web from pom.xml

POINT 6 — OPTIONAL

Docker — Package and Deploy Everything (Do This Later)

Remember: Complete Points 1 to 5 and test the full system with all 6 services running before touching Docker. Docker adds a new layer of complexity and should only be added when everything works locally first.

Docker packages each service into a container — a lightweight, isolated unit that runs the same on any machine. Instead of starting 6 services manually, docker-compose up starts all of them with one command.

What to LearnWhat It DoesWhen to Learn It
DockerfileA recipe that builds a container image for one serviceAfter all 6 services work locally
docker-compose.ymlRuns all services together with one commandAfter writing Dockerfiles for all services
localhost to service-name changeIn Docker, localhost means the container itself — you must change all localhost URLs to service namesThe most important Docker gotcha — learn this first
spring-boot-maven-plugin configNeeded to build a Docker image from a Spring Boot JARWhen writing the Dockerfile
Key: This is a separate topic from microservices. Do not mix it with Points 1–5. When you are ready, treat Docker as a new guide on its own.
