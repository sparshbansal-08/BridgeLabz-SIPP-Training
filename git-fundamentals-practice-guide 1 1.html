Module 1: Git Introduction

Foundational concepts: version control, DVCS, Git workflow, installation, and configuration.

CONCEPT What is Version Control?

Version Control System (VCS) is a system that records changes to files over time so you can recall specific versions later. Think of it as a "time machine" for your code.

Three types of VCS:

  • Local VCS: All versions stored on your computer only (e.g., RCS). Risky — if your computer crashes, everything is lost.
  • Centralized VCS (CVCS): One central server holds all versions. Multiple users connect to it (e.g., SVN, CVS, Perforce). Single point of failure.
  • Distributed VCS (DVCS): Every user has the FULL repository on their machine, including complete history (e.g., Git, Mercurial). Fast, reliable, works offline.

CONCEPT What is a Distributed Version Control System (DVCS)?

In a DVCS, every developer has a complete copy of the repository — including the full history — on their local machine. You can commit, view history, and create branches without any network connection.

Why this matters: If the central server dies, ANY developer's copy can be used to restore everything. There's no single point of failure.

CONCEPT What is Git?

Git is a free, open-source distributed version control system created by Linus Torvalds in 2005 for Linux kernel development. It's now the world's most widely used VCS.

Key features:

  • Distributed — every clone is a full backup
  • Fast — most operations are local
  • Branching is cheap and fast
  • Data integrity via SHA-1 hashes
  • Snapshots, not differences (Git stores full snapshots of files)

CONCEPT Git Workflow — The Three States

Every file in Git lives in one of three states. Understanding this is critical:

  • Modified: You changed a file, but haven't told Git yet.
  • Staged: You marked a modified file (with git add) to go into the next commit.
  • Committed: Data is safely stored in your local .git repository.

SETUP Installing Git on Windows

  1. Go to https://git-scm.com/download/win
  2. Download the installer (Git for Windows)
  3. Run the .exe — accept defaults for most options (Git Bash is recommended terminal)
  4. Verify installation:

SETUP Configuring Git (First-Time Setup)

Set your identity — this is attached to every commit:

Git Configuration
# Set your name and email (used in every commit)
$ git config --global user.name "John Doe"
$ git config --global user.email "john@example.com"

# Set default editor (optional)
$ git config --global core.editor "code --wait"

# Set default branch name
$ git config --global init.defaultBranch main

# View all settings
$ git config --list
Three config levels: --system (all users), --global (current user), --local (current repo, default). Local overrides global, global overrides system.

📝 Practice Questions — Module 1

Q1What is the main difference between a Centralized VCS and a Distributed VCS?
Answer: In a Centralized VCS (like SVN), there is ONE central server that stores all versioned files and history. Developers check out files from this server. If the server goes down, no one can collaborate or save versioned changes.

In a Distributed VCS (like Git), every developer has a FULL copy of the repository — including complete history — on their local machine. Work continues offline, and any clone can serve as a backup if the central server fails.
Q2Who created Git, when, and why?
Answer: Git was created by Linus Torvalds in 2005. The Linux kernel community had been using BitKeeper, but lost access to it. Linus designed Git to be fast, distributed, support non-linear development (thousands of branches), and handle large projects efficiently.
Q3Explain the three states of a file in Git.
Answer:
  1. Modified: File has been changed in your working directory but not yet staged.
  2. Staged: Modified file marked (via git add) to be included in the next commit.
  3. Committed: Changes are safely stored in the local .git database.
These three states correspond to three areas: Working Directory → Staging Area (Index) → Git Repository.
Q4What command do you use to set your name and email globally in Git?
Answer: 
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
The --global flag means these settings apply to ALL Git repositories for the current user.
Q5What are the three configuration levels in Git, and what's their precedence?
Answer: Git has three config levels:
  • --system — applies to all users on the machine (file: /etc/gitconfig)
  • --global — applies to current user, all repos (file: ~/.gitconfig)
  • --local — applies only to the current repo (file: .git/config) — this is the default
Precedence (highest wins): local > global > system.
Q6How do you check the installed Git version?
Answer: git --version

Output example: git version 2.45.2. This is also a quick way to confirm Git is installed and accessible from your terminal.
Q7Why is Git called "distributed"?
Answer: Because every clone is a complete repository with full history — not just a snapshot of files. Every developer has the entire project history on their machine, can commit, branch, and merge offline, and can act as a "server" for others. There's no single authoritative central source by design (though teams often agree on one, like GitHub).
Q8How does Git store data — as differences (deltas) or as snapshots?
Answer: Git stores data as snapshots, not deltas. When you commit, Git takes a picture of what all your files look like at that moment and stores a reference to that snapshot. If a file hasn't changed, Git just stores a link to the previous identical file. This is a key difference from older VCSs (like SVN) which stored differences.

Internally, Git uses content-addressable storage with SHA-1 hashes to identify each snapshot.

Module 2: Working Locally with Git

Creating repos, staging, committing, viewing history, undoing changes, and ignoring files.

CMD Creating a Local Repository

Initialize a Repo
# Create a new project folder and init Git
$ mkdir my-project && cd my-project
$ git init
Initialized empty Git repository in /home/user/my-project/.git/

# Check status (no commits yet)
$ git status
On branch main
No commits yet
nothing to commit (create/copy files and use "git add" to track)

git init creates a hidden .git folder which is the entire database for the repo.

CMD Adding Files & Committing

Add & Commit
$ echo "# My Project" > README.md
$ git add README.md # stage one file
$ git add . # stage everything in current dir
$ git add -A # stage all changes (incl. deletions)

$ git commit -m "Initial commit"
[main (root-commit) e8a4b2c] Initial commit
1 file changed, 1 insertion(+)
create mode 100644 README.md

# Skip the staging area (only for tracked files)
$ git commit -am "Quick fix"

CMD Viewing History & Diffs

History & Diffs
# Full commit log
$ git log

# Compact one-line per commit
$ git log --oneline
e8a4b2c Initial commit
a1b9d3f Add login feature

# Pretty graph
$ git log --oneline --graph --all --decorate

# Diffs
$ git diff # working dir vs staged
$ git diff --staged # staged vs last commit
$ git diff HEAD # working dir vs last commit
$ git diff abc123 def456 # between two commits

CMD Staging Changes as Multiple Commits

Often you've made several changes that should logically be separate commits. Use git add -p for interactive staging:

Interactive Staging
$ git add -p
@@ -1,3 +1,5 @@
existing line
+new line A (bug fix)
+new line B (new feature)
Stage this hunk [y,n,q,a,d,s,e,?]? s # split hunk

# Then stage one piece, commit it, stage the other, commit it
$ git commit -m "Fix login bug"
$ git add -p
$ git commit -m "Add new feature"
Why? Atomic commits — each commit does one thing — make history readable and easier to revert.

CMD Deleting & Renaming Files

Delete & Rename
# Delete a tracked file
$ git rm old-file.txt
$ git commit -m "Remove old-file.txt"

# Remove from git but keep on disk
$ git rm --cached secrets.env

# Rename a file
$ git mv old-name.txt new-name.txt
$ git commit -m "Rename file"

# git mv is shorthand for: mv + git rm + git add

UNDO Undoing Changes to the Working Copy

Undo Working Copy Changes
# Discard changes to a single file (modern way)
$ git restore file.txt

# Old way (still works)
$ git checkout -- file.txt

# Discard ALL working copy changes
$ git restore .

# Unstage a file (move from staged → modified)
$ git restore --staged file.txt
⚠️ Warning: git restore file.txt permanently discards uncommitted changes. There's no undo.

UNDO Undoing/Redoing Repository Changes

Reset, Revert, Amend
# Amend the last commit (change message or add files)
$ git commit --amend -m "Better message"

# Undo last commit, KEEP changes staged
$ git reset --soft HEAD~1

# Undo last commit, KEEP changes in working dir (default)
$ git reset --mixed HEAD~1

# Undo last commit, DISCARD all changes ⚠️
$ git reset --hard HEAD~1

# Create a NEW commit that undoes a previous one (safe for shared history)
$ git revert abc123
Reset vs Revert: reset rewrites history (dangerous on shared branches). revert creates a new "undo" commit (safe for shared branches).

CLEAN Cleaning the Working Copy

Remove Untracked Files
# Preview what would be removed (DRY RUN — always do this first!)
$ git clean -n
Would remove temp.log
Would remove build/

# Remove untracked files
$ git clean -f

# Remove untracked files AND directories
$ git clean -fd

# Also remove ignored files
$ git clean -fdx

CONFIG Ignoring Files with .gitignore

Create a file named .gitignore at your repo root with patterns to ignore:

.gitignore example
# Comments start with #

# Ignore specific files
secrets.env
config.local.json

# Ignore by extension
*.log
*.tmp

# Ignore folders
node_modules/
build/
.idea/

# Ignore everything in /logs but keep .gitkeep
logs/*
!logs/.gitkeep
⚠️ Important: .gitignore only ignores UNTRACKED files. If a file is already tracked, you must git rm --cached file first.

📝 Practice Questions — Module 2

Q1What command initializes a new Git repository in the current folder?
Answer: git init

This creates a hidden .git/ directory containing all the metadata and object database for the new repository. It does NOT create any commit yet — your repo starts empty.
Q2What's the difference between git add file.txt, git add ., and git add -A?
Answer:
  • git add file.txt — stages only that specific file
  • git add . — stages all changes in the current directory and subdirectories (including new files, modifications, and deletions in modern Git)
  • git add -A — stages ALL changes in the entire repository (regardless of current directory)
For most cases, git add . from the repo root is equivalent to git add -A.
Q3How do you commit changes with a message in one line?
Answer: git commit -m "Your message here"

The -m flag lets you add the message inline instead of opening an editor. For multi-line messages, repeat -m: git commit -m "Title" -m "Description on second line".
Q4What does git commit -am "msg" do, and what's its limitation?
Answer: -am combines -a (auto-stage modified tracked files) and -m (message). It saves typing git add separately.

Limitation: It only stages MODIFIED files that are already TRACKED. New untracked files are NOT included — you must explicitly git add those first.
Q5How do you see a compact, one-line-per-commit history?
Answer: git log --oneline

For a visual graph showing branches: git log --oneline --graph --all --decorate. Many developers create an alias for this: git config --global alias.lg "log --oneline --graph --all --decorate".
Q6What's the difference between git diff, git diff --staged, and git diff HEAD?
Answer:
  • git diff — shows changes in working directory that are NOT yet staged
  • git diff --staged (or --cached) — shows changes that ARE staged but not yet committed
  • git diff HEAD — shows ALL changes (both staged and unstaged) compared to the last commit
Q7How do you delete a tracked file from Git?
Answer: git rm filename.txt then git commit -m "Remove filename.txt".

This removes the file from both the working directory and Git tracking. To remove from Git tracking but KEEP the file on disk (e.g., for accidentally committed secrets), use git rm --cached filename.txt.
Q8How do you rename a file in Git?
Answer: git mv old-name.txt new-name.txt

This is shorthand for three operations: rename the file in the OS, git rm the old name, and git add the new name. Git is smart enough to detect renames automatically even if you use the OS mv command directly, as long as content similarity is high.
Q9You modified a file but want to discard changes and revert to the last committed version. How?
Answer: git restore file.txt (modern) or git checkout -- file.txt (older syntax).

⚠️ This permanently destroys your uncommitted changes. There is no undo. To discard ALL working directory changes: git restore ..
Q10You staged a file by mistake. How do you unstage it without losing changes?
Answer: git restore --staged file.txt (modern) or git reset HEAD file.txt (older syntax).

Both move the file from "staged" back to "modified" — the changes remain in your working directory.
Q11Explain the difference between git reset --soft, --mixed, and --hard.
Answer: All three move HEAD backward, but they differ in what they do with your changes:
  • --soft — moves HEAD only. Changes stay STAGED. Use when you want to redo the commit.
  • --mixed (default) — moves HEAD and unstages. Changes stay in working directory. Use to redo staging.
  • --hard — moves HEAD, unstages, AND discards working directory changes. ⚠️ Destructive.
Q12When should you use git revert instead of git reset?
Answer: Use git revert when the commit you want to undo has been pushed to a shared remote. revert creates a NEW commit that undoes the changes — preserving history.

Use git reset only on LOCAL commits that haven't been pushed. reset rewrites history, which causes problems for collaborators if they've already pulled those commits.

Golden rule: Never rewrite shared history.
Q13You forgot to include a file in your last commit. How do you add it without creating a new commit?
Answer: 
git add forgotten-file.txt
git commit --amend --no-edit
--amend modifies the last commit. --no-edit keeps the original commit message. ⚠️ Don't amend commits that have been pushed to shared branches.
Q14How do you remove untracked files from your working directory?
Answer:
  • git clean -n — DRY RUN (preview, always run first!)
  • git clean -f — actually remove untracked files
  • git clean -fd — remove untracked files AND directories
  • git clean -fdx — also remove files normally ignored by .gitignore
Q15You have a tracked file config.json that contains secrets. You added it to .gitignore but it's still being tracked. Why, and how do you fix it?
Answer: .gitignore only affects UNTRACKED files. Once a file is tracked, Git keeps tracking it regardless of .gitignore.

Fix: 
git rm --cached config.json
git commit -m "Remove config.json from tracking"
This stops tracking but keeps the file on your disk. The file then matches .gitignore and won't be re-added.

⚠️ Note: secrets are still in history! For a real leak, you also need to rewrite history with tools like git filter-repo and rotate the secret.
Q16Write a .gitignore that ignores all .log files, the node_modules/ folder, and a file called .env — but DOES track example.env.
Answer: 
*.log
node_modules/
.env
!example.env
The ! prefix negates a previous pattern. example.env won't match .env exactly anyway, but ! is essential when you want to whitelist files inside an ignored folder.

Module 3: Working Remotely with Git

Cloning, fetching, pulling, pushing, protocols, and tagging.

CMD Cloning a Remote Repository

git clone
# HTTPS clone (most common)
$ git clone https://github.com/user/repo.git

# SSH clone (after key setup)
$ git clone git@github.com:user/repo.git

# Clone into a specific folder name
$ git clone https://github.com/user/repo.git my-folder

# Clone only the latest snapshot (saves bandwidth)
$ git clone --depth 1 https://github.com/user/repo.git

git clone downloads the entire repo + history and automatically sets up the remote named origin.

INSPECT Repository Statistics & Inspection

Inspecting a Repo
# List all remotes
$ git remote -v
origin https://github.com/user/repo.git (fetch)
origin https://github.com/user/repo.git (push)

# Detailed remote info
$ git remote show origin

# Count commits
$ git rev-list --count HEAD

# Contributors and commit counts
$ git shortlog -sn

# Last commit details
$ git show HEAD

# Show specific commit
$ git show abc123

PROTO Git Protocols

Git supports four protocols for connecting to remotes:

  • HTTPS (e.g., https://github.com/user/repo.git) — easiest setup, works through firewalls, requires username/token for push
  • SSH (e.g., git@github.com:user/repo.git) — secure, requires SSH key setup, no password prompts after setup
  • Git protocol (e.g., git://...) — fast, read-only, no authentication, mostly deprecated
  • Local (e.g., /path/to/repo) — for repos on the same machine
Recommendation: Use SSH for personal projects (no repeated logins). Use HTTPS for occasional contributions or restricted networks.

VIEW Viewing Branches and Tags

Branches & Tags
# List local branches (current marked with *)
$ git branch
* main
feature-login

# List remote branches
$ git branch -r

# List all (local + remote)
$ git branch -a

# List all tags
$ git tag

# Show details of a tag
$ git show v1.0.0

SYNC Fetch vs Pull — The Critical Difference

Fetch & Pull
# Download remote changes — does NOT merge into your branch
$ git fetch origin
From github.com:user/repo
abc123..def456 main -> origin/main

# Now you can inspect what changed
$ git log main..origin/main

# Pull = fetch + merge (in one step)
$ git pull origin main

# Pull with rebase instead of merge (cleaner history)
$ git pull --rebase origin main
Best practice: Use git fetch first to inspect changes safely, then merge or rebase deliberately. pull is convenient but can cause unexpected merges.

SYNC Pushing to a Remote

git push
# Push current branch to its tracked remote branch
$ git push

# Push and set upstream tracking (first push of a new branch)
$ git push -u origin feature-login

# Force push (DANGEROUS - rewrites remote history)
$ git push --force

# Safer force push - fails if someone else pushed
$ git push --force-with-lease

# Delete a remote branch
$ git push origin --delete old-branch
⚠️ NEVER use --force on shared branches like main or develop. It will overwrite work that other people may have already pushed. Always prefer --force-with-lease.

TAG Creating & Verifying Tags

Tags mark specific points in history — usually releases (v1.0, v2.5.3).

Tagging
# Lightweight tag (just a pointer)
$ git tag v1.0.0

# Annotated tag (recommended - has author, date, message, can be GPG-signed)
$ git tag -a v1.0.0 -m "Release version 1.0.0"

# Tag a specific past commit
$ git tag -a v0.9.0 abc123 -m "Beta release"

# Verify a tag
$ git show v1.0.0

# Delete a tag locally
$ git tag -d v0.9.0

TAG Pushing Tags to a Remote

By default, git push does NOT push tags. You must push them explicitly:

Pushing Tags
# Push a single tag
$ git push origin v1.0.0

# Push ALL local tags
$ git push origin --tags

# Delete a remote tag
$ git push origin --delete v0.9.0

📝 Practice Questions — Module 3

Q1What's the difference between git clone and git init?
Answer:
  • git init — creates a new EMPTY local repository in the current folder
  • git clone <url> — downloads an EXISTING remote repo (with full history) to your machine and automatically sets up the origin remote
Cloning is essentially: init + remote add origin <url> + fetch + checkout the default branch.
Q2How do you list all remotes configured for a repository?
Answer: git remote -v (the -v means verbose — shows URLs).

Output: 
origin  https://github.com/user/repo.git (fetch)
origin  https://github.com/user/repo.git (push)
Q3What is the default name of the remote when you clone a repository?
Answer: origin. This is just a convention — you can rename it with git remote rename origin upstream or use a different name when adding manually: git remote add myremote <url>.
Q4List the four Git protocols and when you'd use each.
Answer:
  • HTTPS (https://...) — easiest, works through firewalls. Use for occasional contributions or where SSH is blocked.
  • SSH (git@host:...) — secure, no repeated logins after key setup. Use for daily personal work.
  • Git (git://...) — fast read-only, no auth. Mostly legacy, rarely used today.
  • Local (/path/to/repo or file://...) — for repos on the same machine or shared filesystem.
Q5What is the critical difference between git fetch and git pull?
Answer:
  • git fetch — downloads remote changes into your local repo's tracking branches (e.g., origin/main) but does NOT touch your working branch.
  • git pull — does fetch AND immediately merges the remote changes into your current branch. Equivalent to git fetch && git merge.
Why it matters: fetch is safe — you can inspect changes before integrating. pull is convenient but can cause unwanted merge commits if not careful.
Q6What's the difference between git pull and git pull --rebase?
Answer:
  • git pull = fetch + merge — creates a merge commit if local and remote have diverged. History becomes branched.
  • git pull --rebase = fetch + rebase — replays your local commits ON TOP of the fetched remote commits. History stays linear.
Many teams configure rebase as default with: git config --global pull.rebase true.
Q7You created a new local branch feature-x. What command pushes it to the remote AND sets up tracking so future git push/pull work without specifying the branch?
Answer: git push -u origin feature-x

The -u flag (or --set-upstream) tells Git to remember the link between your local feature-x and the remote origin/feature-x. After this, you can simply run git push or git pull without arguments.
Q8When and why is git push --force dangerous? What's the safer alternative?
Answer: --force overwrites the remote branch's history with your local version. If someone else pushed commits since you last fetched, their work will be DESTROYED — not just unmerged, but gone from the remote.

Safer alternative: git push --force-with-lease. This force-pushes ONLY if the remote is in the state you last saw it. If anyone else pushed in the meantime, the push fails — protecting their work.

Even safer: never force-push to shared branches like main.
Q9How do you delete a branch on the remote?
Answer: git push origin --delete branch-name

Older syntax (still works): git push origin :branch-name (note the colon and no space). This deletes only the remote branch — the local branch stays. To delete the local branch too: git branch -d branch-name.
Q10What's the difference between a lightweight tag and an annotated tag?
Answer:
  • Lightweight tag: Just a pointer to a commit. Created with git tag v1.0. No metadata.
  • Annotated tag: A full Git object with author, date, message, and optional GPG signature. Created with git tag -a v1.0 -m "message".
Recommendation: Use annotated tags for releases — they carry meaningful metadata and can be cryptographically verified.
Q11You created tag v1.0.0 locally and pushed your code with git push. The tag isn't showing up on GitHub. Why?
Answer: By default, git push does NOT push tags. You must push them explicitly: 
git push origin v1.0.0       # push specific tag
git push origin --tags       # push all local tags
Q12How would you tag a past commit (not the latest one) as v0.5.0?
Answer:
  1. Find the commit hash with git log --oneline
  2. Tag it: git tag -a v0.5.0 abc123 -m "Beta release" (replace abc123 with the actual hash)
  3. Push it: git push origin v0.5.0
Q13How can you see how many commits each contributor has made?
Answer: git shortlog -sn

-s = summary (count only), -n = sort numerically. Output: 
  142  Alice
   89  Bob
   23  Charlie

Module 4: Branching, Merging & Rebasing

The most powerful (and most asked-about) Git topics: branches, merges, rebases, and stashes.

CMD Creating Local Branches

Create Branches
# Create branch (without switching to it)
$ git branch feature-login

# Create AND switch (modern syntax)
$ git switch -c feature-login

# Create AND switch (older syntax, still common)
$ git checkout -b feature-login

# Switch between branches
$ git switch main
$ git checkout main # older syntax

CONCEPT Branches vs Tags

Branch Tag
Movable pointer to a commit Fixed pointer to a commit
Advances with each new commit Never moves — stays on that commit
For ongoing development For marking releases / milestones
Examples: main, feature-x Examples: v1.0.0, v2.5.3

CMD Renaming and Deleting Branches

Rename & Delete
# Rename current branch
$ git branch -m new-name

# Rename a different branch
$ git branch -m old-name new-name

# Delete a branch (safe — fails if unmerged)
$ git branch -d feature-x

# Force delete (even if unmerged) ⚠️
$ git branch -D feature-x

# You can't delete the branch you're on — switch first!

RECOVER Recovering Deleted Commits — git reflog

Git keeps a log of EVERY change to HEAD for ~30 days. This means even "deleted" commits can usually be recovered.

Reflog Recovery
# Show every move HEAD has made
$ git reflog
e8a4b2c HEAD@{0}: reset: moving to HEAD~3
a1b9d3f HEAD@{1}: commit: Add feature X (the "lost" one!)
c5d2e8a HEAD@{2}: commit: Initial work

# Recover by resetting to the lost commit
$ git reset --hard a1b9d3f

# Or create a branch from the lost commit
$ git branch recovered-work a1b9d3f
Lifesaver: Whenever you do something destructive and panic — git reflog is your friend. Almost nothing is truly lost in Git for at least 30 days.

SAVE Stashing Changes

Stash temporarily saves uncommitted work so you can switch branches cleanly. Like a clipboard for code.

Stash
# Save current changes & revert working dir to last commit
$ git stash
Saved working directory and index state WIP on main

# Stash with a descriptive message
$ git stash push -m "Half-done login form"

# Include untracked files too
$ git stash push -u -m "WIP with new files"

# List all stashes
$ git stash list
stash@{0}: On main: Half-done login form
stash@{1}: On feature-x: experimental refactor

# Apply most recent stash and remove it from stash list
$ git stash pop

# Apply but keep in stash list
$ git stash apply stash@{1}

# Delete a stash
$ git stash drop stash@{0}

# Delete ALL stashes
$ git stash clear

MERGE Merging Branches

Merging combines work from one branch INTO another. Two main types:

Merging
# Switch to target branch (the one receiving changes)
$ git switch main

# Merge feature-x INTO main
$ git merge feature-x

# Force a merge commit (no fast-forward)
$ git merge --no-ff feature-x

# Abort if conflicts get messy
$ git merge --abort

Two merge types:

  • Fast-forward merge: If main hasn't moved since branching, Git just moves main's pointer forward. No merge commit.
  • 3-way merge: If both branches have new commits, Git creates a new "merge commit" combining both histories.

CONFLICT Resolving Merge Conflicts

When Git can't auto-merge, it marks conflicts in the affected files:

Conflict Resolution
$ git merge feature-x
CONFLICT (content): Merge conflict in app.js
Automatic merge failed; fix conflicts and commit.

# Open the conflicted file. You'll see:
<<<<<<< HEAD
code from current branch (main)
=======
code from incoming branch (feature-x)
>>>>>>> feature-x

# 1. Edit the file - keep what you want, remove markers
# 2. Stage the resolved file
$ git add app.js
# 3. Complete the merge
$ git commit

REBASE Rebasing Changes

Rebase replays your branch's commits ON TOP of another branch — creating a linear, cleaner history.

Rebase
$ git switch feature-x
$ git rebase main

# If conflicts arise:
# 1. Fix conflicts manually
$ git add <file>
$ git rebase --continue

# Bail out if needed
$ git rebase --abort

# Interactive rebase — squash, reorder, edit commits
$ git rebase -i HEAD~3
⚠️ The Golden Rule of Rebase: Never rebase commits that have been pushed to a public/shared branch. It rewrites history and breaks others' clones.

COMPARE Merge vs Rebase — Which to Use?

Aspect Merge Rebase
History Branched, with merge commits Linear, clean
Preserves history? Yes — exactly as it happened No — rewrites commits
Safe for shared branches? ✅ Yes ❌ No

📝 Practice Questions — Module 4

Q1What's the difference between git branch feature-x and git checkout -b feature-x?
Answer:
  • git branch feature-x — creates the branch but stays on the current branch
  • git checkout -b feature-x (or git switch -c feature-x) — creates the branch AND switches to it
Modern Git recommends git switch -c over checkout -b for clarity.
Q2What's the fundamental difference between a branch and a tag?
Answer:
  • Branch: A movable pointer that advances every time you commit on it. Used for active development.
  • Tag: A fixed pointer that NEVER moves. Used to mark specific points in history, typically releases.
Internally, both are just refs pointing to a commit, but they're treated differently. Tags don't move with new commits.
Q3How do you rename your current branch from feature-old to feature-new?
Answer:
  1. Locally: git branch -m feature-new
  2. If already pushed:
    • git push origin -u feature-new (push the renamed branch)
    • git push origin --delete feature-old (delete the old remote branch)
Q4What's the difference between git branch -d and git branch -D?
Answer:
  • -d (lowercase) — SAFE delete. Refuses if the branch has unmerged commits, protecting you from data loss.
  • -D (uppercase) — FORCE delete. Removes the branch even if commits would be lost.
Use -d by default. Only use -D when you're certain you want to discard the branch's unique commits.
Q5You accidentally ran git reset --hard HEAD~5 and lost 5 commits! How do you recover?
Answer: Use git reflog — Git keeps a log of every HEAD movement for ~30 days. 
git reflog
# Find the commit hash before the reset, e.g., a1b9d3f
git reset --hard a1b9d3f
Or create a branch from it: git branch recovered a1b9d3f. Almost nothing is truly lost in Git!
Q6You're working on changes but suddenly need to switch branches to fix a bug. You don't want to commit your half-done work. What do you do?
Answer: Use git stash: 
git stash push -m "WIP: half-done feature"
git switch hotfix-branch
# ... fix the bug, commit, push ...
git switch original-branch
git stash pop
stash saves your changes safely, leaves the working dir clean, and lets you restore them later.
Q7What's the difference between git stash pop and git stash apply?
Answer:
  • git stash pop — applies the most recent stash AND removes it from the stash list
  • git stash apply — applies the stash but KEEPS it in the stash list (useful if you want to apply the same stash to multiple branches)
Q8Explain a fast-forward merge vs a 3-way merge.
Answer:
  • Fast-forward merge: If main hasn't received any new commits since you branched off, Git simply moves main's pointer forward to your branch's tip. No merge commit is created.
  • 3-way merge: If both branches have advanced since they diverged, Git uses three commits — the common ancestor, the tip of branch A, the tip of branch B — to create a new merge commit that combines them.
Force a merge commit even when fast-forward is possible: git merge --no-ff feature-x (preserves the fact that a feature branch existed in history).
Q9You ran git merge feature-x and got a conflict. Walk through how to resolve it.
Answer:
  1. Run git status to see which files have conflicts
  2. Open each conflicted file. Look for markers: 
    <<<<<<< HEAD
your code (current branch)
=======
their code (incoming branch)
>>>>>>> feature-x
  3. Edit the file — choose what to keep, delete the markers
  4. Stage the resolved file: git add filename
  5. Complete the merge: git commit (Git provides a default merge message)
To bail out entirely: git merge --abort.
Q10What's the conceptual difference between merge and rebase?
Answer:
  • Merge: Combines two branches by creating a new merge commit. History stays branched and shows exactly what happened.
  • Rebase: Takes your branch's commits and replays them ON TOP of another branch. This creates a linear history but rewrites commit hashes — the original commits are replaced with new ones.
Visually: merge preserves the branching shape; rebase pretends your work was done after the latest changes on the target branch.
Q11When should you NEVER use rebase?
Answer: Never rebase commits that have already been pushed to a shared/public branch.

Rebase rewrites commit history (changes hashes). If others have already pulled those commits and based their work on them, rebasing breaks their clones — they'll have duplicate or conflicting history.

Golden rule: Rebase is for cleaning up your LOCAL branch before pushing. Once pushed and shared, use merge.
Q12You started a rebase and got into a conflict mess. How do you abort?
Answer: git rebase --abort

This returns your branch to its pre-rebase state. To CONTINUE after fixing conflicts: git add <files> then git rebase --continue. To skip the current commit: git rebase --skip.
Q13How do you create a remote branch?
Answer: You can't create a remote branch directly. You create it locally, then push it: 
git switch -c feature-x
git push -u origin feature-x
The -u sets up tracking so future git push/pull work automatically.
Q14After deleting branches on the remote (e.g., via GitHub UI), git branch -r still shows them. How do you clean up?
Answer: git fetch --prune (or git fetch -p) — this removes references to remote branches that no longer exist.

To do it automatically on every fetch: git config --global fetch.prune true.
Q15What does git rebase -i HEAD~3 do?
Answer: Opens an INTERACTIVE rebase for the last 3 commits. You'll see a list like: 
pick a1b2c3 First commit
pick d4e5f6 Second commit
pick g7h8i9 Third commit
You can change pick to:
  • reword — change the message
  • edit — pause to amend the commit
  • squash — combine with previous commit
  • fixup — like squash but discards this commit's message
  • drop — remove the commit entirely
⚠️ Don't do this on commits already pushed to shared branches.
