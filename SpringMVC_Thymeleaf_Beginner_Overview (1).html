Section 1

What is Spring MVC?

When someone opens your web application in a browser, they type a URL and hit Enter. Something on the server has to receive that request, figure out what to do, get some data, and send back a web page. Spring MVC is the part of Spring that handles all of this.

Real life analogy

Think of a restaurant. The customer (browser) places an order (HTTP request). The waiter (Spring MVC) takes the order to the kitchen (your Java code), collects the food (data), and brings it back to the customer as a finished meal (HTML page).

The three letters — MVC

MVC stands for Model, View, Controller. It is a design pattern — a proven way to keep three separate concerns from getting mixed together.

LetterNameJobIn Spring MVC
MModelHolds the dataA Java object or list that carries data to the template
VViewDisplays the dataA Thymeleaf HTML template that the user sees
CControllerConnects the twoA Java class that receives requests and decides what to show

Why use Spring MVC?

Without a framework
  • Write raw Servlet code for every URL
  • Parse request parameters manually
  • Build HTML strings in Java (ugly and error-prone)
  • No structure — code becomes one giant mess
  • Re-invent the same patterns every project
With Spring MVC
  • Map a URL to a method with one annotation
  • Parameters injected automatically
  • Templates render HTML cleanly
  • Clear structure — everyone knows where to look
  • Validation, error handling, security built-in

Spring MVC is part of the Spring Framework — the most widely used Java framework in enterprise software. Learning it opens the door to professional Java web development.

Section 2

Why Use Thymeleaf?

Thymeleaf is the template engine Spring MVC uses to build HTML pages. You write normal HTML files, add special th: attributes, and at runtime Thymeleaf fills in the real data from your Java code.

What makes Thymeleaf special

It is valid HTML — always

A Thymeleaf file is a normal HTML file. You can open it in a browser right now — without running Spring — and it looks fine. The th: attributes are simply ignored by the browser. This means designers can work on templates without running the whole application.

Compare: old-style JSP files have <% ... %> Java code mixed into HTML. If you open a JSP file directly in a browser, you see broken garbage. Thymeleaf files always look clean.

FeaturePlain HTMLJSP (old way)Thymeleaf

Designer-friendlyYesNoYes

Section 3

Advantages of Spring MVC with Thymeleaf

1. Clean separation of work

The Controller handles logic, the Model holds data, the Thymeleaf template handles display. A Java developer can change business logic without touching HTML. A designer can change the look without touching Java code. No more one-giant-file chaos.

2. Annotations replace configuration files

In older Java web frameworks you needed large XML files describing every URL mapping. In Spring MVC you write @GetMapping("/students") directly on the method. The URL and the method are in one place, easy to read and change.

3. Validation is built in

Add @NotBlank or @Email on a model field, add @Valid in the Controller, and Spring checks the data automatically. If it fails, Thymeleaf shows error messages next to each bad field. No manual if-else chains needed.

4. Automatic type conversion

HTTP sends everything as plain text strings. If your form has an age field and your Java class has int age, Spring converts "22" to 22 automatically. Same for dates, booleans, and custom types.

5. Thymeleaf files are always valid HTML

Open a Thymeleaf template in a browser without running Spring — it looks like a normal HTML page. This makes it easy for the whole team to view and work on designs. JSP files cannot do this.

6. Works with the whole Spring ecosystem

Spring MVC sits inside Spring Boot, which means you automatically get Spring Security (authentication), Spring Data JPA (database), Spring Validation, DevTools (auto-restart), and more — all working together with zero extra wiring.

Section 4

Important Annotations — Why, What, and How

An annotation in Java is a label you put on a class, method, or parameter (it starts with @). Spring reads these labels and does the right thing automatically. You write less code, Spring does more work. Below, every annotation is explained with a tiny, focused program.

@Controller Marks a class as a web request handler
WHY we need it — Without @Controller, Spring does not know this class is supposed to handle web requests. It is just a plain Java class that nobody calls.

What it does: When you add @Controller to a class, Spring registers it and scans all methods inside it for URL mapping annotations. Spring creates one instance of the class and keeps it ready to handle requests.

Return value rule: A @Controller method returns a String — the name of the Thymeleaf template to display. Return "home" and Spring renders templates/home.html. Return "redirect:/students" and the browser navigates to that URL.

HomeController.javajava
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;

@Controller   // ← Spring: "this class handles web requests"
public class HomeController {

    @GetMapping("/")
    public String home(Model model) {
        model.addAttribute("message", "Hello from Spring MVC!");
        return "home";  // renders templates/home.html
    }
}
templates/home.htmlhtml
<html xmlns:th="http://www.thymeleaf.org">
<body>
    <h1 th:text="${message}">Loading...</h1>
</body></html>
Page shows: Hello from Spring MVC!
@GetMapping & @PostMapping Connect a URL and HTTP method to a Java method
WHY we need them — Without these, Spring does not know which method to call when a request arrives. The URL alone is not enough; the same URL with GET should load a form, while the same URL with POST should save the data.

HTTP GET is used for loading pages and reading data — no data is being changed. HTTP POST is used for submitting forms and saving data — something is being created or updated.

Simple rule: GET = "give me something to look at". POST = "save something I just submitted".

RegistrationController.javajava
@Controller
public class RegistrationController {

    // Browser requests GET /register → show the empty form
    @GetMapping("/register")
    public String showForm() {
        return "register";    // renders templates/register.html
    }

    // User fills form and clicks Submit → browser sends POST /register
    @PostMapping("/register")
    public String handleForm() {
        // save the data ...
        return "redirect:/register";  // go back to the form
    }
}
i
Same URL, different jobs

Both methods here map to /register. Spring picks the right one based on the HTTP method. GET calls showForm(). POST calls handleForm(). They can share a URL because they do different things.

@RequestParam Reads one value from the URL query string or form body
WHY we need it — When a form field or URL parameter arrives at the server, it is just a plain string in the HTTP request. @RequestParam reads one named value and injects it as a method parameter — with automatic type conversion.

Where values come from: A URL like /search?name=Ravi&page=2 has two parameters: name and page. @RequestParam reads them by name.

SearchController.javajava
@Controller
public class SearchController {

    // URL: GET /search?name=Ravi&page=2
    @GetMapping("/search")
    public String search(
            @RequestParam String name,           // reads ?name=Ravi
            @RequestParam(defaultValue = "1") int page,   // reads ?page=2, default 1
            Model model) {

        model.addAttribute("searchName", name);
        model.addAttribute("pageNumber",  page);
        return "search-results";
    }
}
// Visit: /search?name=Ravi     → name="Ravi", page=1 (default)
// Visit: /search?name=Ravi&page=3 → name="Ravi", page=3
!
Use defaultValue for optional parameters

If a parameter is missing and has no defaultValue, Spring throws an error. Add defaultValue="something" or required=false to make it optional.

@PathVariable Reads a value embedded inside the URL path itself
WHY we need it — Sometimes the value you need IS the URL. To view student number 5, the clean URL is /students/5 — not /students?id=5. @PathVariable reads the 5 directly from the path.

How to set it up: Put curly braces in the URL pattern — {id} — and match the name in @PathVariable int id. Spring extracts whatever is in that position and gives it to your method. Type conversion happens automatically.

StudentController.javajava
@Controller
public class StudentController {

    // URL: GET /students/5 → id = 5
    // URL: GET /students/12 → id = 12
    @GetMapping("/students/{id}")
    public String viewStudent(
            @PathVariable int id,   // reads the {id} part of the URL
            Model model) {

        // normally: Student s = studentService.findById(id);
        model.addAttribute("studentId", id);
        return "student-profile";
    }

    // Multiple path variables in one URL
    // URL: GET /courses/java/students/3
    @GetMapping("/courses/{course}/students/{studentId}")
    public String viewCourseStudent(
            @PathVariable String course,
            @PathVariable int studentId,
            Model model) {

        model.addAttribute("course",    course);
        model.addAttribute("studentId", studentId);
        return "course-student";
    }
}
i
@PathVariable vs @RequestParam — when to use which

Use @PathVariable when the value identifies a specific resource: /students/5, /products/42.
Use @RequestParam when the value filters or sorts: /students?course=Java, /products?sort=price.

@ModelAttribute Automatically fills a Java object from all form fields at once
WHY we need it — A registration form might have 10 fields. Without @ModelAttribute you would write 10 @RequestParam parameters and 10 setter calls. With @ModelAttribute you write one parameter and Spring fills the whole object for you.

How it works: Spring takes every field in the submitted form, finds the matching setter in your Java class (e.g., form field name → calls setName()), and calls it. By the time your method runs, the object is fully populated.

One rule: Your model class MUST have a no-argument constructor. Spring calls new Student() first, then fills the fields.

Without @ModelAttribute — painfuljava
@PostMapping("/save")
public String save(@RequestParam String name,
                     @RequestParam String email,
                     @RequestParam int age,
                     @RequestParam String course) {
    Student s = new Student();
    s.setName(name);   s.setEmail(email);
    s.setAge(age);     s.setCourse(course);
    // ... add more fields → nightmare
    return "success";
}
With @ModelAttribute — cleanjava
@PostMapping("/save")
public String save(@ModelAttribute Student student, Model model) {
    // Spring has already called setName(), setEmail(), setAge(), setCourse()
    // student is fully populated — just use it
    model.addAttribute("student", student);
    return "confirmation";
}

// GET: show the empty form — put a blank Student in the model
// so th:object in the template has something to bind to
@GetMapping("/register")
public String showForm(Model model) {
    model.addAttribute("student", new Student());
    return "register";
}
@RequestBody Reads JSON data sent by JavaScript or mobile apps
WHY we need it — HTML forms send data as plain text pairs (name=Ravi&age=22). But JavaScript apps and mobile apps send data as JSON ({"name":"Ravi","age":22}). These are two completely different formats. @RequestBody reads the JSON format. @ModelAttribute reads the form format. You cannot swap them.

What happens internally: Spring uses a library called Jackson (included automatically with Spring Boot) to parse the JSON string into a Java object. Jackson reads each JSON key, finds the matching setter in your class, and calls it. You get a fully populated object.

StudentApiController.javajava
@RestController
@RequestMapping("/api")
public class StudentApiController {

    // A JavaScript app sends: POST /api/students
    // with body: {"name":"Ravi","email":"ravi@x.com","age":22}
    @PostMapping("/students")
    public String createStudent(@RequestBody Student student) {
        // Jackson parses the JSON and calls setName(), setEmail(), setAge()
        // student is ready to use
        return "Saved: " + student.getName();
    }
}
Sends this formatUse this annotation
HTML form (name=Ravi&age=22)@ModelAttribute
JSON body ({"name":"Ravi","age":22})@RequestBody
Single URL value (?name=Ravi)@RequestParam
URL path value (/students/5)@PathVariable
@ResponseBody Returns data as JSON instead of rendering a Thymeleaf template
WHY we need it — Normally a @Controller method returns a template name (a String) and Spring renders an HTML page. But sometimes you just want to return data — for example to a JavaScript app or a mobile app that will display it in its own way. @ResponseBody tells Spring: skip the template, send this object directly as JSON.

@RestController is the shortcut: Adding @ResponseBody to every method in a class is repetitive. @RestController = @Controller + @ResponseBody on every method. Use @RestController for classes that only return JSON, and @Controller for classes that render Thymeleaf templates.

Using @ResponseBody on one methodjava
@Controller
public class MixedController {

    // Returns an HTML page (uses Thymeleaf)
    @GetMapping("/students/page")
    public String listPage(Model model) {
        return "students/list";   // template name
    }

    // Returns JSON (no template involved)
    @GetMapping("/api/students")
    @ResponseBody
    public List<Student> listJson() {
        return List.of(
            new Student("Ravi",  "Java", 22),
            new Student("Priya", "Cloud", 24)
        );
        // Jackson converts the List to JSON automatically:
        // [{"name":"Ravi","course":"Java","age":22}, ...]
    }
}
@RestController — shortcut for all-JSON controllersjava
@RestController          // = @Controller + @ResponseBody on every method
@RequestMapping("/api/students")
public class StudentApiController {

    @GetMapping              // GET /api/students → JSON array
    public List<Student> getAll() { return studentService.findAll(); }

    @GetMapping("/{id}")     // GET /api/students/5 → one JSON object
    public Student getOne(@PathVariable int id) {
        return studentService.findById(id);
    }
}

Section 5

A Complete Working Example — Student Registration

This example connects everything: a Student model class, a Controller with GET and POST, and a Thymeleaf form using th:object and th:field. We trace the full data journey — from the empty form to the filled object and back to a confirmation page.

Step 1 — The Student model class

model/Student.javajava
public class Student {

    private String name;
    private String email;
    private String course;
    private int    age;

    public Student() {}   // REQUIRED — Spring calls new Student() to create an empty one

    // Getters — Thymeleaf calls these to READ values into the template
    public String getName()           { return name; }
    public String getEmail()          { return email; }
    public String getCourse()         { return course; }
    public int    getAge()            { return age; }

    // Setters — DataBinder calls these to WRITE form values into this object
    public void   setName(String n)   { this.name   = n; }
    public void   setEmail(String e)  { this.email  = e; }
    public void   setCourse(String c) { this.course = c; }
    public void   setAge(int a)       { this.age    = a; }
}

Step 2 — The Controller

controller/StudentController.javajava
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.*;

@Controller
public class StudentController {

    // ─── Step A: User visits /register ───────────────────────────
    @GetMapping("/register")
    public String showForm(Model model) {

        // Put an EMPTY Student into the model.
        // Thymeleaf's th:object="${student}" needs this to bind the form.
        model.addAttribute("student", new Student());
        return "register";   // renders templates/register.html
    }

    // ─── Step B: User fills form and clicks Save ─────────────────
    @PostMapping("/register")
    public String submitForm(@ModelAttribute Student student,
                                Model model) {

        // Spring has already filled student.name, student.email,
        // student.course, student.age from the form fields.
        // studentService.save(student); ← in a real app

        model.addAttribute("student", student);
        return "confirmation";   // renders templates/confirmation.html
    }
}

What th:field does — explained clearly

th:field="*{name}" generates THREE HTML attributes at once

You write this one linehtml
<input type="text" th:field="*{name}" />
Thymeleaf renders this in the final HTMLhtml
<input type="text"
       id="name"       ← generated from the field name
       name="name"     ← THIS is what Spring reads to call setName()
       value="" />     ← blank on a new form; pre-filled on an edit form

The name attribute is the critical one. When the form submits, the browser sends name=Ravi. Spring reads this and calls student.setName("Ravi"). If the name attribute were wrong, the field would be silently ignored.

Using th:field means you can never get this wrong — it always generates the correct name from the Java field name.

Section 6

How a Request Flows Through the System

Understanding the complete flow from the user's click to the page they see is the key to understanding Spring MVC. Here is the full journey, traced step by step for both a GET request (loading the form) and a POST request (submitting the form).

Journey A — Loading the form (GET /register)

1
Browser
User visits /register. Browser sends GET /register.
2
DispatcherServlet
Spring's front door. Receives every request. Finds the right Controller method.
3
showForm()
@GetMapping("/register") method runs. Adds empty Student to Model. Returns "register".
4
Thymeleaf
Finds register.html. Reads Student from Model. Renders the empty form.
5
Browser
Receives HTML page. Shows the empty form to the user.

Journey B — Submitting the form (POST /register)

1
Browser
User fills form, clicks Register. Browser sends POST /register with name=Ravi&email=...&age=22
2
DispatcherServlet
Receives POST request. Finds submitForm() method in StudentController.
3
DataBinder
Creates new Student(). Reads each field. Calls setName(), setEmail(), setAge(). Converts "22" to int.
4
submitForm()
Your method runs with a fully populated Student. Saves it. Adds it to Model. Returns "confirmation".
5
Thymeleaf
Reads Student from Model. Renders confirmation.html with the real values filled in.
6
Browser
Receives HTML page. Shows "Registration Successful" with the student's details.
+
The pattern repeats for every feature

Every Spring MVC feature you build — student list, product search, order form, login page — follows this exact same pattern. Browser → DispatcherServlet → Controller method → Model → Thymeleaf → Browser. Once you understand this flow, new features become straightforward to build.

Complete Series Summary

  • Spring MVC structures your app into Model (data), View (templates), Controller (logic). DispatcherServlet is the single entry point that routes every request.
  • Thymeleaf templates are valid HTML that display dynamic data from the Model using th: attributes. They look good even without running Spring.
  • @Controller marks a class as a request handler. Methods return template names or redirect URLs.
  • @GetMapping and @PostMapping connect URLs and HTTP methods to specific methods. GET = read. POST = write.
  • @RequestParam reads one value from the URL query string — ?name=Ravi.
  • @PathVariable reads a value from inside the URL path — /students/{id}.
  • @ModelAttribute fills a whole Java object from all submitted form fields at once. Requires a no-arg constructor.
  • @RequestBody parses a JSON request body into a Java object — for REST API calls from JavaScript or mobile apps.
  • @ResponseBody sends a Java object as JSON directly — no template involved. @RestController applies it to every method in the class.
  • th:object + th:field bind a form to a Java object. th:field generates the correct id, name, and value attributes automatically.
  • DataBinder runs between the request and your method. It creates the object, reads form fields, calls setters, and converts types. You never write this code.
