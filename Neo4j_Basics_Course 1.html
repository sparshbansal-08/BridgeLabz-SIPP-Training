INTRODUCTION

Introduction to Neo4j

What is Neo4j?
Neo4j is a graph database — a system that stores data as connected points rather than rows in a table. The name comes from Neo (new) and 4j (for Java, because it runs on the JVM). It is the world's most widely deployed graph database.
Why is it different?
Traditional databases (MySQL, PostgreSQL) store data in tables. Neo4j stores data as a network of nodes (things) and relationships (connections). Connections are first-class citizens — they have their own storage and properties.
Plain analogy
Imagine a city map. The cities are nodes. The roads connecting them are relationships. The name of a city or the length of a road are properties. Neo4j is built specifically to work with maps like this — fast, no matter how many connections exist.
Where is it used?
Fraud detection (banks), recommendation engines (Netflix, Amazon), knowledge graphs (Google), social networks (LinkedIn), logistics (shipping routes), healthcare (drug interactions), cybersecurity (attack path analysis).
Beginner: You do not need to know SQL, graph theory, or any programming language to start. This course starts from zero and explains every term.

India: Neo4j is used at Flipkart (product recommendations), Razorpay (fraud detection), Wipro and TCS (knowledge graphs), and Infosys (supply chain). Graph databases are a growing skill in Indian tech.
Section Summary: Neo4j stores data as nodes and relationships in a graph. This makes it naturally fast for connected data — things that are slow in traditional databases (joins across many tables) are instant in Neo4j.

The Property Graph Model

Node
A node represents a thing — a Person, Product, City, Movie. It can have one or more labels and any number of properties.
Relationship
A relationship connects two nodes. It always has a direction (from → to) and a type (KNOWS, BOUGHT, LIVES_IN). It can also have properties (since: 2020, weight: 0.8).
Label
A label is a tag on a node that says what type it is — like a category. A node can have multiple labels: a node can be both a Person and an Employee.
Property
A property is a key-value pair stored on a node or relationship. Examples: name: 'Alice', age: 30, since: 2020. Values can be strings, numbers, booleans, or lists.

CYPHER

Cypher Query Language

Cypher is Neo4j's query language. It is designed to look like ASCII art — the way you write a query looks like a picture of what you are searching for.

MATCH
Find patterns in the graph. Like SELECT in SQL. Most queries start with MATCH.
WHERE
Filter results by a condition. Like WHERE in SQL.
RETURN
Specify what to return. Every query must end with RETURN (or another output clause).
CREATE
Create nodes and relationships.
MERGE
Create if not exists, match if it does. Prevents duplicates.
SET
Add or update properties.
DELETE
Remove nodes or relationships.

Cypher Pattern Syntax — The Core Idea

Key: In Cypher, a node is written as () and a relationship is written as -[:TYPE]->. You draw what you want to find.
Cypher pattern syntax explainedCYPHER
// A node: (variable:Label {property: value})
(alice:Person {name: "Alice"})

// A relationship: -[:TYPE]->
[:KNOWS]

// A pattern (node-relationship-node):
(alice:Person)-[:KNOWS]->(bob:Person)

// Full query:
MATCH (alice:Person {name: "Alice"})-[:KNOWS]->(friend:Person)
RETURN friend.name

// Reading it like a sentence:
// "Find Alice (a Person), follow KNOWS relationships,
//  and return the names of everyone she knows."
The 6 core clauses with examplesCYPHER
// 1. MATCH — find patterns
MATCH (p:Person) RETURN p.name

// 2. WHERE — filter
MATCH (p:Person) WHERE p.age > 25 RETURN p.name

// 3. CREATE — create data
CREATE (p:Person {name: "Priya", age: 28})

// 4. MERGE — create or match
MERGE (p:Person {name: "Raj"})
ON CREATE SET p.age = 30
ON MATCH  SET p.age = 31

// 5. SET — update properties
MATCH (p:Person {name: "Priya"})
SET p.city = "Mumbai"

// 6. DELETE — remove data
MATCH (p:Person {name: "Temp"})
DELETE p
// Note: use DETACH DELETE to remove a node AND its relationships

NODES & RELS

Nodes, Relationships, Properties

Every piece of data in Neo4j is either a node, a relationship, or a property on one of those. This section covers each in depth with examples.

Nodes in Detail

Creating nodesCYPHER
// Create a node with one label:
CREATE (:Person {name: "Alice", age: 30})

// Create a node with multiple labels:
CREATE (:Person:Employee {name: "Bob", department: "Engineering"})

// Create and return the new node:
CREATE (p:Product {id: 1, name: "Laptop", price: 55000})
RETURN p

// Query result:
// p: {id: 1, name: "Laptop", price: 55000}

Relationships in Detail

Key: Relationships always have a direction in Neo4j. (Alice)-[:KNOWS]->(Bob) means Alice knows Bob. You can query without direction using -[:KNOWS]- (no arrow) to match both directions.
Creating relationshipsCYPHER
// First create the nodes:
CREATE (alice:Person {name: "Alice"})
CREATE (bob:Person   {name: "Bob"})

// Then create the relationship:
MATCH (a:Person {name: "Alice"}), (b:Person {name: "Bob"})
CREATE (a)-[:KNOWS {since: 2020}]->(b)

// Create nodes AND relationships in one query:
CREATE (priya:Person {name: "Priya"})-[:WORKS_AT {since: 2022}]->(company:Company {name: "TechCorp"})

// Verify:
MATCH (p:Person)-[r:WORKS_AT]->(c:Company)
RETURN p.name, r.since, c.name
// p.name: Priya | r.since: 2022 | c.name: TechCorp

Properties in Detail

Property TypeCypher ExampleNotes
Stringname: 'Alice'Use single or double quotes
Integerage: 30Whole number
Floatprice: 55000.50Decimal number
Booleanactive: truetrue or false (lowercase)
Listtags: ['scala', 'java']Array of values
Datejoined: date('2024-01-15')Use date() function
Setting and updating propertiesCYPHER
// Add a new property:
MATCH (p:Person {name: "Alice"})
SET p.city = "Mumbai"

// Update multiple properties at once:
MATCH (p:Person {name: "Alice"})
SET p += {age: 31, active: true}
// += adds/updates without removing existing properties

// Remove a property (set to null):
MATCH (p:Person {name: "Alice"})
REMOVE p.city

// Remove a label:
MATCH (p:Person:Employee {name: "Bob"})
REMOVE p:Employee

CREATE & QUERY

Creating and Querying Graphs

This section is hands-on. You will create a small e-commerce graph and query it in multiple ways.

Build a Sample E-Commerce Graph

Create the sample graph — run in BrowserCYPHER
// Create customers:
CREATE (alice:Customer {name: "Alice", city: "Mumbai", tier: "Gold"})
CREATE (raj:Customer   {name: "Raj",   city: "Delhi",  tier: "Silver"})
CREATE (priya:Customer {name: "Priya", city: "Bangalore", tier: "Gold"})

// Create products:
CREATE (laptop:Product  {id: 1, name: "Laptop",   price: 55000, category: "Electronics"})
CREATE (phone:Product   {id: 2, name: "Phone",    price: 22000, category: "Electronics"})
CREATE (book:Product    {id: 3, name: "Scala Book", price: 899, category: "Books"})

// Create BOUGHT relationships:
MATCH (a:Customer {name: "Alice"}), (l:Product {name: "Laptop"})
CREATE (a)-[:BOUGHT {date: "2024-01-10", quantity: 1}]->(l)

MATCH (a:Customer {name: "Alice"}), (b:Product {name: "Scala Book"})
CREATE (a)-[:BOUGHT {date: "2024-01-15", quantity: 2}]->(b)

MATCH (r:Customer {name: "Raj"}), (p:Product {name: "Phone"})
CREATE (r)-[:BOUGHT {date: "2024-02-01", quantity: 1}]->(p)

MATCH (p:Customer {name: "Priya"}), (l:Product {name: "Laptop"})
CREATE (p)-[:BOUGHT {date: "2024-02-10", quantity: 1}]->(l)

// Create REVIEWED:
MATCH (a:Customer {name: "Alice"}), (l:Product {name: "Laptop"})
CREATE (a)-[:REVIEWED {rating: 5, comment: "Excellent!"}]->(l)

Querying the Graph

10 essential queriesCYPHER
// 1. All customers:
MATCH (c:Customer) RETURN c.name, c.city

// 2. What did Alice buy?
MATCH (c:Customer {name: "Alice"})-[:BOUGHT]->(p:Product)
RETURN p.name, p.price
// p.name: Laptop | p.price: 55000
// p.name: Scala Book | p.price: 899

// 3. Who bought the Laptop?
MATCH (c:Customer)-[:BOUGHT]->(p:Product {name: "Laptop"})
RETURN c.name
// Alice, Priya

// 4. Customers who spent more than 20000:
MATCH (c:Customer)-[b:BOUGHT]->(p:Product)
WHERE p.price > 20000
RETURN c.name, p.name, p.price

// 5. Total spend per customer:
MATCH (c:Customer)-[b:BOUGHT]->(p:Product)
RETURN c.name, sum(p.price * b.quantity) AS totalSpend
ORDER BY totalSpend DESC

// 6. Products not yet bought:
MATCH (p:Product)
WHERE NOT (p)<-[:BOUGHT]-()
RETURN p.name

// 7. Gold tier customers only:
MATCH (c:Customer {tier: "Gold"})
RETURN c.name, c.city

// 8. Count nodes by label:
MATCH (n)
RETURN labels(n) AS label, count(n) AS count

// 9. Average product price by category:
MATCH (p:Product)
RETURN p.category, avg(p.price) AS avgPrice, count(p) AS productCount

// 10. Full graph overview:
MATCH (n)-[r]->(m)
RETURN n, r, m

Neo4j Browser: The graph view shows circles for Customer nodes (blue) and Product nodes (orange). Arrows labelled BOUGHT and REVIEWED connect them. Alice has two outgoing BOUGHT arrows. The Laptop node has two incoming BOUGHT arrows from Alice and Priya.

// 1. Create constraints (run once on new database):
CREATE CONSTRAINT customer_id IF NOT EXISTS
FOR (c:Customer) REQUIRE c.id IS UNIQUE;

CREATE CONSTRAINT product_id IF NOT EXISTS
FOR (p:Product) REQUIRE p.id IS UNIQUE;

// 2. Create indexes for fast lookup:
CREATE INDEX customer_city IF NOT EXISTS
FOR (c:Customer) ON (c.city);

// 3. Verify setup:
SHOW CONSTRAINTS;
SHOW INDEXES;

TESTING

Testing Queries

Testing a Neo4j system means verifying that your queries return exactly the expected results. This section shows a simple but complete verification approach.

Verification query patternCYPHER
// Pattern: setup → query → assert expected result

// Step 1: Create known test data
CREATE (:TestCustomer {name: "TestAlice", city: "TestCity"})-[:BOUGHT]->(:TestProduct {name: "TestItem", price: 100})

// Step 2: Run the query you want to test
MATCH (c:TestCustomer)-[:BOUGHT]->(p:TestProduct)
RETURN c.name, p.price
// Expected output:
// c.name: TestAlice | p.price: 100

// Step 3: Assert the count is correct
MATCH (c:TestCustomer)-[:BOUGHT]->(p:TestProduct)
RETURN count(*) AS purchaseCount
// Expected: 1

// Step 4: Teardown test data
MATCH (n:TestCustomer) DETACH DELETE n
MATCH (n:TestProduct)  DETACH DELETE n
Useful verification queriesCYPHER
// Count all nodes:
MATCH (n) RETURN count(n)

// Count by label:
MATCH (n:Customer) RETURN count(n) AS customers

// Check a specific relationship exists:
MATCH (c:Customer {name: "Alice"})-[:BOUGHT]->(p:Product {name: "Laptop"})
RETURN count(*) AS exists
// 1 = relationship exists, 0 = does not exist

// See all node labels and their counts:
CALL db.labels() YIELD label
CALL apoc.cypher.run("MATCH (n:" + label + ") RETURN count(n) as count", {})
YIELD value RETURN label, value.count AS count

// Simpler version (Neo4j 5+):
MATCH (n)
RETURN labels(n)[0] AS label, count(n) AS count
ORDER BY count DESC
LAB — Verification Lab

Objective: Create test data, verify it, then clean up.

Steps:

  1. Create: CREATE (:VerifyTest {id: 99, name: 'Test'})
  2. Verify: MATCH (n:VerifyTest) RETURN count(n) — expect 1
  3. Update: MATCH (n:VerifyTest {id: 99}) SET n.status = 'checked'
  4. Confirm: MATCH (n:VerifyTest) RETURN n.status — expect 'checked'
  5. Clean up: MATCH (n:VerifyTest) DETACH DELETE n
  6. Confirm clean: MATCH (n:VerifyTest) RETURN count(n) — expect 0
□count(n:VerifyTest) returns 1 after create
□n.status returns 'checked' after set
□count(n:VerifyTest) returns 0 after delete
Section Summary: Always verify queries by checking counts and specific values. Use TestXxx labels for test data. Clean up with DETACH DELETE after testing. The result count must match the expected count.
USE CASES

Real-World Use Cases

Graph databases shine in specific scenarios where connected data matters. Here are the most common real-world uses with concrete Cypher examples.

Use Case 1 — Recommendation Engine

The problem
An e-commerce site needs to recommend products. 'People who bought X also bought Y' requires finding users similar to the current user and seeing what they bought. In SQL, this is 3+ JOINs. In Neo4j, it is one pattern.
Collaborative filtering — products Alice has not bought but similar customers haveCYPHER
// "Customers like Alice also bought:"
MATCH (alice:Customer {name: "Alice"})-[:BOUGHT]->(p1:Product)<-[:BOUGHT]-(similar:Customer)
MATCH (similar)-[:BOUGHT]->(p2:Product)
WHERE NOT (alice)-[:BOUGHT]->(p2)
  AND p2 <> p1
RETURN p2.name, count(similar) AS frequency
ORDER BY frequency DESC
LIMIT 5

Use Case 2 — Fraud Detection

The problem
A bank wants to detect fraud rings — multiple accounts sharing the same phone, address, or device, connected in a circle. In a table database, finding this requires expensive self-joins. In a graph, it is a pattern match.
Find shared identity across accountsCYPHER
// Accounts sharing the same phone number:
MATCH (a1:Account)-[:HAS_PHONE]->(ph:Phone)<-[:HAS_PHONE]-(a2:Account)
WHERE a1 <> a2
RETURN a1.id, a2.id, ph.number AS sharedPhone

// Find fraud rings (cycles of length 3+):
MATCH path = (a1:Account)-[:TRANSFERRED_TO*2..5]->(a1)
RETURN path, length(path) AS ringSize
ORDER BY ringSize

Use Case 3 — Knowledge Graph

Knowledge graph query — find connections between entitiesCYPHER
// Who directed movies that Tom Hanks acted in?
MATCH (tom:Person {name: "Tom Hanks"})-[:ACTED_IN]->(m:Movie)<-[:DIRECTED]-(dir:Person)
RETURN dir.name, m.title

// 2-degree connection: movies Tom Hanks and another actor both appeared in:
MATCH (tom:Person {name: "Tom Hanks"})-[:ACTED_IN]->(m:Movie)<-[:ACTED_IN]-(coactor:Person)
RETURN m.title, coactor.name
ORDER BY m.title

Use Case 4 — Shortest Path (Supply Chain / Logistics)

Find shortest path between two citiesCYPHER
// Find the shortest route from Mumbai to Chennai:
MATCH path = shortestPath(
  (mumbai:City {name: "Mumbai"})-[:ROAD_TO*]-(chennai:City {name: "Chennai"})
)
RETURN path, length(path) AS hops

// Find all paths up to 4 hops:
MATCH path = (mumbai:City {name: "Mumbai"})-[:ROAD_TO*1..4]->(end:City)
RETURN end.name, length(path) AS hops
ORDER BY hops
Section Summary: Neo4j excels at recommendations (similar users), fraud detection (shared entities), knowledge graphs (multi-hop reasoning), and shortest path (routing). These are slow or impossible in relational databases.

LAB — Lab 1 — Movie Graph Exploration

Overview: Use the built-in movie dataset to explore core Cypher queries.

Prerequisites: Neo4j Browser open, movie dataset loaded (:play movie-graph).

Movie lab queriesCYPHER
// 1. How many movies are in the database?
MATCH (m:Movie) RETURN count(m) AS movieCount
// Expected: ~38

// 2. List all movies released after 2000:
MATCH (m:Movie) WHERE m.released > 2000 RETURN m.title, m.released ORDER BY m.released

// 3. Who acted in The Matrix?
MATCH (p:Person)-[:ACTED_IN]->(m:Movie {title: "The Matrix"})
RETURN p.name

// 4. Tom Hanks filmography:
MATCH (tom:Person {name: "Tom Hanks"})-[:ACTED_IN]->(m:Movie)
RETURN m.title, m.released ORDER BY m.released

// 5. Co-actors of Tom Hanks:
MATCH (tom:Person {name: "Tom Hanks"})-[:ACTED_IN]->(m:Movie)<-[:ACTED_IN]-(coactor:Person)
RETURN coactor.name, count(m) AS sharedMovies
ORDER BY sharedMovies DESC LIMIT 10

// 6. Kevin Bacon 6-degrees of separation:
MATCH path = shortestPath(
  (kevin:Person {name: "Kevin Bacon"})-[*]-(tom:Person {name: "Tom Hanks"})
)

INDEXES

Indexes and Constraints

Indexes make queries faster. Constraints enforce data rules. Both are essential for production Neo4j systems.

What is an index?
An index is a lookup structure that makes finding nodes by a property value fast. Without an index, Neo4j scans every node. With an index, it jumps directly to matches.
What is a constraint?
A constraint is a rule that all data must follow. The most common is a uniqueness constraint: no two Customer nodes can have the same id. Neo4j automatically creates an index for every constraint.
When to add them?
Add a uniqueness constraint for every property you use as an ID. Add a regular index for every property you filter on in WHERE clauses.
Creating indexes and constraintsCYPHER
// Uniqueness constraint (also creates an index automatically):
CREATE CONSTRAINT customer_id IF NOT EXISTS
FOR (c:Customer) REQUIRE c.id IS UNIQUE;

// Node property index (for fast WHERE filtering):
CREATE INDEX customer_city IF NOT EXISTS
FOR (c:Customer) ON (c.city);

// Composite index (two properties together):
CREATE INDEX product_category_price IF NOT EXISTS
FOR (p:Product) ON (p.category, p.price);

// Full-text search index:
CREATE FULLTEXT INDEX productSearch IF NOT EXISTS
FOR (n:Product) ON EACH [n.name, n.description];

// Use full-text search:
CALL db.index.fulltext.queryNodes("productSearch", "laptop")
YIELD node RETURN node.name

// View all constraints:
SHOW CONSTRAINTS;

// View all indexes:
SHOW INDEXES;

// Drop an index:
DROP INDEX customer_city IF EXISTS;
SHOW INDEXES Output
Neo4j Browser: After running SHOW INDEXES, a table appears showing columns: Name, Type, Labelsortypes, Properties, State. Indexes with State=ONLINE are ready to use. A constraint shows Type=UNIQUENESS.
Key: Always create a uniqueness constraint on your ID property before loading large datasets. This prevents duplicate nodes and makes MERGE operations fast.
Section Summary: Constraints prevent bad data (uniqueness). Indexes speed up queries (lookup). Always add constraints for ID properties and indexes for frequently filtered properties. Run SHOW INDEXES to verify.

ADVANCED CYPHER

Advanced Cypher Features

This section covers Cypher patterns that go beyond simple MATCH/RETURN. These are used in real applications.

WITH — passing intermediate resultsCYPHER
// WITH passes results between query stages:
MATCH (c:Customer)-[:BOUGHT]->(p:Product)
WITH c, count(p) AS purchaseCount, sum(p.price) AS totalSpent
WHERE purchaseCount >= 2
RETURN c.name, purchaseCount, totalSpent
ORDER BY totalSpent DESC
// Only returns customers with 2+ purchases
OPTIONAL MATCH — like a LEFT JOINCYPHER
// OPTIONAL MATCH returns null instead of omitting rows when no match:
MATCH (c:Customer)
OPTIONAL MATCH (c)-[:BOUGHT]->(p:Product)
RETURN c.name, p.name
// Customers with no purchases appear with p.name = null
// Regular MATCH would omit them entirely
Variable-length paths — traversalCYPHER
// Find all people connected within 3 hops:
MATCH (alice:Person {name: "Alice"})-[:KNOWS*1..3]->(person:Person)
RETURN DISTINCT person.name

// shortestPath:
MATCH path = shortestPath(
  (a:Person {name: "Alice"})-[*]-(b:Person {name: "Bob"})
)
RETURN length(path), [node IN nodes(path) | node.name] AS route

// All shortest paths:
MATCH path = allShortestPaths(
  (a:Person {name: "Alice"})-[*]-(b:Person {name: "Bob"})
)
RETURN path
UNWIND — expand lists into rowsCYPHER
// UNWIND converts a list into individual rows:
WITH ["Alice", "Bob", "Carol"] AS names
UNWIND names AS name
MERGE (:Person {name: name})
RETURN name
// Creates 3 Person nodes from the list

// Useful for JSON import:
WITH [  {name: "Laptop", price: 55000},
        {name: "Phone",  price: 22000}] AS products
UNWIND products AS product
MERGE (p:Product {name: product.name})
ON CREATE SET p.price = product.price
Aggregation functionsCYPHER
MATCH (c:Customer)-[:BOUGHT]->(p:Product)
RETURN
  count(*) AS totalPurchases,
  count(DISTINCT c) AS uniqueCustomers,
  sum(p.price) AS totalRevenue,
  avg(p.price) AS avgPrice,
  min(p.price) AS cheapest,
  max(p.price) AS mostExpensive,
  collect(DISTINCT p.category) AS categories
Section Summary: WITH chains query stages. OPTIONAL MATCH is a LEFT JOIN. Variable-length paths use *n..m. UNWIND expands lists. collect() aggregates values into a list. These patterns appear in every real application.

Performance Tuning Basics

EXPLAIN and PROFILE — understand query executionCYPHER

Slow symptomCauseFix
NodeByLabelScan in EXPLAINNo index for the property in WHERE clauseCREATE INDEX for that property
High DB Hits in PROFILEQuery touches too many unnecessary nodesAnchor on the most specific node first

def get_all_customers(driver):
    with driver.session() as session:
        result = session.run("MATCH (c:Customer) RETURN c.name AS name, c.city AS city")
        return [{"name": row["name"], "city": row["city"]} for row in result]

def create_customer(driver, name, city, tier):
    with driver.session() as session:
        result = session.run(
            """
            MERGE (c:Customer {name: $name})
            ON CREATE SET c.city = $city, c.tier = $tier
            RETURN c.name AS name
            """,
            name=name, city=city, tier=tier
        )
        return result.single()["name"]

TROUBLESHOOT

Troubleshooting and Pitfalls

This section covers the most common errors beginners encounter with exact fixes.

Neo.ClientError.Schema.ConstraintValidationFailed

Cause: You tried to create a node that violates a uniqueness constraint — a node with that id or name already exists.

Fix: Use MERGE instead of CREATE. MERGE creates the node only if it does not exist; if it does exist, it matches it instead.
Neo.ClientError.Statement.SyntaxError

Cause: Your Cypher query has a syntax mistake — wrong keyword, missing bracket, or incorrect case.

Fix: Read the error message carefully — it shows the exact line and position. Common mistakes: MATCH without RETURN, missing parentheses (), wrong relationship direction.
This node (id=X) still has relationships — use DETACH DELETE

Cause: You tried to DELETE a node that still has relationships. Neo4j prevents orphan relationships.

Fix: Use DETACH DELETE instead of DELETE. DETACH DELETE removes the node AND all its relationships: MATCH (n:Customer {name: 'Alice'}) DETACH DELETE n
ServiceUnavailable: Could not connect to Aura

Cause: Neo4j Aura instance is paused (free instances pause after 3 days of inactivity) or your internet is down.

Fix: Log in to console.neo4j.io, find your instance, and click Resume. Wait 1-2 minutes. If internet is the issue, switch to Neo4j Desktop for offline work.
Cannot merge with non-existent property key in MERGE

Cause: MERGE requires the property used in the pattern to already be indexed or constrained. Without it, Neo4j scans all nodes.

Fix: Create a uniqueness constraint before running MERGE: CREATE CONSTRAINT c_id FOR (c:Customer) REQUIRE c.id IS UNIQUE
Query timeout — query takes too long

Cause: A query with no upper bound on a variable-length path scans too many nodes.

Fix: Add a max hops limit: change -[:KNOWS*]- to -[:KNOWS*1..5]-. Also check EXPLAIN for NodeByLabelScan — create an index if found.
Authentication failed — wrong password

Cause: The password entered is wrong. Aura passwords are shown once at creation.

Fix: Reset: in Aura console, go to your instance → Security → Reset credentials. For Desktop: stop the database, go to settings, change password.
LOAD CSV returns 0 rows — file not found

Cause: The file path is wrong. Local imports must use file:///filename.csv and the file must be in Neo4j's import directory.

Fix: For Neo4j Desktop: place the file in the import folder (shown in Desktop under the database settings). For Aura: use a public URL (GitHub raw, Google Drive public link).
duplicate nodes created after multiple imports

Cause: CREATE was used instead of MERGE during import. Every import run creates new nodes.

Fix: Change CREATE to MERGE in your import query. Add a uniqueness constraint first to make MERGE fast.
Node property returns null in Python driver

Cause: The property name in the query ('name') does not match the result key used in Python (row['Name'] vs row['name']).

Fix: Cypher is case-sensitive for property names and aliases. Verify: RETURN c.name AS name — then use row['name'] (lowercase) in Python.
Section Summary: The most common issues: use MERGE not CREATE to avoid duplicates, use DETACH DELETE not DELETE for nodes with relationships, add upper bounds to variable-length paths, and resume paused Aura instances.
