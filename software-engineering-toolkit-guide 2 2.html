Design Principles

The foundational rules that separate code that works from code that lasts. Every senior engineer applies these instinctively, and every team benefits when juniors learn them early.

What are design principles?

Design principles are time-tested guidelines for writing software that is easy to understand, easy to change, and resistant to bugs. They are not rules enforced by a compiler; they are wisdom accumulated over decades of software failures and successes. Think of them as the "grammar" of good code: you can write a sentence without grammar, but nobody will want to read your book.

Why do we need them?

Without design principles, code degrades quickly as a project grows. A 500-line program might work fine with messy code. A 50,000-line enterprise system will collapse under its own weight if every developer writes code however they please. Design principles solve three real problems:

1. Maintainability: You will read code 10 times more often than you write it. Principles make code readable and predictable so that a new team member can understand it in hours, not weeks.

2. Flexibility: Business requirements change constantly. Well-designed code can accommodate a new payment gateway, a new report format, or a new user role without rewriting half the system.

3. Reliability: Code that follows principles has fewer hidden dependencies and fewer surprise side effects, which means fewer production bugs at 2 AM.

Banking application scenario

A bank builds a loan approval system. Initially, it supports only home loans. Six months later, the business asks for car loans, education loans, and personal loans. If the original code put all loan logic in one giant class, adding each new type means editing that class, risking bugs in home loans while adding car loans. With proper design principles (particularly abstraction and separation of concerns), each loan type is its own class, and adding a new one requires zero changes to existing code.

The core principles

1. DRY (Do not Repeat Yourself)

Every piece of knowledge should exist in exactly one place. When you copy-paste code, you create two places that must be updated when requirements change. Miss one, and you have a bug.

Violating DRY
// Discount logic copied in 3 places
public double calculateCartTotal() {
    double discount = 0;
    if (customer.isPremium()) {
        discount = total * 0.10;
    }
    return total - discount;
}

public double calculateInvoiceTotal() {
    double discount = 0;
    if (customer.isPremium()) {
        discount = total * 0.10;  // same logic!
    }
    return total - discount;
}
Following DRY
// Single source of truth
public double applyDiscount(
        double total,
        Customer customer) {
    if (customer.isPremium()) {
        return total * 0.90;
    }
    return total;
}

// Both methods call the shared one
public double calculateCartTotal() {
    return applyDiscount(total, customer);
}
public double calculateInvoiceTotal() {
    return applyDiscount(total, customer);
}

2. KISS (Keep It Simple, Stupid)

The simplest solution that works is usually the best. Over-engineering is as dangerous as under-engineering. A junior developer who writes a Strategy pattern with a Factory for a feature that has only one possible implementation has added complexity that nobody needs.

Over-engineered
// For a simple "is user adult?" check:
interface AgeValidator { ... }
class AdultAgeValidator
    implements AgeValidator { ... }
class AgeValidatorFactory { ... }
class AgeValidationService { ... }
// 4 classes for one if-statement
KISS approach
public boolean isAdult(int age) {
    return age >= 18;
}
// Done. If you need more validators
// later, refactor then. Not now.

3. YAGNI (You Aren't Gonna Need It)

Do not build features "just in case." Every line of code you write today must be justified by a requirement that exists today. If the business has not asked for multi-currency support, do not build it. You are guessing about the future, and you are usually wrong.

4. Separation of Concerns

Each class, each method, each module should handle one responsibility. Your controller handles HTTP requests. Your service handles business logic. Your repository handles database access. When a billing bug appears, you know to look in the billing service, not in the HTTP controller or the database layer.

E-commerce project scenario

An online store has a checkout flow. If the order validation, payment processing, inventory update, email notification, and invoice generation are all in one 800-line method, debugging a payment failure means reading all 800 lines. With separation of concerns, each of those is a separate service class. The payment team owns PaymentService, the inventory team owns InventoryService, and each can be tested, debugged, and deployed independently.

5. Favour Composition over Inheritance

Instead of creating deep inheritance hierarchies (Animal extends LivingThing, Dog extends Animal, GuideDog extends Dog), build objects by combining smaller, reusable components. A Dog "has-a" WalkBehaviour and "has-a" BarkBehaviour. This is more flexible because you can swap behaviours at runtime without changing the class hierarchy.

Composition example
// Instead of: class EmailNotifier extends Notifier extends CommunicationService
// Use composition:

class NotificationService {
    private final MessageFormatter formatter;    // has-a
    private final DeliveryChannel channel;        // has-a
    private final RecipientResolver resolver;    // has-a

    public void send(Notification n) {
        String message = formatter.format(n);
        List<String> recipients = resolver.resolve(n);
        channel.deliver(message, recipients);
    }
}
// Now you can swap EmailChannel for SMSChannel or SlackChannel
// without touching NotificationService at all.
Practice 1 Identify the violated principle

A developer wrote a UserService class that validates user input, saves users to the database, sends a welcome email, generates a PDF report of all users, and logs analytics events. Which principle is violated and how would you fix it?

View solution

Violated: Separation of Concerns. The UserService is doing five completely unrelated jobs.

Fix: Extract into separate classes: UserValidator (validates input), UserRepository (database), WelcomeEmailService (emails), UserReportService (PDF), AnalyticsService (logging). The UserService becomes a thin orchestrator that calls each of these in sequence.

Practice 2 Refactor duplicate logic

You have three methods in an OrderService: calculateSubtotal(), calculateTaxAmount(), and calculateShippingCost(). Each one starts by fetching the order from the database and checking if it is null. The null check and database fetch code is identical in all three. How do you apply DRY?

View solution

Fix: Extract a private helper method:

private Order getOrderOrThrow(Long orderId) {
    Order order = orderRepository.findById(orderId);
    if (order == null) {
        throw new OrderNotFoundException(orderId);
    }
    return order;
}

public double calculateSubtotal(Long orderId) {
    Order order = getOrderOrThrow(orderId);
    // ... subtotal logic only
}

Now the fetch + null check lives in one place. If the logic changes (for example, soft-deleted orders should also throw), you change one method.

Practice 3 Composition vs. inheritance

You are building a reporting system. Currently: Report extends BaseDocument extends Printable. The business asks for reports that can be exported as PDF, Excel, and CSV. With inheritance, you would need PdfReport, ExcelReport, CsvReport — and if you also have Invoice and Receipt, that becomes 9 classes. Redesign this using composition.

View solution
interface ExportStrategy {
    byte[] export(DocumentData data);
}

class PdfExporter implements ExportStrategy { /* ... */ }
class ExcelExporter implements ExportStrategy { /* ... */ }
class CsvExporter implements ExportStrategy { /* ... */ }

class Report {
    private ExportStrategy exporter; // injected
    public byte[] export() {
        return exporter.export(this.data);
    }
}
// 3 exporters + 3 document types = 6 classes, not 9.
// Adding a new format = 1 new class, zero changes to existing.

SOLID Principles

Five principles introduced by Robert C. Martin (Uncle Bob) that form the backbone of object-oriented design. Master these, and your code will be flexible, testable, and resilient to change.

What is SOLID?

SOLID is an acronym for five design principles. Each letter stands for one principle. Together, they guide you to write classes that are small, focused, and easy to extend without breaking existing functionality. These are not theoretical concepts; they are practical techniques used in every serious Java project from banking systems to e-commerce platforms.

Why do we need SOLID?

Without SOLID, codebases develop three diseases: Rigidity (hard to change because every change cascades), Fragility (one change breaks something unrelated), and Immobility (impossible to reuse code in another project because everything is tangled). SOLID cures all three.

S - Single Responsibility Principle (SRP)

Definition: A class should have only one reason to change. In practical terms, each class should do exactly one job.

Why it matters: If a class handles both invoice calculation and PDF generation, and the PDF library changes, you must edit and retest a class that also contains financial logic. That is unnecessary risk.

Hospital management system

A PatientService class initially handles patient registration, appointment booking, medical history retrieval, and billing. When the billing rules change (new insurance regulations), the developer edits PatientService and accidentally breaks the appointment booking logic. With SRP, these are four separate classes: PatientRegistration, AppointmentService, MedicalHistoryService, and BillingService. Billing changes cannot affect appointments.

Violates SRP
class Employee {
    public double calculatePay() { /*...*/ }
    public void saveToDatabase() { /*...*/ }
    public String generateReport() { /*...*/ }
}
// 3 reasons to change: pay rules,
// database schema, report format
Follows SRP
class PayCalculator {
    public double calculate(Employee e) {...}
}
class EmployeeRepository {
    public void save(Employee e) {...}
}
class EmployeeReportGenerator {
    public String generate(Employee e) {...}
}
// Each class: 1 reason to change

O - Open/Closed Principle (OCP)

Definition: Software entities should be open for extension but closed for modification. You should be able to add new behaviour without changing existing, tested code.

Why it matters: Every time you modify a working class, you risk introducing bugs in production. OCP says: add new code, do not touch old code.

Payment gateway in an e-commerce platform

The platform starts with Razorpay. Later, the business wants PayPal and Stripe. If the checkout code has if (gateway == "razorpay") {...} else if (gateway == "paypal") {...}, every new gateway means editing this chain and retesting everything. With OCP, you define a PaymentGateway interface and each provider implements it. Adding UPI support means creating one new class. Zero edits to existing code.

OCP example — Payment system
// Step 1: Define the contract
interface PaymentGateway {
    PaymentResult processPayment(Order order);
}

// Step 2: Implement each gateway separately
class RazorpayGateway implements PaymentGateway {
    public PaymentResult processPayment(Order order) {
        // Razorpay-specific logic
    }
}

class StripeGateway implements PaymentGateway {
    public PaymentResult processPayment(Order order) {
        // Stripe-specific logic
    }
}

// Step 3: Checkout service depends on the interface
class CheckoutService {
    private final PaymentGateway gateway;   // injected

    public void checkout(Order order) {
        PaymentResult result = gateway.processPayment(order);
        // works with ANY gateway — no if-else chain
    }
}

// Adding UPI? Create UpiGateway implements PaymentGateway.
// CheckoutService is never modified.

L - Liskov Substitution Principle (LSP)

Definition: Subtypes must be substitutable for their base types without breaking the program. If your code works with a parent class reference, it must also work correctly with any child class.

Why it matters: If a subclass changes the expected behaviour, every piece of code that uses the parent type could break silently.

Violates LSP
class Bird {
    public void fly() {
        System.out.println("Flying");
    }
}

class Penguin extends Bird {
    public void fly() {
        throw new UnsupportedOperationException();
        // Penguin cannot fly. Code that
        // calls bird.fly() will crash.
    }
}
Follows LSP
interface Bird {
    void eat();
}
interface Flyable extends Bird {
    void fly();
}

class Sparrow implements Flyable {
    public void eat() { /*...*/ }
    public void fly() { /*...*/ }
}
class Penguin implements Bird {
    public void eat() { /*...*/ }
    // No fly() — correct!
}

I - Interface Segregation Principle (ISP)

Definition: No client should be forced to depend on methods it does not use. Split large interfaces into smaller, specific ones.

Telecom billing system

A giant TelecomService interface has 20 methods: voice call billing, SMS billing, data billing, roaming, international, postpaid, prepaid. A prepaid-only module is forced to implement postpaid methods it will never use. With ISP, you split into VoiceBilling, SmsBilling, DataBilling interfaces. Each module implements only what it needs.

Fat interface
interface Machine {
    void print();
    void scan();
    void fax();
}

// Simple printer forced to implement
// scan() and fax() — throws exceptions
class BasicPrinter implements Machine {
    public void print() { /* ok */ }
    public void scan()  { throw...; }
    public void fax()   { throw...; }
}
Segregated interfaces
interface Printer  { void print(); }
interface Scanner  { void scan(); }
interface Fax      { void fax(); }

class BasicPrinter
    implements Printer {
    public void print() { /* ok */ }
    // No scan. No fax. Clean.
}

class AllInOne
    implements Printer, Scanner, Fax {
    // Implements all three
}

D - Dependency Inversion Principle (DIP)

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions (interfaces). In simple terms, your business logic should not know whether it is talking to MySQL, PostgreSQL, or a mock database. It talks to an interface.

DIP example — Notification system
// BAD: High-level depends on low-level
class OrderService {
    private GmailSender sender = new GmailSender();
    // Tightly coupled to Gmail. Cannot swap to SMS or Slack.
}

// GOOD: Both depend on abstraction
interface NotificationSender {
    void send(String to, String message);
}

class GmailSender implements NotificationSender { /*...*/ }
class SmsSender   implements NotificationSender { /*...*/ }

class OrderService {
    private final NotificationSender sender;  // injected

    public OrderService(NotificationSender sender) {
        this.sender = sender;
    }
    // Works with Gmail, SMS, Slack — whatever is injected
}
i
Spring Boot connection

If you use Spring Boot, dependency injection via @Autowired or constructor injection is the framework's built-in way of implementing DIP. Spring creates the concrete class and injects it into your service. You program to the interface; Spring provides the implementation.

Practice 1 Identify SOLID violations

A class ReportManager does the following: fetches data from MySQL, applies business rules to filter the data, converts results to PDF, and emails the PDF to managers. Which SOLID principles does it violate?

View solution

SRP: Four responsibilities in one class (data access, business logic, PDF generation, email sending).

OCP: If you need Excel output instead of PDF, you must modify ReportManager.

DIP: Direct dependency on MySQL (should use a Repository interface) and direct dependency on email (should use a NotificationSender interface).

Fix: Split into DataRepository (interface), ReportFilter (business logic), ReportExporter (interface with PdfExporter, ExcelExporter implementations), ReportNotifier (interface). ReportManager becomes a thin orchestrator calling these four.

Practice 2 Apply OCP to a discount system

An online store calculates discounts with a big if-else chain: if (type == "FESTIVAL") ... else if (type == "LOYALTY") ... else if (type == "BULK") .... Refactor this to follow OCP so that adding a new discount type requires zero changes to existing code.

View solution
interface DiscountStrategy {
    double apply(Order order);
}

class FestivalDiscount implements DiscountStrategy {
    public double apply(Order order) {
        return order.getTotal() * 0.20; // 20% off
    }
}

class LoyaltyDiscount implements DiscountStrategy {
    public double apply(Order order) {
        return order.getTotal() * 0.05; // 5% off
    }
}

class OrderService {
    private final DiscountStrategy discount; // injected

    public double finalPrice(Order order) {
        return order.getTotal() - discount.apply(order);
    }
}
// New discount? Create a new class. OrderService untouched.
Practice 3 Fix an LSP violation

A Rectangle class has setWidth() and setHeight(). A Square extends Rectangle and overrides both methods to keep width and height equal. Code that sets width=5 and height=10 on a Rectangle reference expects area=50, but when the object is actually a Square, the area is 100. How do you fix this LSP violation?

View solution

Make Rectangle and Square separate classes that both implement a Shape interface with a getArea() method. Do not extend Rectangle from Square or vice versa. They have different constraints (Square enforces equal sides), so one cannot substitute for the other.

interface Shape {
    double getArea();
}

class Rectangle implements Shape {
    private double width, height;
    public double getArea() { return width * height; }
}

class Square implements Shape {
    private double side;
    public double getArea() { return side * side; }
}

UML Basics

Unified Modelling Language is the visual language of software design. Before writing code, architects draw UML diagrams the same way building architects draw blueprints before laying bricks.

What is UML?

UML (Unified Modelling Language) is a standardised way to draw diagrams that represent the structure and behaviour of a software system. It is not a programming language; it is a visual notation that helps developers, architects, and business stakeholders communicate about how a system works without ambiguity.

Why do we need UML?

Imagine a team of 15 developers building an insurance claims system. Without diagrams, each developer has a different mental picture of how the system works. One thinks the ClaimValidator calls the PaymentService directly; another thinks it goes through an ApprovalWorkflow first. UML gives everyone a shared, unambiguous picture. It is used in design meetings, code reviews, onboarding documents, and system documentation.

Banking project onboarding

A new developer joins a banking project. Instead of reading 200 source files to understand the system, they are given three UML diagrams: a class diagram showing all the domain classes and their relationships, a sequence diagram showing how a fund transfer flows from the REST controller through validation, debit, credit, and notification, and a use case diagram showing all the features available to customers, tellers, and managers. In one hour, the new developer understands the architecture. Without UML, this would take a week of reading code.

The three most useful UML diagrams

1. Class diagram (shows structure)

A class diagram shows the classes in your system, their attributes (fields), their methods, and the relationships between them. Each class is drawn as a box with three sections: class name, attributes, and methods.

Test-Driven Development (TDD)

Write the test first, watch it fail, write the minimum code to pass, then refactor. This counterintuitive cycle produces cleaner, more reliable code than writing tests after the fact.

What is TDD?

Test-Driven Development is a development methodology where you write a failing test before writing any production code. The cycle has three steps, often called Red-Green-Refactor:

Red: Write a test for a feature that does not exist yet. Run it. It fails (red). This proves the test is meaningful, it is actually checking something.

Green: Write the simplest possible code to make the test pass. Do not optimise, do not handle edge cases yet. Just make the red test turn green.

Refactor: Now clean up the code. Remove duplication, improve naming, extract methods. Run the tests again to confirm nothing broke. The tests are your safety net during refactoring.

Why do we need TDD?

Most developers write code first and tests later (or never). The problem: when you write tests after the code, you unconsciously write tests that confirm what you already built, not tests that verify what the business actually needs. TDD forces you to think about requirements and edge cases before writing any implementation.

Insurance premium calculator

A team needs to build a premium calculator for health insurance. The business rules are complex: age-based rates, smoker surcharge, pre-existing condition loading, family discount. With TDD, each business rule becomes a test first: "A 30-year-old non-smoker with no conditions should pay Rs. 5,000/month." Then the developer writes code to pass that test. Then: "A 30-year-old smoker should pay Rs. 7,500/month." Each rule is verified before moving to the next. When the code is complete, there is a comprehensive test suite that acts as living documentation of every business rule.

Step-by-step TDD example

Scenario: Build a StringCalculator that adds numbers from a comma-separated string.

Cycle 1: Empty string returns 0

RED — Write the failing test first
@Test
void shouldReturnZeroForEmptyString() {
    StringCalculator calc = new StringCalculator();
    assertEquals(0, calc.add(""));
}
// This will NOT compile yet — StringCalculator does not exist.
GREEN — Write minimum code to pass
public class StringCalculator {
    public int add(String numbers) {
        return 0;  // simplest code that passes
    }
}

Cycle 2: Single number returns that number

RED
@Test
void shouldReturnNumberForSingleInput() {
    assertEquals(5, calc.add("5"));
}
// FAILS: returns 0 instead of 5
GREEN
public int add(String numbers) {
    if (numbers.isEmpty()) return 0;
    return Integer.parseInt(numbers);
}

Cycle 3: Two numbers separated by comma

RED, then GREEN
@Test
void shouldReturnSumOfTwoNumbers() {
    assertEquals(8, calc.add("3,5"));
}

// GREEN — updated implementation:
public int add(String numbers) {
    if (numbers.isEmpty()) return 0;
    String[] parts = numbers.split(",");
    int sum = 0;
    for (String part : parts) {
        sum += Integer.parseInt(part.trim());
    }
    return sum;
}
// All 3 tests pass. REFACTOR if needed, then move to next cycle.
i
Key TDD rule

Never write production code without a failing test. If all your tests pass, you cannot write production code, only refactor. This discipline ensures 100% of your code is covered by tests.

Practice 1 TDD a password validator

Using TDD (write test first, then code), build a PasswordValidator with these rules: minimum 8 characters, at least one uppercase letter, at least one digit, at least one special character. Write one test per rule, make each pass before writing the next test.

View solution
// Test 1: too short
@Test
void rejectPasswordShorterThan8() {
    assertFalse(validator.isValid("Ab1!"));  // 4 chars
}

// Test 2: no uppercase
@Test
void rejectPasswordWithoutUppercase() {
    assertFalse(validator.isValid("abcdefg1!"));
}

// Test 3: no digit
@Test
void rejectPasswordWithoutDigit() {
    assertFalse(validator.isValid("Abcdefgh!"));
}

// Test 4: no special char
@Test
void rejectPasswordWithoutSpecialChar() {
    assertFalse(validator.isValid("Abcdefg1"));
}

// Test 5: valid password
@Test
void acceptValidPassword() {
    assertTrue(validator.isValid("Abcdefg1!"));
}

// Implementation built incrementally:
public boolean isValid(String pw) {
    if (pw.length() < 8) return false;
    if (!pw.matches(".*[A-Z].*")) return false;
    if (!pw.matches(".*[0-9].*")) return false;
    if (!pw.matches(".*[!@#$%^&*].*")) return false;
    return true;
}

JUnit 5

The standard testing framework for Java. Every professional Java project uses JUnit. It is the tool that turns TDD from theory into practice.

What is JUnit?

JUnit is a framework that lets you write small, automated test methods that verify your code works correctly. You write a test method, call your code inside it, and use assertions to check that the result matches your expectation. If the assertion fails, JUnit reports the test as failed with a clear message showing expected vs. actual values.

Why do we need JUnit?

Without JUnit, the only way to verify your code is to run the application manually and click through every feature after every change. In a large project with 500 features, manual testing after every code change would take days. With JUnit, you write tests once, and they run in seconds. A team of 20 developers making changes every hour can run 2,000 tests in under a minute to confirm nothing is broken.

Setup: Add to pom.xml

pom.xml
<dependency>

Mockito

When your class depends on a database, an external API, or another service, Mockito lets you create fake versions of those dependencies so you can test your class in complete isolation.

What is Mockito?

Mockito is a Java mocking framework. A "mock" is a fake object that pretends to be a real dependency. You tell the mock what to return when a specific method is called, and then you verify that your class interacted with the mock correctly.

Why do we need Mockito?

Imagine testing an OrderService that calls a PaymentGateway (which charges real credit cards) and a DatabaseRepository (which needs a running database). Without mocking, your test would charge a real credit card and require a database server running. With Mockito, you create fake versions of PaymentGateway and DatabaseRepository that return predefined responses. Your test runs in milliseconds, charges no cards, and needs no database.

Microservices project

A team builds a flight booking service that depends on three external services: SeatAvailability API, PricingEngine API, and PaymentGateway API. During development, the Pricing team has not deployed their API yet. Without Mockito, the booking team cannot test their code. With Mockito, they mock the PricingEngine to return a fixed price and continue testing the booking flow end to end. When the real PricingEngine is ready, they replace the mock with integration tests.

        OrderResult result = orderService.placeOrder(order);

        // ASSERT — verify the result
        assertTrue(result.isSuccess());
        assertEquals("TXN-123", result.getTransactionId());

        // VERIFY — confirm interactions happened
        verify(paymentGateway, times(1)).charge(order);
        verify(orderRepo, times(1)).save(order);

PMD

What is PMD?

PMD is an open-source static analysis tool for Java (and other languages). "Static analysis" means it reads your source code directly, without executing it. public class OrderProcessor {

    private final Map<String, Consumer<Order>> handlers = Map.of(
        "PENDING",   this::handlePending,
        "APPROVED",  this::handleApproved,
        "SHIPPED",   this::handleShipped,
        "DELIVERED", this::handleDelivered
    );

    public void process(Order order) {
        // No unused variable
        try {
            double total = order.getTotal();
        } catch (Exception e) {
            log.error("Failed to get total: {}", e.getMessage());
            throw e;  // re-throw or handle properly
        }

        // Low complexity: Map lookup replaces 4 if-else branches
        Consumer<Order> handler = handlers.get(order.getStatus());
        if (handler != null) handler.accept(order);
    }
    // No unused private methods
}

SpotBugs

SpotBugs analyses your compiled bytecode (not source code) to find real bugs that other tools miss: null pointer dereferences, infinite loops, resource leaks, incorrect synchronisation, and more.

What is SpotBugs?

SpotBugs is the successor to FindBugs. Unlike PMD (which analyses source code), SpotBugs analyses compiled .class files (Java bytecode). This gives it a deeper understanding of how your code actually behaves at runtime. It can detect bugs that are invisible in source code but become apparent in bytecode, such as incorrect equality comparisons, potential null pointer exceptions, and resource leaks.

Why do we need SpotBugs?

PMD and Checkstyle look at source code patterns. SpotBugs looks at execution patterns. Some bugs only reveal themselves at the bytecode level. For example, comparing two Integer objects with == instead of .equals() works for values between -128 and 127 (due to Integer caching) but fails for 128 and above. This is invisible to source-level tools but SpotBugs catches it because it understands Java's type system at the bytecode level.

E-commerce platform production bug

An e-commerce platform had a bug where orders above Rs. 12,700 were being charged incorrectly. The root cause: a developer compared two Integer objects using == instead of .equals(). For order quantities 1 to 127, the comparison worked (Integer caching). For quantity 128+, it failed silently and the discount was not applied. PMD did not catch this because the source code looks correct. SpotBugs would have flagged it immediately as a "RC_REF_COMPARISON_BAD_PRACTICE" bug.

Example: Bugs SpotBugs catches that PMD misses

Code with hidden bugs
public class InvoiceService {

    // BUG 1: Null pointer risk
    public String getCustomerName(Long invoiceId) {
        Invoice invoice = repo.findById(invoiceId);
        return invoice.getCustomer().getName();
        // SpotBugs: NP_NULL_ON_SOME_PATH
        // repo.findById may return null
    }

    // BUG 2: Integer comparison
    public boolean isSameQuantity(Integer a, Integer b) {
        return a == b;
        // SpotBugs: RC_REF_COMPARISON
        // Works for -128..127, fails for 128+
    }

    // BUG 3: Resource leak
    public String readReport(String path) throws IOException {
        FileReader reader = new FileReader(path);
        return new BufferedReader(reader).readLine();
        // SpotBugs: OBL_UNSATISFIED_OBLIGATION
        // FileReader never closed if exception occurs
    }
}

Fixed versions

Bugs fixed
// FIX 1: Null check
public String getCustomerName(Long invoiceId) {
    return repo.findById(invoiceId)
        .map(Invoice::getCustomer)
        .map(Customer::getName)
        .orElse("Unknown");
}

// FIX 2: Use .equals()
public boolean isSameQuantity(Integer a, Integer b) {
    return Objects.equals(a, b);
}

// FIX 3: try-with-resources
public String readReport(String path) throws IOException {
    try (BufferedReader reader = new BufferedReader(
            new FileReader(path))) {
        return reader.readLine();
    }
}

Recommended CI/CD pipeline order

In your build pipeline, run them in this order: (1) Checkstyle — fast, catches style issues. (2) PMD — fast, catches code smells. (3) Compile — must compile before SpotBugs. (4) Tests + JaCoCo — runs tests and measures coverage. (5) SpotBugs — analyses bytecode for bugs. (6) SonarQube — aggregates all results into dashboard. If any tool fails, the pipeline stops early, saving time.

Practice 1 Identify SpotBugs patterns

For each code snippet, identify the SpotBugs bug pattern and write the fixed version:

Snippet A:

public Date getCreatedDate() {
    return this.createdDate;  // Date is mutable
}

Snippet B:

String query = "SELECT * FROM users WHERE name = '" + name + "'";
statement.execute(query);
View solution

Snippet A — EI_EXPOSE_REP: Returns a reference to a mutable internal Date field. The caller can modify it, breaking encapsulation.

public Date getCreatedDate() {
    return new Date(this.createdDate.getTime()); // defensive copy
}
// Even better: use java.time.LocalDate (immutable)

Snippet B — SQL_NONCONSTANT_STRING_PASSED_TO_EXECUTE: String concatenation in SQL query = SQL injection vulnerability.

PreparedStatement stmt = connection
    .prepareStatement("SELECT * FROM users WHERE name = ?");
stmt.setString(1, name);  // safe: parameterized query
stmt.executeQuery();
