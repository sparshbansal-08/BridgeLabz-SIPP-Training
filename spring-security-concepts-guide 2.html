How to use this guide

This is a thinking guide, not a build guide. There is no code to copy and nothing to install. The single goal is to make each security idea click — what it is, why it exists, and which keyword stands for it — so when you later build a project, every step already feels obvious.

One example runs through the whole guide: a simple online banking application. It has three kinds of pages: a public home page anyone can see, an account details page only the logged-in account owner can see, and an admin panel only staff can access. Every concept here protects exactly that kind of system.

The banking app our example uses throughout. Three pages, three different access levels. Spring Security protects each one.

Every concept follows the same seven headings: what it is (with an analogy), why we need it, whether it is mandatory, what happens without it, what we gain, the keyword that represents it, and how it connects to the rest.

The most important distinction

Authentication vs Authorisation

These two words sound similar and are often confused. Get them straight now and the rest of the guide will fall into place. They are two separate checks that happen one after the other.

Authentication always happens first. Authorisation only runs after identity is confirmed. They are two different questions.

The big picture

What Spring Security is

Spring Security is a framework that adds security to a Spring Boot application. Its two jobs are exactly the two steps above: Authentication (who are you?) and Authorisation (what can you do?).

The moment you add Spring Security to a project, it immediately does several things automatically — without you writing a single line:

  • Every single URL in the application becomes protected. Nobody can access anything without logging in.
  • A basic login form appears at /login.
  • A random password is generated and printed in the console for a default user.
  • Logout is handled at /logout.
  • Sessions are managed between requests.

What you would have to build by hand without it

Without Spring Security, every protected endpoint would need its own manual check: "Is there a logged-in session? Does this user have the right role?" — written in every controller, every method. You would also need to build the login form, session management, password hashing, token validation, CSRF protection, and CORS handling yourself. That is hundreds of lines of security-critical code where one mistake creates a real vulnerability.

The simplest way to understand it

Spring Security is a layer that sits in front of your application and handles all the "who can get in?" questions in one place, so your controllers can focus entirely on their job.

An honest answer

Is Spring Security mandatory for every project?

No — but for most real applications it is the right choice. Here is the honest picture.

Use it when

Users log in. Data belongs to specific people. Some pages need roles. You store passwords. Any of these is enough reason.

You can skip it when

A tiny internal tool, a fully public API with no user accounts, or a quick learning prototype where security does not matter yet.

The real risk of skipping it

If you skip Spring Security and later try to add security manually, you will almost certainly miss something. Security is one of those things that is far easier to build in from the start than to bolt on later. For any application that touches real user data, treat it as mandatory.

1
The foundation

The Filter Chain

The Filter Chain is an ordered row of checkpoints that every HTTP request must pass through before it ever reaches your application code. Think of it as a series of security gates at an airport.

Analogy — Airport security

Before boarding a flight, you pass through check-in (who are you?), then passport control (is this document valid?), then the security scanner (are you carrying anything dangerous?). Each gate does one job. Miss one gate and you cannot board. The Filter Chain works exactly the same way for web requests.

Each filter does one job. The request passes all three or is stopped. Order matters: you cannot authorise before authenticating.
Why we need it

Without a filter chain, security checks would have to be copy-pasted into every controller method. With the chain, security is handled once, in one place, before any application code even runs. The chain is also where Spring Security adds its automatic protections — even before you write any configuration.

MANDATORY The Filter Chain is the entire mechanism Spring Security runs on. Everything else is part of it.
✗ Without it

Security logic must be repeated in every controller. One forgotten check and a protected page becomes public. Maintenance is a nightmare.

✓ What we gain

All security in one ordered pipeline. Add or remove a filter and every request is instantly affected. Controllers stay clean.

The keyword that represents it
KeywordWhat it means (plain English)Status
SecurityFilterChainThe Java type that represents the ordered list of filters for your application. Defining one is how you customise what the chain does.MANDATORY
OncePerRequestFilterA base class for writing your own custom filter that runs exactly once per request. You extend this when adding JWT or custom checks.OPTIONAL
How it connects

The Filter Chain is the container. Every other concept in this guide — Authentication, Authorisation, JWT — is a filter inside this chain. Understanding the chain first means the rest fits naturally.

2
Core concept

Authentication

Authentication is the process of confirming who you are. In Spring Security it has two steps: collect what the user claims (username and password), then verify that claim against a trusted source (the database).

Analogy — Hotel check-in

You arrive at a hotel and say "I have a reservation under Smith." The receptionist does not just take your word for it — they look up "Smith" in the system and check that your ID matches. If it does, they hand you a key card. If not, they turn you away. Spring Security does exactly this for every login.

The Manager coordinates; the Provider does the actual check. On success, identity is stored in the Security Context for this request.
Why we need it

Without authentication, any request could claim to be anyone. In the banking app, without authentication anyone could reach /account and see all accounts. Authentication is the lock on the door.

MANDATORY Authentication is one of the two core jobs of Spring Security. Every protected application needs it.
✗ Without it

All URLs are effectively public. Anyone can access any page by just visiting the address, regardless of whether they should.

✓ What we gain

Only users who prove their identity can access protected pages. The identity is stored so the rest of the request does not need to re-verify.

3
Core concept

Security Context & SecurityContextHolder

The Security Context is a small storage space that holds the identity of the currently logged-in user for the duration of one request. The SecurityContextHolder is the class that owns that storage space and makes it available everywhere.

Analogy — Staff ID badge while inside the building

Once you scan your badge at the entrance and security confirms who you are, you wear your badge all day. Any colleague or locked door can check your badge without you having to re-prove your identity at every step. At the end of the day you hand the badge back. The Security Context is that badge, held in memory for the duration of your visit (the request).

After authentication, identity is stored in the Security Context for this request. Filters and controllers can all read it. When the request ends, it is wiped.
Why we need it

After authentication confirms who the user is, that information needs to be available to every part of the application for the rest of that request — the authorisation filter, the controller, and any service method. Without a shared context, each would have to re-verify the user separately.

MANDATORY The Security Context is how identity flows through a request. Spring Security uses it constantly behind the scenes.
✗ Without it

There is no shared way to know "who is this request from?" Each part of the code would need its own identity-checking logic, leading to repetition and inconsistency.

✓ What we gain

One place holds the identity for the whole request. Any controller can ask "who is the current user?" with one line, and always gets the same answer.

The keyword that represents it
KeywordWhat it means (plain English)Status
SecurityContextHolderThe class that owns the Security Context. Think of it as the badge rack. You call SecurityContextHolder.getContext() to read who is logged in.AUTOMATIC
Authentication (the interface)The object stored in the context that represents "the current user and their roles." It is what you read when you want to know who made this request.AUTOMATIC
How it connects

Authentication (concept 2) writes to the Security Context. Authorisation (concept 6) reads from it to decide what the user is allowed to do. The context is the handoff point between the two.

4
Core concept

UserDetails & UserDetailsService

UserDetails is the shape (the "mould") that Spring Security uses to understand a user. UserDetailsService is the bridge that loads a user from your database and fits them into that mould. Spring Security does not know how your database is structured, so it needs you to provide this bridge.

Analogy — The standard ID card format

A government office accepts ID cards in one standard format: name, photo, ID number, expiry date. Your bank card, driving licence, and passport are all different shapes — but a translator can read yours and fill in the standard form. UserDetailsService is that translator.

Your User entity (your shape) is loaded by your UserDetailsService and converted into a UserDetails (Spring's shape). Spring Security only ever sees UserDetails.
Why we need it

Spring Security does not know that your database has a table called app_users with a column called email. It only knows one standard shape: UserDetails. You write the bridge (UserDetailsService) that loads your entity and returns it in that standard shape.

MANDATORY You must provide a UserDetailsService to connect Spring Security to your own database. Without it, Spring cannot load your users.
✗ Without it

Spring Security does not know where your users live. It cannot verify a login because it cannot look anyone up. You get a default in-memory user with a generated password, which is useless for a real application.

✓ What we gain

Spring Security can load any user from any database by name. Authentication works against your real data, with your real roles.

Your User entity vs UserDetails

Your User entity (a JPA class) is for your application — it can have anything: address, date of birth, profile picture. UserDetails is for Spring Security — it only carries what security needs: username, password, roles, and account status. You map one to the other inside your UserDetailsService.

The keyword that represents it
KeywordWhat it means (plain English)Status
UserDetailsServiceAn interface with one method: "given a username, return a UserDetails object." You implement this to tell Spring how to find a user in your database.MANDATORY
UserDetailsAn interface describing what a security user looks like: username, password, list of roles, and four account-status flags. Your implementation must provide all of these.MANDATORY
How it connects

The AuthenticationProvider (concept 2) calls UserDetailsService to load a user, then uses PasswordEncoder (concept 5) to compare passwords. These three always work together during a login.

Core concept

Password Encoding (BCrypt)

Password encoding means turning a plain-text password into a scrambled string before storing it, using a one-way mathematical process called hashing. BCrypt is the standard hashing algorithm Spring Security recommends.

Analogy — A combination lock that forgets

You set a combination lock to 4729. From now on, to prove you know the combination you must produce 4729. But the lock never stores "4729" written on it — it only keeps a scrambled form it can check against. Even the locksmith who built it cannot tell you the combination from looking at the lock. BCrypt works the same way.

Top: the plain password is hashed before storage. Bottom: at login, the plain password is re-hashed and compared to the stored hash. The original is never stored.
Why we need it

If passwords are stored as plain text and the database is ever stolen, every user's password is immediately exposed — including their passwords for other websites, since people reuse passwords. Hashing means a stolen database reveals nothing usable.

Hashing vs Encryption — a critical difference

Encryption is reversible — a key can decrypt the message back. Hashing is one-way — there is no key and no way to reverse it. Passwords must be hashed, not encrypted. If they were encrypted, whoever holds the key can decrypt all passwords.

BCrypt also adds a salt — a random value mixed into the hash before storing. This means two users with the same password produce completely different hashes, so an attacker cannot use a pre-computed lookup table to crack them.

MANDATORY Always use a PasswordEncoder. Storing plain text passwords is a serious security vulnerability.
✗ Without it

Passwords stored in plain text. One database breach exposes every user's password immediately. This is the single most common cause of mass credential leaks.

✓ What we gain

Even if the database is stolen, the stored hashes are computationally infeasible to reverse. User passwords remain safe.

The keyword that represents it
KeywordWhat it means (plain English)Status
PasswordEncoderThe interface Spring Security uses for hashing. It has two methods: encode (hash it) and matches (compare a plain password to a stored hash).MANDATORY
BCryptPasswordEncoderThe standard implementation of PasswordEncoder. It uses the BCrypt algorithm with a built-in salt and work factor. This is what you use unless you have a special reason.MANDATORY (recommended)
How it connects

PasswordEncoder is used by the AuthenticationProvider (concept 2) when comparing a login attempt against the stored hash. UserDetailsService (concept 4) returns the stored hash; PasswordEncoder checks it.

Core concept

Authorisation & Roles

Authorisation is the second check — deciding what an authenticated user is allowed to do. A Role is a broad label that groups what a user can access (like ROLE_USER or ROLE_ADMIN). A Permission / Authority is a fine-grained specific right (like account:delete).

Analogy — Access levels in an office building

Showing your employee badge at the front door is authentication (you proved you work here). But once inside, your badge may not open the server room — that requires a different level. Authorisation is what decides which doors your badge opens.

The user is authenticated as ROLE_USER. /home and /account are allowed. /admin requires ROLE_ADMIN — access denied with a 403 Forbidden.
Why we need it

Authentication only confirms identity. Without authorisation, any logged-in user could reach any page, including the admin panel. Authorisation adds the rule layer: identity is necessary but not sufficient for access.

MANDATORY Without authorisation, any logged-in user can access everything.
✗ Without it

All logged-in users are equal. A regular customer can reach the admin panel and manage other accounts. Roles are meaningless without enforcement.

✓ What we gain

Fine-grained control: each URL can require a specific role. An admin page simply cannot be reached by a regular user, no matter what they try.

Important add-on

JWT — JSON Web Token

A JWT (JSON Web Token) is a small, self-contained digital ticket. After a user logs in, the server creates a JWT, signs it (proves it came from this server), and gives it to the client. The client sends it back with every future request. The server verifies the signature and trusts the identity inside without needing to look anything up.

Analogy — A signed concert wristband

At the entrance, staff check your ticket and give you a wristband stamped with a unique mark only they can create. For the rest of the night, any staff member can see your wristband and know you are allowed in — without calling the box office every time. If someone fakes the mark, the stamp does not match and they are turned away. That is exactly how a JWT works.

Step 1 (top): Login succeeds, server creates and signs a JWT, client stores it. Step 2 (bottom): Every future request sends the JWT; the filter verifies the signature without touching the database.

The three parts of a JWT

PartWhat it containsPlain-English purpose
HeaderAlgorithm used (e.g. HS256) and token type"This is a JWT, signed with this method."
PayloadClaims: username, roles, expiry time (sub, roles, exp)"This is who the user is and when this token expires."
SignatureA hash of Header + Payload, created with a secret key"Only the server that knows the secret could have made this."
Signing vs Encrypting — critical difference

Signing proves the token has not been tampered with (integrity). Anyone can read the payload — it is not secret. Encrypting hides the content. A standard JWT is signed, not encrypted — do not put sensitive data like passwords in the payload.

OPTIONAL Required for stateless REST APIs and microservices. Not needed for traditional session-based web apps.
✗ Without JWT (sessions)

Every server in a microservices system needs access to the session store, forcing shared state. Scaling is harder and one session store becomes a single point of failure.

✓ With JWT

Stateless: any server can verify the token without shared storage. Perfect for microservices and mobile apps where session cookies do not work.

The keyword that represents it
KeywordWhat it means (plain English)Status
OncePerRequestFilterThe base class you extend to write a JWT filter. It ensures your filter runs once per request and intercepts the token before the rest of the chain runs.OPTIONAL
jjwt (library)The common library for creating and verifying JWTs in Java. Not part of Spring itself, but the standard choice in Spring Security projects.OPTIONAL
How it connects

JWT is an alternative to session-based Authentication (concept 2). The JWT filter sits in the Filter Chain (concept 1), verifies the token, and writes the identity to the Security Context (concept 3) — the same context, just populated differently.

Core concept

SecurityFilterChain Configuration

Security configuration is where you write the rulebook: which URLs are open to everyone, which require a login, which require a specific role, and which authentication mechanism to use. All of these rules live in one place so the whole security posture of the application is visible at a glance.

Analogy — The bank's access policy document

A bank has a written policy: "The lobby is open to all. The counter is open to customers. The vault is open to managers only." This document lives in one place. Security configuration is that document for your application.

The config maps each URL to an access rule: open to all, requires login, or requires a specific role.
Why we need it

Without configuration, Spring Security locks every URL by default (which is safe but useless). Configuration is how you open some URLs to the public, protect others, and define how users prove their identity (form login, HTTP basic, or JWT).

MANDATORY You must configure which URLs are public and which are protected, or the default (everything locked) is rarely what you want.
✗ Without it

Every URL is locked by default. Even the public home page requires a login. The application is unusable without at least minimal configuration.

✓ What we gain

The full security posture of the app is visible in one class. Changing a rule is one line. Reviewing security needs no searching through controllers.

The keyword that represents it

Configuration is where everything comes together: you define the filter chain (concept 1), plug in UserDetailsService (concept 4), set the PasswordEncoder (concept 5), choose authentication type (session or JWT), and write the access rules (concept 6).

Important add-on

CSRF, CORS & Session Management

Three related but separate security concerns that beginners frequently hit when building REST APIs or front-end applications. Each one protects against a different kind of problem.

CSRF — Cross-Site Request Forgery

Analogy — Forged letter

You are logged into your bank in one browser tab. In another tab you open a malicious site. That site secretly sends a request to your bank (transfer 1000 to the attacker), using your live session cookie. Your bank sees a valid session and processes it. CSRF protection stops this by requiring a secret token that only your actual bank page knows.

✗ Without CSRF protection

Malicious pages can trigger actions on your users' behalf using their session cookies. Money transfers, password changes, or account deletions can happen silently.

✓ What we gain

Every state-changing request must carry a secret token from the legitimate page. Forged requests from other sites do not have this token and are rejected.

When is it safe to disable CSRF?

CSRF attacks only work when the browser automatically includes credentials (session cookies). If your API uses JWT tokens sent manually in a header, the browser never sends them automatically, so the attack is not possible. That is why stateless REST APIs that use JWT can safely disable CSRF. Never disable CSRF on a form-login, session-based application.

CORS — Cross-Origin Resource Sharing

Analogy — A bouncer with a guest list

Your backend at api.mybank.com will only talk to a browser page coming from www.mybank.com. A request arriving from evil.com is on the wrong guest list and is refused before it even starts. CORS lets you define exactly which origins are allowed.

Browsers block requests where the page's origin (domain, port, protocol) does not match the API's origin. This is called a cross-origin request. CORS configuration tells the browser "this API allows requests from these specific origins." Without it, your React or Angular front-end cannot call your API unless both run on the same address.

Session Management — Stateless vs Stateful

Stateful: server holds the session and the browser sends a cookie. Stateless: server holds nothing; the client sends the JWT with every request.
OPTIONAL These are configuration choices. Most beginners encounter CSRF and CORS errors first before understanding them, so it is worth knowing why they exist.
The keyword that represents it

How it connects

These settings live inside the SecurityFilterChain Configuration (concept 8). If you use JWT (concept 7) you will need to set STATELESS session policy and consider disabling CSRF. If you have a React or Angular front-end you will need CORS configuration.

Clear it up

Five common confusions

These are the five pairs beginners mix up most. Read them once and they will not trip you again.

1 · Authentication vs Authorisation
AuthenticationProves WHO you are. Happens first. Failure = 401 ("I do not know you").
AuthorisationDecides WHAT you can do. Happens after. Failure = 403 ("I know you, but no").
2 · Role vs Permission
RoleBroad label: ADMIN, USER. Spring adds ROLE_ prefix automatically.
PermissionFine-grained right: account:delete. No prefix. Used for specific actions.
3 · @Secured vs @PreAuthorize
@SecuredOlder, simpler. Only accepts role names. Cannot use complex expressions.
@PreAuthorizeModern, flexible. Accepts expressions like hasRole() and #id == principal.id.
4 · JWT signing vs encryption
SigningProves the token was not tampered with. The payload is still readable by anyone. Used for standard JWTs.
EncryptionHides the payload content. Needed only if the payload itself is secret (rare).
5 · Disable CSRF (REST) vs Enable (form login)
Disable (JWT REST)Safe: JWT is sent manually in a header, not as a cookie, so cross-site attacks are not possible.
Keep enabledRequired for any app using session cookies and browser forms. Never disable for these.
Putting it together

The whole idea, in plain words

Spring Security is a framework that places an ordered row of checkpoints (the Filter Chain) in front of your application. Every incoming request passes through this chain. The first important checkpoint is Authentication: it collects the user's credentials, loads the user from your database through a UserDetailsService, compares the password using a PasswordEncoder (BCrypt), and either confirms identity or rejects it with a 401. If identity is confirmed, the user's details are stored in the Security Context so every other part of the request can see "who is this?" without re-checking. The next checkpoint is Authorisation: it reads the role from the context and compares it against the access rules in your Security Configuration — open to all, login required, or specific role required — blocking with a 403 if the rules are not met. For stateless REST APIs and microservices, you replace the session with a JWT: a signed ticket the server issues at login and verifies on every subsequent request without remembering anything. Finally, CSRF protection stops forged requests from malicious sites, CORS controls which front-end origins can call your API, and session management lets you declare the system is stateless. Every piece exists to answer one of two questions: Who are you? And what are you allowed to do?
