How to use this guide

This is a thinking guide, not a build guide. There is no code to copy and nothing to install. The single goal is to make each idea click — what it is, why it exists, and which keyword stands for it — so that when you later build a project, every step already feels obvious.

One example runs through the whole guide: a small online shop split into two parts — a Product Service that knows about products, and an Order Service that creates orders and needs product details. The moment the Order Service needs a product's price, it has to ask the Product Service. Almost every concept here exists to make that one kind of cooperation safe, simple, and reliable.

The one cooperation every concept is here to support: one service asking another for data.

Every concept is explained the same way, so the rhythm becomes familiar: what it is (with an everyday analogy), why we need it, whether it is mandatory, what happens without it, what we gain, the keyword that represents it, and how it connects to the rest.

Vocabulary

The words you'll meet

Skim these once. Each is one plain sentence; come back whenever a term feels fuzzy.

ServiceA small program that runs on its own and does a job for others.
MicroserviceOne small service that handles just one part of a bigger system.
MonolithOne big program that does everything, all in a single piece.

Registry / DiscoveryA live directory of which service is where, found by name.
GatewayA single front door all outside requests pass through.

Loosely coupledParts that can change on their own without breaking each other.
The big idea

Microservices vs the monolith

A monolith is one big application that contains everything — products, orders, payments, users — built and run as a single piece. Microservices split that into several small services, each doing one job and running on its own.

Left: everything fused into one. Right: small pieces that connect only when they need to.
QuestionMonolithMicroservices
How many programs?One.Many small ones.
Change one partRebuild and redeploy the whole thing.Rebuild only that one service.
If one part crashesThe whole app can go down.Often only that one service is affected.
Scaling a busy partScale everything together.Scale only the busy service.
ComplexitySimple to start, harder as it grows.More moving parts from day one.
An honest answer

Are microservices mandatory for every project?

No — and that matters. Splitting one app into many services adds real complexity: more programs to run, more calls travelling over the network, and more things that can go wrong. You should only take on that cost when you actually get something back for it.

A monolith is usually better when

The project is small or new, the team is small, the idea is still changing fast, or you just want to ship quickly and keep things simple. Starting as a monolith and splitting later is a perfectly respected path.

Microservices are worth it when

The app is large, several teams work on different parts, parts must scale or deploy independently, or one part being busy or failing must not drag the rest down. Big shops, streaming, and banks fit this.

Their real purpose, in one line

Microservices exist to give each part of a system independence — independent building, deploying, and scaling, plus isolation so one part's failure does not become everyone's failure. Every concept in this guide exists to protect that independence while still letting the services cooperate.

Priorities

What matters most for a beginner

Not every concept carries equal weight at the start. Here is the honest grouping, so you know where to focus.

COREA service, Service Discovery, and service-to-service calls (Feign) — the heart of microservices. If you understand only these three, you understand the idea.
CORE+API Gateway and Database per service — important add-ons that almost every real system uses. Understand them soon after the core.
LATERConfig Server, centralized logging, and advanced testing/deployment — genuinely useful, but you can grasp the whole system without them at first.
A note on the order below

We explain the concepts in the order most courses use, which introduces the Config Server early. Keep this map in mind: for a first project the Config Server is optional — helpful to understand, but not needed to grasp the system.

1
Foundation

A Service

A service is one small program that runs on its own and answers requests. "Setting up a service" simply means bringing one such program to life and giving it a door number (a port). In our shop, the Product Service is one service; the Order Service is another.

Think of it like

Opening one small shop in a mall. Before it can sell anything, the shop must exist: it needs a unit, a door number, and the lights on. That is all "setting up a service" means.

A service opens one numbered door, listens for requests, and sends back responses.
Why we need it

Everything else — discovery, calls between services, gateways — needs at least one running service to attach to. A service is the basic building block; without one, there is nothing to connect.

MANDATORY A microservices system is, by definition, made of services. This is step zero.
✗ Without it

There is nothing. No endpoints to call, nothing to register in a directory, nothing for a gateway to route to. It is the seed everything grows from.

✓ What we gain

One independent unit that can run, be tested, and later be connected to others — without touching any other part of the system.

The keyword that represents it
KeywordWhat it means (plain English)Status
@SpringBootApplicationThe label on the one starting class of every service. It says "this is a complete, runnable application — start it." It turns a plain class into a launchable service.MANDATORY
How it connects

This is the foundation. The next ideas give a service its settings (Config Server), help it find others (Discovery), and let it call others (Feign).

2
Settings · Optional add-on

Config Server

A Config Server is one special service whose only job is to hold the settings for all the other services in a single, central place. Instead of each service keeping its own copy of shared settings, they all read from this one source.

Think of it like

A company handbook kept in one place. Instead of every employee keeping a private copy of the rules (which slowly drift out of date), everyone reads the single official copy. Update it once and everyone is current.

One central source hands the same settings to every service.
Why we need it

Many services share the same settings — the directory's address, database details, shared limits. Keeping those in one place means a change is made once, not copied into every service by hand.

OPTIONAL A beginner can fully understand microservices without it. It earns its place once several services repeat the same settings.
✗ Without it

The same setting is written inside every service. Change one shared value and you must edit it in every service and restart them all — and it is easy to miss one.

✓ What we gain

One change in one place updates everyone. Settings live in a single, trustworthy source instead of many drifting copies.

The keyword that represents it
KeywordWhat it means (plain English)Status
@EnableConfigServerThe label that turns an ordinary app into the Config Server. It says "this app's job is to hand out settings to others." Without it, the app is just an empty service.MANDATORY on the server
Worth noticing

The Config Server is a real, separate server. This matters later, because Feign (concept 5) is the opposite — it is only a client, with no server of its own.

How it connects

The Config Server only matters because other services read from it. That reading side is the very next concept.

3
Settings · Optional add-on

Client Configuration

Client configuration is the other half of the Config Server idea. A "config client" is any ordinary service that, when it starts, asks the Config Server for its settings instead of keeping them all locally.

Think of it like

The new employee who, on day one, reads the official handbook instead of relying on hearsay. The handbook is the server; the employee reading it is the client.

Each service pulls its settings from the central server as it starts up.
Why we need it

A central handbook is useless if nobody reads it. For the Config Server to be worth anything, each service must connect to it and pull its settings on startup. This is what makes "change once, applies everywhere" actually happen.

OPTIONAL It is optional in exactly the same situations as the Config Server — they are two halves of one feature.
✗ Without it

Each service keeps its own private settings, which can drift apart and disagree — one points at the old directory address, another at the new one. These silent mismatches cause failures that are hard to trace.

✓ What we gain

Every service starts with the same, current, central settings. No duplicated values and no silent drift between services.

The keyword that represents it
KeywordWhat it means (plain English)Status
spring.config.import
(a setting, not an annotation)		A single line in a service that says "before you start, fetch your configuration from the Config Server." There is no special annotation on the client side — the connection is a setting.AUTOMATIC no annotation
How it connects

Server (concept 2) and client (this concept) form one feature. With settings sorted, the next big problem is how services find each other.

4
Core concept

Service Discovery (Eureka)

Service Discovery is a live directory of services. When a service starts, it registers its name and current address with the directory. When another service wants it, it looks the name up instead of knowing the address. Eureka is Spring's name for this directory.

Think of it like

A phone directory. You do not memorise everyone's number; you search a name and get the current number. If the number changes, the directory updates — you still just search the name.

Left: hardcoded addresses break when anything moves. Right: services register, and callers ask the directory by name.
Why we need it — the port-number problem, plainly

Every running service sits at an address with a port number — Product at 8081, Order at 8082. The simplest way for the Order Service to reach the Product Service is to write that address down. That works until the address changes — and in real systems addresses change constantly: services move machines, restart on new ports, or run as several copies for load. Each time, you would have to find every place the address was written, change it, and restart. Discovery removes this: services register by name, callers ask by that name, and the directory always knows the current address. You stop remembering ports and start using names.

CORE Not strictly required for two services on one laptop, but standard practice and the concept that makes services portable and scalable.
✗ Without it

Every service hardcodes the addresses it calls. The day anything moves, restarts on a new port, or scales to several copies, those addresses break and must be hunted down by hand — failing only at the moment of the call.

✓ What we gain

Callers use names, not addresses. Services can move, restart, or run as many copies, and the directory keeps everyone findable automatically.

The keyword that represents it
KeywordWhat it means (plain English)Status
@EnableEurekaServerThe label that turns one app into the directory itself: "this app's job is to be the phone directory of services."MANDATORY on the directory
@EnableEurekaClient
@EnableDiscoveryClient		Older labels meaning "this service should register itself." On modern Spring, just including the discovery library is enough, so these are usually not needed.AUTOMATIC on a service
How it connects

Discovery lets services be found by name. The very next question is how one service actually makes the call using that name — which is Feign.

5
Core concept

Feign Client

Feign is the idea of calling another service as if it were a normal method in your own code. You describe the call once — which service, which endpoint — and the framework makes the real web request behind the scenes. In our shop, the Order Service uses Feign to ask the Product Service for a product.

Think of it like

Speed-dial on a phone. Instead of dialing a full number each time, you press one labelled button. You label the call once; pressing the button does the dialing.

Feign lives only inside the caller. The called service does not change at all.
Drop this myth right now

There is no "Feign server". Feign is only a client idea — it lives on the side that is asking. The Product Service is an ordinary service; it neither knows nor cares that the caller used Feign.

Why we need it

Services constantly need data from each other. Doing that by hand means writing the same plumbing every time: build the address, send the request, read the reply, convert it. Feign hides all of that so a remote call looks like a simple method call.

CORE IDEA Service-to-service communication is core; Feign is the simplest tool for it, so treat it as the beginner default.
✗ Without it

Every call repeats the same manual request-and-response plumbing, often with a hardcoded address (bringing back the port problem). More code, more repetition, more places to break.

✓ What we gain

One short description of the call, reused everywhere. With Discovery you call by name, the reply is converted for you, and each call becomes a single readable line.

The keyword that represents it
KeywordWhat it means (plain English)Status
@EnableFeignClientsThe label on the calling service: "look for my call descriptions and make them real." Without it, your descriptions are ignored.MANDATORY on the caller
@FeignClient(name="product-service")The label on a small interface: "this describes calls to the service named product-service." The name must match the target's registered name.MANDATORY
How it connects

Feign relies on Discovery (concept 4) to turn a name into an address. Next we step outside the services and ask how the outside world reaches them.

6
Important add-on

API Gateway

An API Gateway is a single entry point that sits in front of all your services. Every request from the outside world comes to the gateway, which then sends it to the correct service. Deciding which service a request belongs to is called routing.

Think of it like

The reception desk of an office building. Visitors do not wander to individual rooms; they go to one reception, which directs them. You hand out one address (reception), not the room number of every team.

Many callers, one door. The gateway reads the path and routes each request to the right service.
Why we need it

Without a front door, anyone outside must know the address and port of every service — fragile, and it exposes your internal layout. The gateway is also the natural single place to handle shared jobs once (security checks, request logging) instead of repeating them in every service.

CORE+ Not required to make two services talk, but standard in any real system and worth understanding early.
✗ Without it

Callers juggle many addresses. Add a service and every caller learns a new one. Shared concerns like security get rebuilt in each service, and internal ports leak to the outside.

✓ What we gain

One address for everything. Callers never see internal ports, you add or move services without changing callers, and you get one place to enforce shared rules.

The keyword that represents it
KeywordWhat it means (plain English)Status
(no enable annotation)A useful surprise: the API Gateway has no "enable" annotation. Its behaviour comes entirely from its routing settings. Beginners often hunt for an @EnableGateway — it does not exist.AUTOMATIC settings, not a label
How it connects

The gateway usually uses Discovery to route by name. With the outside-in path handled, the next concern is being able to see what is happening across all these services.

7
Optional add-on

Centralized Logging & Monitoring

Monitoring means seeing the health of each service — up or down, healthy or not. Centralized logging means gathering the messages from all services into one place, so you can follow a single request as it travels from service to service.

Think of it like

Security cameras feeding one control room. Each shop has its own camera (its own logs), but the guard watches every feed on one wall, so they can follow one person from shop to shop.

Green dots = healthy. Every service sends its logs to one place you can search.
Why we need it

In a monolith there is one log to read. In microservices a single user action can pass through the gateway, the Order Service, and the Product Service — three separate places. Without a way to join them, finding out what went wrong means jumping between windows and guessing which line belongs to which request.

OPTIONAL Strongly recommended, but you can understand the core ideas without it.
✗ Without it

No single view of health and no easy way to follow one request across services. You compare separate logs by eye, matching timestamps and guessing, and cannot quickly answer "is that service even up?"

✓ What we gain

A health check per service (up or down at a glance) and the ability to follow one request end to end across every service it touched.

The keyword that represents it
KeywordWhat it means (plain English)Status
Actuator
(a library, not an annotation)		The common tool here is "Actuator," added as a library rather than switched on by a label. It exposes simple health and status information about a service. No annotation to memorise — the behaviour comes from including the library.AUTOMATIC library
How it connects

Monitoring watches over everything we have connected so far. The next concept keeps each service independent at the data level.

8
Important rule

Database per Service

Database per service means each service owns and manages its own database, and no other service reaches directly into it. If one needs another's data, it asks through the API (the Feign idea) — it never reads the other's database directly.

Think of it like

Each shop in the mall has its own locked stockroom. If one shop needs an item from another, it asks at the counter — it does not walk into the other shop's stockroom and take it.

Each service owns its own data. Crossing into another service's database directly is the rule this concept forbids.
Why we need it

The whole point of microservices is independence. If two services share one database, they are secretly joined: neither can change its data structure freely, and one database problem hits both. Separate databases keep services truly independent.

CORE RULE The core data rule of microservices. Understand it from the start.
✗ Without it

If two services share a database and read each other's tables, one team cannot change its data without breaking the other. They become glued together — a monolith with extra network calls, the downsides of both designs.

✓ What we gain

Each service grows its own data freely, can even use a different kind of database, and one service's data problem cannot corrupt another. Data is shared only through clear APIs.

The keyword that represents it
KeywordWhat it means (plain English)Status
@EntityThe label on a class meaning "objects of this class are stored as rows in this service's own table." It marks the data a service owns.MANDATORY for stored data
@IdThe label on the one field that uniquely identifies each stored item (its key).MANDATORY for stored data

There is no annotation for "database per service" itself — it is a rule you follow, not a label you write.

How it connects

Owning data privately is the last piece that keeps services independent. The final concept is how you verify and run them all together.

9
Running it

Testing & Deployment

Testing means checking that each service works on its own and that they work together. Deployment means running the whole system — and crucially, starting the services in the right order so they can find each other.

Think of it like

Opening the mall in the morning: switch on the building directory and reception first, then open the individual shops. Open a shop before the directory is running and customers cannot be guided to it.

Start order: the directory first, then the services that register in it, then the front door.
Why we need it

Microservices depend on each other at startup. If a service starts before the directory is ready, it cannot register or be found, and calls fail with confusing errors that have nothing to do with the code. Knowing the right order, and verifying each layer, makes the system predictable.

MANDATORY Understanding startup order. OPTIONAL Deeper automated testing and advanced deployment.
✗ Without it

Start a caller before the directory and you get "no instances available" — not a code bug, just bad order. Without a verification habit, you also cannot tell which service in the chain actually failed.

✓ What we gain

A reliable, repeatable way to bring the system up and confirm it works end to end, so problems are obvious and isolated to one service.

The keyword that represents it
KeywordWhat it means (plain English)Status
@SpringBootTestThe label on a test meaning "start the service the way it really runs, so I can test it realistically." It represents the idea of automated verification.OPTIONAL

The startup-order idea itself has no annotation — it is an operating habit (directory first, then services, then the gateway).

How it connects

This ties everything together: independent services, connected through discovery and Feign, fronted by a gateway, watched by monitoring, each owning its data — brought up in a sensible order and verified.

The three things beginners most often get wrong

1) The API Gateway has no enable annotation — it is pure configuration. 2) On modern Spring, a service registers with the directory automatically from its library, so you usually do not write @EnableEurekaClient. 3) The config client needs no annotation either — just a setting. In short: not every concept has an annotation. Some are settings, some are libraries, and some are simply rules you follow.

Putting it together

The whole idea, in plain words

A microservices system is a set of small, independent programs (services), each doing one job and owning its own data. They may read shared settings from one central place (Config Server). They find each other through a live directory by name, not by memorised addresses (Service Discovery) — which is what ends the "remembering port numbers" headache. One service calls another by that name as if it were a local method (Feign, a client-only idea with no server of its own). The outside world reaches all of them through a single front door that routes each request to the right place (API Gateway). You can see their health and follow one request across them (logging and monitoring). And you run them in a sensible order — directory first, then services, then the front door — verifying as you go. Every single piece exists for one reason: to let independent services cooperate without becoming secretly glued together.

You are now ready to build

That is the complete theory. The next stage is the hands-on build — creating the services, adding dependencies, writing the settings and code, and testing each endpoint. With the understanding from this document, every step there will already make sense.
