WHAT IS IT?

What Is an API Gateway? (Very Simple)

🏨 Think of a Hotel

A hotel has 10 departments — restaurant, gym, pool, spa, room service, laundry, etc.

Without a reception desk: every guest must memorise the direct phone number of every department. If the restaurant moves to a new floor, every guest must be told the new number. If the spa temporarily closes, guests still call it and get no answer.

The reception desk (API Gateway): guests call ONE number. The receptionist says "you want the restaurant? Let me connect you." Guests never know or care about internal department numbers.

In your microservices system: the "guests" are your mobile app, browser, and Postman. The "departments" are product-service (:8081), order-service (:8082), auth-service (:8085). The API Gateway is the reception desk on port :8080.

WHY NEED IT?

Why Do We Need API Gateway? (5 Real Problems)

Problem 1: Client Must Know Every Port

Without Gateway: Your mobile app hardcodes :8081 for products and :8082 for orders. You add a payment service on :8083. Now you must update and redeploy the mobile app — and push an update to 1 million phones. That takes weeks.

With Gateway: With Gateway: clients call :8080 forever. You add 10 more services behind the Gateway without touching any client app.
Problem 2: Authentication Code Is Repeated

Without Gateway: Without Gateway, every service (product, order, auth, payment) must check JWT tokens itself. You write the same JWT validation code in 4 places. When the JWT secret key changes, you must update and redeploy all 4 services.

With Gateway: With Gateway: JWT validation in the Gateway filter once. All services behind it trust all requests.
Problem 3: No Central Logging

Without Gateway: A customer reports: 'My order is missing.' Their request touched auth-service, product-service, and order-service. Logs are in 3 different files on 3 different servers. Finding the root cause takes hours.

With Gateway: With Gateway: every request is logged in one place — URL, response code, time taken — before anything else.
Problem 4: Anyone Can Overload Your Services

Without Gateway: A hacker sends 100,000 requests per second to GET /api/products. Your product-service runs out of memory and crashes. All users get errors.

With Gateway: With Gateway: rate limiter allows 100 requests per second per IP. Everything above is rejected before reaching the service.
Problem 5: CORS Configuration Duplicated

Without Gateway: Your browser app needs CORS headers on every response. Without Gateway, every service adds its own CORS config. A new allowed origin means updating 5 services.

With Gateway: With Gateway: CORS configured once. All services benefit automatically.
WHEN USE / NOT USE

When to Use / When NOT to Use Gateway

✅ Use Gateway When...

  • You have 2 or more microservices that outside apps need to call
  • You are building a mobile app or website that should not know internal ports
  • You need JWT authentication checked in one place
  • You need rate limiting to protect your services
  • You want all request logs in one place
  • You are deploying to production or cloud
  • Different client types need different responses (mobile vs web)
  • Your team has different developers owning different services

❌ Skip Gateway When...

  • You are still learning Phase 1–4 — understand basics first
  • You have only 1 microservice — Gateway adds pointless complexity
  • Services talk to each other internally — Feign handles that, not Gateway
  • You are building a simple monolith — does not need Gateway at all
  • Your team has 1–2 developers — overhead is not worth it yet
  • APIs are only called by other internal services, never by a browser or phone
  • You are just testing an idea quickly — focus on business logic first
Key: You built Phases 1–6 without a Gateway and everything worked fine. The Gateway was added in Phase 7 because by then you had multiple services, external clients, and JWT security needs. Do not add it before you feel the pain of those problems.

Dependency 1: spring-cloud-starter-gateway

spring-cloud-starter-gateway
pom.xml → <dependencies>
What it is
This is the main Gateway engine. When you add this to pom.xml, your Spring Boot app becomes an API Gateway. It includes: the routing system (reads routes from application.properties), WebFlux (a reactive web server using Netty instead of Tomcat), and Spring Cloud LoadBalancer (the part that resolves lb://product-service to a real address via Eureka).
Simple words
Think of this as buying the reception desk for your hotel. Without this, your app is just an empty room. With this, it can receive requests and route them to the right department (service).
Why you need it
Without this, your project has no routing capability at all. It is just a plain empty Spring Boot application. No routes are registered. Every request returns 404 Not Found.
Mandatory?
YES — Required This IS the API Gateway. You cannot have a Gateway project without this dependency. It is the entire purpose of this project.
If you remove it
The project compiles but the Gateway does nothing. application.properties routes are ignored. Every request to port 8080 returns 404. The app is just an empty Spring Boot application.
When to use / not use
Add it to the api-gateway project only. Never add it to product-service, order-service, auth-service, or any other microservice. Those services are the destinations, not the router. Only the router needs the routing engine.
Example error if missing
You start the project, call GET http://localhost:8080/api/products. Response: 404 Not Found — because there is no routing engine to process the request.

Dependency 2: spring-cloud-starter-netflix-eureka-client

spring-cloud-starter-netflix-eureka-client
pom.xml → <dependencies>
What it is
This makes the Gateway a Eureka client. It does two things: (1) registers the Gateway itself into Eureka so other services know the Gateway exists, and (2) allows the Gateway to ask Eureka for the current address of any service when it sees lb://product-service in a route.
Simple words
This is like giving the receptionist access to the hotel's internal phone directory. Without the directory, the receptionist cannot forward your call — they don't know the room number of any department. With it, they look up 'product-service' and find its current phone number (address).
Why you need it
When a route says uri=lb://product-service, the Gateway must look up what address product-service is currently running on. This dependency provides that lookup ability by connecting to Eureka Server.
Mandatory?
YES — if using lb:// URIs   OPTIONAL — if hardcoding all URLs In practice: always add it. Using lb:// is the correct approach.
If you remove it
Routes with uri=lb://product-service throw an error: Unable to find instance for product-service. Is the configured service id correct? The Gateway cannot resolve the service name to an address. You would have to replace every lb:// with a hardcoded URL like http://localhost:8081.
When to use / not use
Add it whenever you have Eureka in your system (Phase 5 onwards). If you are in an early learning phase without Eureka and use hardcoded URLs, you can skip it. But for any real production system, always use Eureka + this dependency.
Real example of what this enables
You start product-service on port 8081. It registers with Eureka as 'product-service'. You then start a second instance on port 8091. It also registers as 'product-service'. Now the Gateway has TWO addresses for product-service and load-balances between them automatically. This dependency makes all of that possible.

Dependency 3: spring-boot-starter-test

spring-boot-starter-test
pom.xml → <dependencies> with scope=test
What it is
Testing libraries: JUnit 5 (for writing test methods), Mockito (for mocking dependencies in tests), AssertJ (for readable assertions). Added automatically by Spring Initializr.
Simple words
This lets you write test files like ApiGatewayApplicationTests.java that verify your app works correctly.
Why it has scope=test
The <scope>test</scope> means these libraries are only included during testing. They are NOT included in the final JAR that runs in production. This keeps the production JAR smaller.
Mandatory?
OPTIONAL You can delete it if you are not writing tests. The Gateway runs fine without it. But it is good practice to keep it.
If you remove it
The Gateway still works completely. You just cannot write automated tests. No runtime effect.
When to change
Never change this during learning. Leave it as Spring Initializr generated it.
What scope=test means
Your final api-gateway.jar file does NOT contain JUnit or Mockito libraries. They are only used when you run mvn test. This makes your production JAR smaller and cleaner.

dependencyManagement Block — The Version Controller

spring-cloud-dependencies (BOM Block)
pom.xml → <dependencyManagement>
What it is
A BOM (Bill of Materials) is a list of pre-tested, compatible library versions. When you write ${spring-cloud.version} as the version and add this BOM block, Maven automatically uses the correct version for every Spring Cloud library (Gateway, Eureka Client, LoadBalancer) without you specifying them individually.
Simple words
Imagine buying a car. Instead of individually choosing which tyres, engine parts, and electronics are compatible with each other, you buy a 'car package' where a professional already figured out which parts work together. The BOM block is that package — it says: 'Spring Cloud 2023.0.0 comes with these exact compatible library versions.'
Why you need it
Without this block, Maven picks the latest version of each Spring Cloud library independently. Gateway v4.0 might be incompatible with Eureka Client v4.1. You get cryptic startup errors or ClassNotFoundExceptions. The BOM ensures all libraries are tested together and known to be compatible.
Mandatory?
YES — Required whenever you use ANY Spring Cloud dependency. Without it, version conflicts cause hard-to-debug startup errors.
If you remove it
Maven picks random/latest versions for Gateway, Eureka Client, and LoadBalancer. They may be incompatible. You get errors like: ClassNotFoundException: EurekaInstanceConfigBean or NoSuchMethodError: ReactiveLoadBalancerClientFilter. Very hard to debug.
When to change the version
Change spring-cloud.version when upgrading Spring Boot. The version must match: Spring Boot 3.2.x → Spring Cloud 2023.0.x. Never mix versions across major releases.

STEP 3: MAIN CLASS

Step 3 — Main Class: Only One Annotation Needed

ApiGatewayApplication.java — The Full FileJAVA
package com.gateway;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class ApiGatewayApplication {
    public static void main(String[] args) {
        SpringApplication.run(ApiGatewayApplication.class, args);
    }
}
@SpringBootApplication
ApiGatewayApplication.java — Line above the class
What it does
One annotation that secretly combines three annotations: @Configuration (this class can define Spring beans), @EnableAutoConfiguration (Spring Boot reads what is in pom.xml and automatically sets up Gateway routes, Eureka client, etc.), @ComponentScan (scans the package for @Component, @Service, @GlobalFilter classes you wrote).
Simple words
This annotation is like a master switch. When Spring Boot starts, it sees this and says: 'OK, time to set up everything.' It reads your pom.xml, sees spring-cloud-starter-gateway, and automatically creates the routing engine. It reads application.properties and loads all your routes. Without it, nothing happens.
Why it is here
Every Spring Boot application must have exactly one class with this annotation. It is the entry point. SpringApplication.run() tells Spring Boot to start the application using this class as the root.
Mandatory?
YES — Required Without it, Spring Boot does not start. The application exits immediately. The Gateway does nothing.
If you remove it
The main() method still runs but Spring Boot's auto-configuration does not happen. No Netty server starts. No routes are loaded. No Eureka client registers. The program starts and immediately exits.
When to change / what not to add
Never change it. This annotation stays exactly as generated. Do NOT add these annotations — they are wrong for Gateway:

@EnableDiscoveryClient — not needed in Spring Boot 3 (auto-configured)
@EnableFeignClients — Gateway does not use Feign
@EnableEurekaServer — turns your Gateway into a registry server (WRONG)
@EnableConfigServer — turns your Gateway into a Config Server (WRONG)
What happens inside when this runs
1. JVM starts. 2. Spring Boot reads pom.xml classpath — finds gateway jar. 3. Auto-configures routing engine. 4. Reads application.properties — loads your routes. 5. Reads eureka.client.service-url.defaultZone — registers with Eureka. 6. Starts Netty server on port 8080. 7. Prints: Started ApiGatewayApplication in X seconds.

→ server.port

server.port=8080 — In Deep Detail

server.port=8080
application.properties — Line 1
What it does
Tells the Gateway which port to listen on. After this is set, the Gateway starts a Netty server on port 8080 and waits for incoming requests. Every client — your mobile app, browser, Postman — sends all requests to this port.
Simple words
Think of this as the hotel's main telephone number. You print this on your business card. Everyone calls this number. The hotel (Gateway) picks up and routes the call internally. If you change this number, you must tell every customer.
Why 8080 specifically?
8080 is the industry convention for HTTP in development (production uses 80 for HTTP and 443 for HTTPS). Your other services use 8081, 8082, 8085 — so 8080 is free and makes logical sense as the front door.
Mandatory?
YES Well, not strictly — if you remove it, Spring Boot defaults to port 8080 anyway. But you should always write it explicitly so it is visible and obvious.
If you remove this line
Gateway still starts on port 8080 (Spring Boot default). No visible difference. However, best practice is to always be explicit about which port your service uses. If you set it to a different value and remove the line, it goes back to 8080.
When to change it
Change if: 8080 is already occupied by another app on your computer, you want to run two Gateway instances on the same machine, or you are deploying to a cloud server that assigns a specific port. In Docker, this is overridden by the compose port mapping -p 9090:8080.
Practical example
If you set server.port=9090, all your Postman requests change:
Before: http://localhost:8080/api/products
After: http://localhost:9090/api/products
Your clients (mobile app, browser) must also be updated to call 9090.
→ spring.application.name

spring.application.name=api-gateway — In Deep Detail

spring.application.name=api-gateway
application.properties — Line 2
What it does
Gives this application a name. This name is used in: (1) Eureka registration — the Gateway shows up as 'API-GATEWAY' in the Eureka dashboard, (2) Log files — every log line shows the application name so you know which service printed it, (3) Spring Boot Admin / monitoring tools — identifies this service in the monitoring dashboard.
Simple words
This is like putting a name tag on the receptionist: 'Hi, I am the API Gateway.' When Eureka keeps a list of all running services, it lists this service under this name.
Why 'api-gateway'?
It is descriptive. When you look at the Eureka dashboard at http://localhost:8761, you see a list of services. This name tells you exactly which one is the Gateway. You could name it 'gateway', 'front-door', or anything — but 'api-gateway' is the industry convention.
Mandatory?
OPTIONAL The Gateway works without it. But without it, the service shows as "unknown" in Eureka and logs. Every Spring Boot service should have a name — it is a best practice, not a rule.
If you remove this line
Gateway still works for routing. But: in the Eureka dashboard it shows as 'UNKNOWN'. Log messages have no app name (hard to filter in Kibana/Splunk). Monitoring tools cannot identify this service.
When to change it
Keep it as 'api-gateway'. Only change if you have multiple Gateway instances with different purposes, like 'api-gateway-internal' and 'api-gateway-external'. The name must be unique per service type.
What you see in Eureka when this is set
Open http://localhost:8761. You see:
API-GATEWAY   1 instance   localhost:api-gateway:8080   UP
If you removed this line, you would see:
UNKNOWN   1 instance   ...   UP
→ eureka.client.service-url

eureka.client.service-url.defaultZone — In Deep Detail

eureka.client.service-url.defaultZone=http://localhost:8761/eureka/
application.properties — Line 3
What it does
Tells the Gateway WHERE the Eureka Server is running. The Gateway uses this address to: (1) Register itself — sends its own address to Eureka on startup, (2) Look up other services — when a route has uri=lb://product-service, the Gateway calls this Eureka URL and asks: where is product-service right now?
Simple words
This is the address of the hotel's internal phone directory. Without this, the receptionist has no directory to look up department numbers. They cannot forward any calls.
Why this exact URL format?
http:// = the protocol. localhost = Eureka is running on the same machine. :8761 = Eureka's port (industry standard). /eureka/ = the path that Eureka's REST API is on. All three parts must be exactly correct.
Mandatory?
YES — if you use lb:// URIs Without this, lb://product-service cannot be resolved. Every request returns 503 Service Unavailable. Only optional if all routes use hardcoded URLs (not recommended).
If you remove this line
All routes with lb:// stop working. You get error on startup: Cannot execute request on any known server. Then every request throws: Unable to find instance for product-service. The Gateway cannot find any service.
When to change it
Change localhost to the Eureka server's IP in production: http://10.0.1.5:8761/eureka/. In Docker Compose, change localhost to the Eureka service name: http://eureka-server:8761/eureka/ — because in Docker, localhost means the container itself, not Eureka.
What happens internally when Gateway starts
1. Gateway reads this URL. 2. Gateway sends HTTP POST to http://localhost:8761/eureka/apps/API-GATEWAY with its own host, port, and health info. 3. Eureka stores this. 4. When any route is called with lb://product-service, Gateway sends HTTP GET to http://localhost:8761/eureka/apps/PRODUCT-SERVICE and gets back a list of instances.
→ routes[0].id

routes[0].id — In Deep Detail

Remember: Every route is defined with an index number in square brackets: routes[0] for the first route, routes[1] for the second, routes[2] for the third. Each route needs exactly three lines: id, uri, and predicates[0].
spring.cloud.gateway.routes[0].id=product-service-route
application.properties — Route 1, Part 1 of 3
What it does
Sets a unique name for this route. The name product-service-route appears in: (1) Gateway log files — when a request is routed, the log prints which route matched, (2) Metrics and monitoring — you can count how many requests used each route, (3) Error messages — if a route fails, the error says which route caused the problem.
Simple words
This is like naming a rule. Instead of 'Rule 1', you call it 'product-service-route' so everyone knows what this rule does. When something goes wrong, the logs say 'product-service-route failed' instead of 'some route failed'.
Why this naming convention?
The convention is {service-name}-route. Using the service name makes it instantly obvious which service this route is for. When you have 10 routes, meaningful names save hours of debugging.
Mandatory?
YES — Required Every route must have an id. If you remove this line, the Gateway fails to start with: Route must have an id.
If you remove this line
Gateway startup fails immediately: Bean instantiation via constructor failed: Route must have a non-null id. No routes are registered. All requests return 404.
When to change / rules to follow
1. Every route id must be unique. Two routes with the same id — the second one silently overwrites the first. 2. Use descriptive names: product-read-route, product-write-route if you split read/write. 3. The [0] index must be sequential — never skip numbers or repeat them.
What you see in logs with this id set
Request comes in: GET /api/products/1
Gateway log: Matched route: product-service-route
If something goes wrong: Error in route product-service-route: Connection refused
Without an id: Error in route a3f2b1c0-...-uuid: ... — much harder to read.
→ routes[0].uri

routes[0].uri=lb://product-service — In Deep Detail

spring.cloud.gateway.routes[0].uri=lb://product-service
application.properties — Route 1, Part 2 of 3 — THE MOST IMPORTANT LINE
What it does
Tells the Gateway WHERE to forward the request when this route matches. lb:// = load balanced (use Eureka to find the address). product-service = the service name to look up in Eureka. This must EXACTLY match the spring.application.name in product-service's application.properties.
Simple words
This line answers: where should I forward this request? lb://product-service means: ask the phone directory (Eureka) for 'product-service', pick one of the available numbers, and forward the call to that number. You do not hardcode a specific phone number — you let the directory give you the current one.
Why lb:// instead of http://localhost:8081?
lb:// solves the hardcoded URL problem (Phase 4). With http://localhost:8081: if product-service moves to a new server, the Gateway breaks. If you start 3 instances on ports 8081, 8091, 8092, only 8081 gets traffic — the others are wasted. If product-service crashes and restarts on a different port, the Gateway still calls the old dead port. With lb://product-service: Eureka gives the current live addresses automatically.
Mandatory?
YES — Required Every route must have a uri. Without it, the Gateway does not know where to send matching requests. Startup fails: URI must be set.
If you remove this line
Gateway fails to start: URI is required for route configuration.
When to use lb:// vs http://
URI FormatWhen to UseLoad Balancing?Needs Eureka?
lb://product-serviceMicroservices with Eureka — recommendedYES — automaticYES
http://localhost:8081Dev/testing without EurekaNO — one instanceNO
https://api.stripe.comExternal APIs not in EurekaNONO
What happens step by step when this line is used
1. Request comes: GET /api/products/1
2. Predicate matches (Path=/api/products/**)
3. Gateway sees lb://product-service
4. Spring Cloud LoadBalancer asks Eureka: what instances of PRODUCT-SERVICE are up right now?
5. Eureka returns: [{localhost:8081}, {localhost:8091}]
6. LoadBalancer picks one: localhost:8081 (round-robin)
7. URL built: http://localhost:8081/api/products/1
8. Request forwarded. Response returned to client.
→ routes[0].predicates

routes[0].predicates[0]=Path — In Deep Detail

spring.cloud.gateway.routes[0].predicates[0]=Path=/api/products/**
application.properties — Route 1, Part 3 of 3
What it does
A predicate is a condition that must be TRUE for this route to apply. Path=/api/products/** means: only use this route if the request URL starts with /api/products/. The ** is a wildcard that matches anything after the prefix — so /api/products, /api/products/1, /api/products/search?q=phone all match.
Simple words
This line answers: when should I use this route? Think of it as the sorting label at the post office: envelopes that say 'api/products' in the address go into the product-service bin. Envelopes that say 'api/orders' go into a different bin.
Why this is critical
Without predicates, the route would match EVERY request. Whether you call /api/products or /api/orders or /auth/login, all would go to product-service. Predicates are what makes each route selective — each route only handles what it is supposed to handle.
Mandatory?
YES — At least one predicate required Without predicates, a route matches nothing (or everything, depending on configuration). Best practice: always have at least one Path predicate.
If you remove this line
The route has no condition. Depending on Gateway version, it either: (1) matches ALL requests — every request goes to product-service regardless of URL, or (2) throws a configuration error at startup. Neither is what you want.
When to change the pattern
Change the path to match your service's URL structure. If your product API is at /products/v2/**, write that. If your service only handles one endpoint, write the exact path: /api/products/{id}. The pattern must match exactly what your service controller expects.

PREDICATES

All Predicate Types — When and How to Use Each

A predicate is a condition on the incoming request. If ALL predicates on a route match, that route is used. You can combine multiple predicates by adding predicates[0], predicates[1], predicates[2]...

Path=/api/products/** URL Pattern Matching

Matches based on the URL path. Most used predicate.

Example matches: GET /api/products → ✅ GET /api/products/1 → ✅ GET /api/orders → ❌

Example: Path=/api/products/**PROPERTIES
routes[0].predicates[0]=Path=/api/products/**
# Use when: routing by URL structure (almost always)
# Not useful when: you route by something other than URL (rare)

Method=GET HTTP Method Matching

Matches based on HTTP method. Combine with Path for fine-grained routing.

Example matches: GET request → ✅ POST request → ❌ DELETE request → ❌

Example: Method=GETPROPERTIES
routes[0].predicates[0]=Path=/api/products/**
routes[0].predicates[1]=Method=GET
# This route only handles GET /api/products/**
# POST /api/products does not match — needs a separate route

Header=Authorization, Bearer.* Request Header Matching

Matches if the request has a header whose value matches a regex.

Example matches: Header 'Authorization: Bearer eyJ...' → ✅ No header → ❌

Example: Header=Authorization, Bearer.*PROPERTIES
routes[0].predicates[0]=Path=/api/products/**
routes[0].predicates[1]=Header=Authorization, Bearer.*
# Route only applies if request has a valid Bearer token
# Requests without auth header do not match this route

Query=category, electronics Query Parameter Matching

Matches if the URL has a specific query parameter (optionally with a value regex).

Example matches: GET /api/products?category=electronics → ✅ GET /api/products?category=shoes → ❌

Example: Query=category, electronicsPROPERTIES
routes[0].predicates[0]=Path=/api/products/**
routes[0].predicates[1]=Query=category, electronics
# Route electronics queries to a specialised service
# All other categories go through a different route

After=2025-01-01T00:00:00+05:30[Asia/Kolkata] Time-Based Matching

This route is only active AFTER the specified date and time. Before that, requests fall through to the next matching route.

Example matches: Request on Dec 31 2024 → ❌ Request on Jan 1 2025 → ✅

Example: After=2025-01-01T00:00:00+05:30[Asia/Kolkata]PROPERTIES
routes[0].predicates[0]=Path=/api/new-feature/**
routes[0].predicates[1]=After=2025-01-01T00:00:00+05:30[Asia/Kolkata]
# Feature goes live automatically at midnight Jan 1
# No code deployment or restart needed
FILTERS

All Filter Types — When and How to Use Each

Filters modify the request BEFORE forwarding it to the service, or modify the response BEFORE returning it to the client. They run after the predicate matches.

AddRequestHeader=X-Source, api-gateway Request Header Filter

Adds a header to the request before forwarding it. The service receives this header as if the client sent it.

What it does: Client sends nothing. Product-service receives X-Source: api-gateway automatically.

Example: AddRequestHeader=X-Source, api-gatewayPROPERTIES
routes[0].filters[0]=AddRequestHeader=X-Source, api-gateway
# Product-service can log X-Source to know all traffic came via Gateway
# Useful for: request tracing, identifying request source

AddResponseHeader=X-Served-By, product Response Header Filter

Adds a header to the response before returning it to the client.

What it does: Client receives extra header X-Served-By: product in the response.

Example: AddResponseHeader=X-Served-By, productPROPERTIES
routes[0].filters[0]=AddResponseHeader=X-Served-By, product-service
# Client can see which service handled their request
# Useful for: debugging, identifying which instance responded

StripPrefix=1 Path Strip Filter

Removes N segments from the beginning of the URL path before forwarding. Client calls /api/products/1 → after StripPrefix=1 → service receives /products/1.

What it does: Client: /v1/api/products/1 → StripPrefix=1 → Service: /api/products/1

Example: StripPrefix=1PROPERTIES
routes[0].predicates[0]=Path=/v1/**
routes[0].filters[0]=StripPrefix=1
# Client: GET /v1/api/products/1
# Service receives: GET /api/products/1
# The "/v1" prefix is stripped

RewritePath=/old/(?<seg>.*), /new/${seg} Path Rewrite Filter

Rewrites the URL path using a regex pattern. The captured group (?<seg>.*) is reused in the replacement.

What it does: Client: /v1/products/1 → Rewrite → Service: /api/products/1

Example: RewritePath=/old/(?<seg>.*), /new/${seg}PROPERTIES
routes[0].predicates[0]=Path=/v1/products/**
routes[0].filters[0]=RewritePath=/v1/products/(?<seg>.*), /api/products/${seg}
# Client calls old URL: /v1/products/1
# Service receives new URL: /api/products/1
# Used for API versioning migrations

CircuitBreaker=name=productCB,fallbackUri=forward:/fallback Circuit Breaker Filter

If product-service fails repeatedly (connection errors), the circuit 'opens' and requests immediately get a fallback response without trying the broken service.

What it does: Product-service down → client gets /fallback response instead of error

Example: CircuitBreaker=name=productCB,fallbackUri=forward:/fallbackPROPERTIES
routes[0].filters[0]=CircuitBreaker=name=productCB,fallbackUri=forward:/fallback
# Add this @GetMapping("/fallback") in a Gateway controller:
# return "Product service is temporarily unavailable";
# Used when: you want graceful degradation instead of hard errors
REQUEST FLOW

What Happens Step by Step — Complete Request Flow

Let us trace GET http://localhost:8080/api/products/1 through the entire Gateway from start to finish.

1
Client sends request to Gateway

The client (Postman, browser, mobile app) sends: GET http://localhost:8080/api/products/1. The client knows nothing about port 8081. It only knows port 8080.

2
Netty server receives the request

The Gateway uses Netty (a non-blocking server, different from Tomcat). Netty receives the request on port 8080 and passes it to the Gateway pipeline.

3
GlobalFilters run first

If you have a GlobalFilter (like the JWT filter from Phase 8), it runs on EVERY request. It checks for Authorization: Bearer token. If missing or invalid → 401 returned immediately. If valid → continues to next step.

4
Gateway checks routes in order — routes[0] first

Is /api/products/1 matched by Path=/api/products/**? YES. Route selected: product-service-route. Gateway stops checking other routes.

5
Route filters run (pre-request)

Any filters[N] defined for this route run now. Example: AddRequestHeader=X-Source, api-gateway adds the header to the forwarded request.

6
lb:// resolved via Eureka

Gateway calls LoadBalancer: where is PRODUCT-SERVICE? LoadBalancer queries local Eureka cache. Returns: [localhost:8081, localhost:8091]. Picks: localhost:8081 (round-robin).

7
Request forwarded to product-service

Final URL: http://localhost:8081/api/products/1. All original headers are preserved. Any added headers are included.

8
product-service processes the request

ProductController.getProductById(1) runs. ProductService queries MySQL. Returns ProductDTO as JSON.

9
Response travels back through Gateway

Response goes back through the Gateway. Response filters run (e.g., AddResponseHeader). Any response transformations happen here.

10
Client receives the response

HTTP 200 OK with product JSON. The client received a response from port 8080. The client has no idea that port 8081 was involved.

ERRORS

Common Errors — Exact Message + Cause + Fix

Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway

Why this happens: You added spring-boot-starter-web to pom.xml. Gateway uses WebFlux (Netty). Spring Web uses Tomcat. They cannot run together.

How to fix it: Remove spring-boot-starter-web from pom.xml. Save, reimport Maven. Restart the Gateway.

Unable to find instance for product-service

Why this happens: (1) Product-service is not running. (2) Product-service is running but not yet registered in Eureka (takes ~30 seconds). (3) spring.application.name in product-service does not match what you wrote after lb://. Example: product-service has spring.application.name=products but Gateway says lb://product-service.

How to fix it: 1. Start product-service. 2. Wait 30 seconds. Open http://localhost:8761 — confirm PRODUCT-SERVICE shows UP. 3. Check the name matches exactly: spring.application.name=product-service ↔ lb://product-service.

404 Not Found — No route found

Why this happens: The request URL does not match any predicate in any route. Example: you call GET /products/1 but your predicate is Path=/api/products/**. Missing the /api/ prefix.

How to fix it: Check your URL. It must start with exactly what the predicate expects. Add routes[N].predicates[0]=Path=/** as the LAST route to catch all unmatched requests for debugging.

Cannot execute request on any known server

Why this happens: Gateway cannot connect to Eureka Server. Either: Eureka is not running, or the eureka.client.service-url.defaultZone URL is wrong.

How to fix it: 1. Start Eureka Server FIRST before starting Gateway. 2. Verify the URL: open http://localhost:8761 in browser — you should see the Eureka dashboard. 3. If in Docker, change localhost to eureka-server.

Route must have a non-null id

Why this happens: One of your routes in application.properties is missing the .id= line, or has a typo in the property name.

How to fix it: Add the id line: spring.cloud.gateway.routes[N].id=any-unique-name. Check all routes have id, uri, and predicates.

Routes overwrite each other silently

Why this happens: Two routes have the same index: two lines start with routes[0]. The second one overwrites the first.

How to fix it: Use sequential unique indices: routes[0], routes[1], routes[2]. Never repeat an index number.

INTERVIEW Q&A

10 Interview Questions with Complete Answers

10 Interview Questions — API Gateway
Q: What is an API Gateway? Explain in simple terms.
A: An API Gateway is a single entry point for all client requests. Instead of clients knowing multiple service ports (8081 for products, 8082 for orders), all requests go to one port (8080). The Gateway reads the URL and routes to the correct service. It also handles authentication, logging, and rate limiting in one place.
Q: Why can't you add spring-boot-starter-web to the Gateway project?
A: Gateway uses Spring WebFlux (reactive) which runs on Netty server. spring-boot-starter-web uses Spring MVC which runs on Tomcat. They cannot run together. Adding both causes startup failure: 'Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway'.
Q: What does lb://product-service mean?
A: lb:// stands for 'load balanced'. Instead of a hardcoded URL, the Gateway asks Eureka: where is product-service right now? Eureka returns all current live instances. The Gateway picks one using round-robin and forwards the request. If product-service moves ports, scales to 5 instances, or crashes — the Gateway adapts automatically without any code change.
Q: What are the three required parts of every Gateway route?
A: id (unique name for the route — used in logs and metrics), uri (where to forward matching requests — lb://service-name or http://host:port), predicates (conditions that must match — at least one, usually Path=). Missing any of these causes a startup error.
Q: What is a predicate and why is it important?
A: A predicate is a condition. Only if the condition is true does the route apply. Without predicates, a route would match ALL requests — every URL would go to the same service regardless of what it is. Predicates (especially Path) ensure product requests go to product-service, order requests go to order-service, etc.
Q: What is a GlobalFilter vs a route filter?
A: A GlobalFilter runs on EVERY request through the Gateway, regardless of which route matches. Used for JWT validation, logging, rate limiting. A route filter (filters[0], filters[1] in properties) runs only for requests matching its specific route. Used for header manipulation, path rewriting, circuit breaking on individual services.
Q: What happens if no route matches an incoming request?
A: Gateway returns 404 Not Found with message 'No route found for URI'. This is correct — the Gateway only forwards requests it has explicit rules for. To handle unknown routes, add a catch-all route with Path=/** as the VERY LAST route — it matches anything that didn't match earlier routes.
Q: What is the route matching order?
A: Routes are checked in index order: routes[0] first, then routes[1], routes[2], etc. The FIRST matching route is used. Other routes are not checked. This means more specific routes must come before general routes. A catch-all Path=/** must always be LAST, otherwise it catches everything and no other route gets a chance.
Q: What error occurs when routes[0] is defined twice?
A: No error at startup — the second definition silently overwrites the first. The first route disappears. Requests that were supposed to use the first route get 404 (no route found). Always use unique sequential indices: routes[0], routes[1], routes[2]. Never repeat an index.
Q: When should you NOT use an API Gateway?
A: When you have only 1 service (unnecessary overhead). When you are still learning basics (adds complexity before you understand the core). For internal service-to-service calls (Feign handles those, not Gateway). When all APIs are internal only with no external clients. When your team is 1-2 developers and the operational complexity outweighs the benefits.
