Section 1

REST API — All the Ways to Create One

REST API means your server sends back data (JSON) instead of an HTML page. A mobile app, Postman, or a React frontend calls your URL and gets data it can use however it wants. There are multiple ways to write a REST endpoint in Spring Boot — from simplest to most complete.

The one key difference from MVC

In Spring MVC you use @Controller and return a page name like "students/list". In REST you use @RestController and return actual data. Spring automatically converts that data to JSON using a library called Jackson that is already included. That is the only change.

Way 1 — Return data directly (simplest, for learning only)

Example 1 — Return a list directly, no status control
controller/StudentRestController.java — Way 1: direct returnjava
@RestController
// @RestController = @Controller + every method returns JSON automatically
// No need to return a template name like "students/list"
@RequestMapping("/api/students")
// All URLs in this class start with /api/students
// Good practice: put /api/ before REST endpoints so they don't clash with HTML pages
public class StudentRestController {

    @Autowired
    private StudentService studentService;

    @GetMapping
    // Handles: GET /api/students
    // Test in Postman: GET http://localhost:8080/api/students
    public List<Student> getAll() {
        return studentService.findAll();
        // Spring converts List<Student> to JSON:
        // [{"id":1,"name":"Ravi","email":"ravi@x.com","age":22}, ...]
        // HTTP status is always 200 OK — you have no control over it this way
    }

    @GetMapping("/{id}")
    // Handles: GET /api/students/5
    // {id} is a placeholder for any number
    public Student getOne(@PathVariable Long id) {
        // @PathVariable takes the number from the URL
        // /api/students/5 → id becomes 5
        return studentService.findById(id);
    }

    @PostMapping
    // Handles: POST /api/students with a JSON body
    public Student create(@RequestBody Student student) {
        // @RequestBody reads the JSON the client sent and fills a Student object
        // Client sends: {"name":"Ravi","email":"ravi@x.com","age":22}
        // Spring fills student.name, student.email, student.age automatically
        return studentService.save(student);
        // Returns the saved student (now with id assigned by database)
    }

    @PutMapping("/{id}")
    // Handles: PUT /api/students/5 — update student with id=5
    public Student update(@PathVariable Long id, @RequestBody Student student) {
        student.setId(id);     // make sure we update the correct one
        return studentService.save(student);
    }

    @DeleteMapping("/{id}")
    // Handles: DELETE /api/students/5 — delete student with id=5
    public String delete(@PathVariable Long id) {
        studentService.delete(id);
        return "Student deleted";
        // Returns the string as JSON: "Student deleted"
        // Problem: always HTTP 200 — but delete should return 204 No Content
    }
}

Problem with Way 1

You cannot control the HTTP status code. POST should return 201 (Created). DELETE should return 204 (No Content). With direct return you always get 200. This is technically wrong. Use Way 2 to fix it.

Way 2 — ResponseEntity (correct way for production)

Example 2 — ResponseEntity with correct HTTP status codes
ResponseEntity lets you set the HTTP status AND the bodyjava
@RestController
@RequestMapping("/api/students")
public class StudentRestController {

    @Autowired
    private StudentService studentService;

    @GetMapping
    public ResponseEntity<List<Student>> getAll() {
        List<Student> list = studentService.findAll();
        return ResponseEntity.ok(list);
        // .ok(data) = HTTP 200 OK + the list as JSON
        // Postman shows: 200 OK and the JSON array
    }

    @GetMapping("/{id}")
    public ResponseEntity<Student> getOne(@PathVariable Long id) {
        Student student = studentService.findById(id);
        return ResponseEntity.ok(student);
    }

    @PostMapping
    public ResponseEntity<Student> create(@RequestBody Student student) {
        Student saved = studentService.save(student);
        return ResponseEntity
            .status(HttpStatus.CREATED)   // HTTP 201 Created — correct for POST
            .body(saved);
    }

    @PutMapping("/{id}")
    public ResponseEntity<Student> update(@PathVariable Long id,
                                            @RequestBody Student student) {
        student.setId(id);
        return ResponseEntity.ok(studentService.save(student));
        // HTTP 200 OK — correct for PUT
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        studentService.delete(id);
        return ResponseEntity.noContent().build();
        // HTTP 204 No Content — correct for DELETE (success but nothing to return)
    }
}

// ─── HTTP Status quick guide ─────────────────────────────────────────────────
// 200 OK           → GET and PUT success
// 201 Created      → POST success (new record was created)
// 204 No Content   → DELETE success
// 400 Bad Request  → validation failed, wrong data sent
// 404 Not Found    → id does not exist in database
// 500 Server Error → unexpected exception

Way 3 — POST with validation and proper error response

Example 3 — Validate incoming JSON and return errors if invalid
POST with @Valid — returns 400 with error details if data is wrongjava
import jakarta.validation.Valid;
import org.springframework.validation.BindingResult;

@PostMapping
public ResponseEntity<?> create(
        @RequestBody @Valid Student student,
        // @RequestBody = read JSON, convert to Student
        // @Valid = run @NotBlank @Email @Min @Max checks on it
        BindingResult result
        // BindingResult = holds the list of any errors @Valid found
        // Must come IMMEDIATELY after the @Valid object
) {
    if (result.hasErrors()) {
        // Build a map: fieldName → errorMessage
        Map<String, String> errors = new HashMap<>();
        result.getFieldErrors()
              .forEach(e -> errors.put(e.getField(), e.getDefaultMessage()));
        return ResponseEntity.badRequest().body(errors);
        // HTTP 400 Bad Request + {"name":"Name cannot be empty","email":"..."}
    }
    Student saved = studentService.save(student);
    return ResponseEntity.status(201).body(saved);
}

// Postman — send this body to POST /api/students:
// {"name":"","email":"notvalid","age":5}
//
// You get back HTTP 400 with:
// {
//   "name":   "Name cannot be empty",
//   "email":  "Please enter a valid email",
//   "age":    "Age must be at least 16",
//   "course": "Course cannot be empty"
// }

Way 4 — GET with query parameters (search and filter)

Example 4 — Filter by course, search by name using query params
GET /api/students?course=Python or ?name=ravijava
@GetMapping("/search")
// Handles: GET /api/students/search?course=Python
//          GET /api/students/search?name=ravi
// Query parameters come after the ? in the URL
public ResponseEntity<List<Student>> search(
        @RequestParam(required = false) String course,
        @RequestParam(required = false) String name
        // @RequestParam reads ?course=Python from the URL
        // required=false means the param is optional — URL works without it
) {
    if (course != null) {
        return ResponseEntity.ok(studentService.findByCourse(course));
    }
    if (name != null) {
        return ResponseEntity.ok(studentService.findByNameContaining(name));
    }
    return ResponseEntity.ok(studentService.findAll());
}

// Test URLs:
// GET /api/students/search?course=Python    → all Python students
// GET /api/students/search?name=ravi        → students with "ravi" in name
// GET /api/students/search                  → all students (no filter)

Way 5 — REST with DTO (best practice for real projects)

Example 5 — Complete REST controller using DTO
Full CRUD using StudentDTO (see Section 2 for DTO explanation)java
@RestController
@RequestMapping("/api/students")
public class StudentRestController {

    @Autowired private StudentService service;

    // ─── Convert Entity → DTO (what we send to client) ────────────────
    private StudentDTO toDTO(Student s) {
        StudentDTO d = new StudentDTO();
        d.setId(s.getId()); d.setName(s.getName());
        d.setEmail(s.getEmail()); d.setCourse(s.getCourse());
        return d; // password and other sensitive fields NOT copied
    }

    // ─── Convert DTO → Entity (what we save to database) ──────────────
    private Student toEntity(StudentDTO d) {
        Student s = new Student();
        s.setName(d.getName()); s.setEmail(d.getEmail());
        s.setCourse(d.getCourse()); return s;
    }

    @GetMapping
    public ResponseEntity<List<StudentDTO>> getAll() {
        return ResponseEntity.ok(
            service.findAll().stream().map(this::toDTO).toList());
    }

    @PostMapping
    public ResponseEntity<StudentDTO> create(@RequestBody @Valid StudentDTO dto) {
        return ResponseEntity.status(201).body(toDTO(service.save(toEntity(dto))));
    }

    @PutMapping("/{id}")
    public ResponseEntity<StudentDTO> update(@PathVariable Long id,
                                               @RequestBody @Valid StudentDTO dto) {
        Student entity = toEntity(dto); entity.setId(id);
        return ResponseEntity.ok(toDTO(service.save(entity)));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        service.delete(id);
        return ResponseEntity.noContent().build();
    }
}

DTO — What It Is, Before vs After, With and Without

DTO stands for Data Transfer Object. It is a plain Java class (no @Entity, no @Id) used to carry only the data you choose to the client. It is the difference between handing someone your entire wallet and just your business card.

WITHOUT DTO — returning entity directly

Your Student entity goes to the client as-is.

  • Client sees ALL fields: id, name, email, password, createdAt, updatedAt, and any Hibernate internal proxy fields
  • If you add a password field later, the client immediately sees it — security risk
  • Circular reference crash: Employee.department → Department.employees → Employee... (infinite loop)
  • API breaks when you rename a field in the entity
  • You cannot have different validation rules for "create" vs "update"
WITH DTO — return only what you choose

Client gets exactly what you put in the DTO.

  • You decide which fields the client sees
  • Password and other sensitive fields are never included
  • No circular reference problems
  • You can rename entity fields without breaking the API
  • Different validation rules per DTO (CreateStudentDTO vs UpdateStudentDTO)

BEFORE — Without DTO (what the client actually receives)

Example 1 — No DTO: entity is exposed directly
model/Student.java — this ENTIRE class goes to the clientjava
@Entity
public class Student {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long   id;
    private String name;
    private String email;
    private String password;       // ← DANGER: client will see this!
    private String course;
    private int    age;
    private String internalNotes;  // ← client should never see this
    private LocalDateTime createdAt; // ← client doesn't need this
    // getters setters ...
}

// Controller — returning entity directly:
@GetMapping
public List<Student> getAll() {
    return studentService.findAll();
}

// What the client ACTUALLY receives (all fields exposed):
// [
//   {
//     "id": 1,
//     "name": "Ravi Kumar",
//     "email": "ravi@x.com",
//     "password": "secret123",      ← EXPOSED! Security breach!
//     "course": "Java",
//     "age": 22,
//     "internalNotes": "flagged",   ← EXPOSED! Should be private!
//     "createdAt": "2024-01-15T10:30:00"  ← unnecessary noise
//   }
// ]

AFTER — With DTO (client gets only what you choose)

Example 2 — With DTO: clean and controlled response
dto/StudentDTO.java — only the fields the client needsjava
package com.example.studentapp.dto;
import jakarta.validation.constraints.*;

// NO @Entity — this is NOT a database table
// NO @Id    — this has no primary key
// It is a plain class used ONLY to carry data to and from the client
public class StudentDTO {

    private Long   id;      // shown when returning data, null when creating

    @NotBlank(message = "Name is required")
    @Size(min = 2, max = 50)
    private String name;

    @NotBlank(message = "Email is required")
    @Email(message = "Enter a valid email")
    private String email;

    @NotBlank(message = "Course is required")
    private String course;

    // NO password field — client NEVER sees it
    // NO internalNotes — hidden from API
    // NO createdAt — not needed by client

    public Long   getId()              { return id; }
    public String getName()            { return name; }
    public String getEmail()           { return email; }
    public String getCourse()          { return course; }
    public void   setId(Long id)       { this.id = id; }
    public void   setName(String n)    { this.name = n; }
    public void   setEmail(String e)   { this.email = e; }
    public void   setCourse(String c)  { this.course = c; }
}

// What the client now receives (clean and safe):
// [
//   {
//     "id": 1,
//     "name": "Ravi Kumar",
//     "email": "ravi@x.com",
//     "course": "Java"
//     ← no password, no internalNotes, no createdAt
//   }
// ]
Conversion helpers: Entity → DTO and DTO → Entityjava
// ─── Inside the REST controller ───────────────────────────────────────────────

// Convert Entity → DTO: used when RETURNING data to the client
// We pick which fields to copy — sensitive fields are left out
private StudentDTO toDTO(Student student) {
    StudentDTO dto = new StudentDTO();
    dto.setId(student.getId());
    dto.setName(student.getName());
    dto.setEmail(student.getEmail());
    dto.setCourse(student.getCourse());
    // password, internalNotes, createdAt are NOT copied — they stay hidden
    return dto;
}

// Convert DTO → Entity: used when SAVING data from the client
// Client sends a DTO, we create a real Entity from it to save to the database
private Student toEntity(StudentDTO dto) {
    Student student = new Student();
    student.setName(dto.getName());
    student.setEmail(dto.getEmail());
    student.setCourse(dto.getCourse());
    // id NOT set — database generates it automatically
    // password NOT set — handled separately (hashing etc.)
    return student;
}

// ─── Using them in methods ────────────────────────────────────────────────────
@GetMapping
public ResponseEntity<List<StudentDTO>> getAll() {
    return ResponseEntity.ok(
        service.findAll()          // get List<Student> from database
               .stream()           // process each one
               .map(this::toDTO)  // convert every Student to StudentDTO
               .toList()           // collect back to a List
    );
}

@PostMapping
public ResponseEntity<StudentDTO> create(@RequestBody @Valid StudentDTO dto) {
    Student entity = toEntity(dto);          // DTO → Entity
    Student saved  = service.save(entity);   // save Entity to DB
    StudentDTO result = toDTO(saved);       // Entity → DTO (with id now set)
    return ResponseEntity.status(201).body(result);
}

How many DTOs do you create?

The number of DTOs depends on how many different shapes of data you need. Here is the typical pattern for a student system:

DTO nameWhen it is usedFields included
StudentDTOGET all, GET by id — return to clientid, name, email, course (no password, no internals)
CreateStudentDTOPOST — create a new studentname, email, course, password (no id — DB generates it)
UpdateStudentDTOPUT — update an existing studentname, email, course (no id — taken from URL, no password change)
StudentSummaryDTOGET list — show compact list viewid, name, course only (no email for list performance)

Simple rule: one DTO per "shape of data" you need

If you only have a simple project, one StudentDTO is enough for everything. As your project grows, you split into more specific DTOs when different operations need different fields.

DTO works the same way in MVC — bind the form to the DTO instead of the entityjava
// In MVC you can also bind forms to a DTO instead of the entity
// Benefit: the form only receives fields you allow, not all entity fields

@GetMapping("/new")
public String showForm(Model model) {
    model.addAttribute("studentDTO", new StudentDTO());
    // Give Thymeleaf a blank DTO, not a blank Entity
    return "students/form";
}

@PostMapping("/save")
public String save(@Valid @ModelAttribute("studentDTO") StudentDTO dto,
                    BindingResult result) {
    if (result.hasErrors()) return "students/form";
    studentService.save(toEntity(dto)); // convert DTO to Entity before saving
    return "redirect:/students";
}

Logging — What It Is and Why Every App Needs It

Logging means writing messages to a log file or console as your app runs. These messages help you see what your app is doing and find problems when something goes wrong. Without logging, you are running your app blind.

Think of logging like a flight recorder

An airplane's black box records everything that happens during a flight. If something goes wrong, investigators read the box to understand what happened and when. Logging is your app's black box. When a bug appears or the app crashes, you read the log to see exactly what happened, in what order, and with what data.

Without logging
  • App crashes at 2am → you have no idea why
  • A student says "it gave an error when I registered" → you cannot trace what happened
  • You cannot tell how many times a method was called
  • Performance problems are invisible — you cannot see which method is slow
  • Debugging means adding temporary print statements everywhere
With logging
  • Every request, save, and error is recorded with a timestamp
  • You see exactly which line failed and what value caused it
  • You can filter: show only ERRORS, or show DEBUG messages for one class only
  • Log files can be kept for weeks — review them any time
  • No temporary print statements — logging is always on

Log levels — what they mean

LevelUse it whenExample message
ERRORSomething broke — action required immediately"Database connection failed"
WARNSomething unusual but app still works"Request took 5 seconds — may be slow"
INFONormal events you want to track"Student Ravi registered successfully"
DEBUGDetailed info for finding bugs (dev only)"Entering save() with student id=null"
TRACEVery detailed — every small step"Checking field: name = 'Ravi'"

SLF4J vs Log4j2 — what is the difference?

SLF4JLog4j2
A logging interface — defines how you write log messages in your code (log.info(), log.error())A logging implementation — actually writes the messages to console, files, databases
You write import org.slf4j.Logger in your codeYou configure Log4j2 in log4j2.xml — it does the actual writing
Like a power socket — the standard shape your plug goes intoLike the electricity behind the socket — the actual power that runs things
Cannot work alone — needs an implementation behind itCan work alone but SLF4J in front makes your code portable
Your code uses SLF4J → you can swap Log4j2 for Logback any time without changing your codeIf you use Log4j2 API directly → changing is harder

How they work together in Spring Boot

You write your log messages using SLF4J (log.info("Student saved")). Behind the scenes, Spring Boot uses Logback by default — or you switch it to Log4j2. Either way your code stays the same because you always write to SLF4J.

Section 4

Log4j2 Setup — Step by Step

Spring Boot uses Logback by default. To use Log4j2 you need to do two things: remove Logback from pom.xml and add Log4j2, then create a config file.

1

Remove Logback and add Log4j2 in pom.xml

Spring Boot includes Logback by default inside spring-boot-starter. You must exclude it first, then add Log4j2.

2

Create the Log4j2 configuration file

Create src/main/resources/log4j2.xml — this tells Log4j2 where to write messages and which level to use.

3

Use SLF4J in your Java classes

Import org.slf4j.Logger and write log.info(), log.error() — your code never changes even if you swap Log4j2 for something else later.

Step 1 — pom.xml: exclude Logback, add Log4j2
pom.xml — switch from Logback to Log4j2xml
<dependencies>

  <!-- Spring Boot Web — but exclude the default Logback logger -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
      <exclusion>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-logging</artifactId>
        <!-- This removes Logback — Spring Boot's default logger
             Without this exclusion, both Logback and Log4j2 run together and clash -->
      </exclusion>
    </exclusions>
  </dependency>

  <!-- Also exclude from data-jpa if you use it -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
    <exclusions>
      <exclusion>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-logging</artifactId>
      </exclusion>
    </exclusions>
  </dependency>

  <!-- Now add Log4j2 — this replaces Logback -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-log4j2</artifactId>
    <!-- This adds: log4j-core, log4j-api, log4j-slf4j-impl
         log4j-slf4j-impl is the bridge that lets SLF4J calls go through Log4j2 -->
  </dependency>

</dependencies>
Step 2 — Create log4j2.xml configuration file
src/main/resources/log4j2.xmlxml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
<!-- status="WARN" — Log4j2 itself only shows warnings about its own internal state -->

  <Appenders>
  <!-- Appenders = WHERE to write the log messages -->

    <!-- Console appender: write messages to the terminal -->
    <Console name="Console" target="SYSTEM_OUT">
      <PatternLayout
        pattern="%d{yyyy-MM-dd HH:mm:ss} [%-5level] %logger{36} - %msg%n"/>
      <!-- Pattern explained:
           %d{...}      = date and time:  2024-01-15 10:30:45
           [%-5level]   = log level:      [INFO ] [ERROR] [DEBUG]
           %logger{36}  = class name:     com.example.StudentService
           %msg         = your message:   Student Ravi saved
           %n           = new line -->
    </Console>

    <!-- File appender: also write to a file (logs are saved here) -->
    <RollingFile name="File"
                  fileName="logs/studentapp.log"
                  <!-- File where logs are written: logs/studentapp.log
                       The folder "logs" is created automatically -->
                  filePattern="logs/studentapp-%d{yyyy-MM-dd}.log">
                  <!-- When the log rolls over: create studentapp-2024-01-15.log -->
      <PatternLayout
        pattern="%d{yyyy-MM-dd HH:mm:ss} [%-5level] %logger{36} - %msg%n"/>
      <Policies>
        <TimeBasedTriggeringPolicy interval="1"/>
        <!-- Roll the log file every day — create a new file each day -->
      </Policies>
    </RollingFile>

  </Appenders>

  <Loggers>
  <!-- Loggers = WHAT to log and at what level -->

    <!-- Your own code: show DEBUG and above (very detailed for your classes) -->
    <Logger name="com.example.studentapp" level="DEBUG" additivity="false">
      <AppenderRef ref="Console"/>
      <AppenderRef ref="File"/>
      <!-- Write to BOTH console and file for your code -->
    </Logger>

    <!-- Everything else (Spring, Hibernate): only show INFO and above
         Without this: Hibernate prints thousands of lines per request -->
    <Root level="INFO">
      <AppenderRef ref="Console"/>
      <AppenderRef ref="File"/>
    </Root>

  </Loggers>
</Configuration>
Section 5

SLF4J with Logback — The Default Spring Boot Setup (Simpler Way)

If you do not want to deal with Log4j2 configuration, Spring Boot's default Logback with SLF4J is perfectly fine and much simpler to set up. You do not add any dependency — Logback is already included. You just configure it.

Logback = no setup needed for basic use

Spring Boot configures Logback automatically. You can start logging immediately without touching pom.xml or any config file. Just add a logger to your class and write messages. For more control, add a logback-spring.xml file.

1

No pom.xml changes needed

spring-boot-starter-web already includes SLF4J + Logback. Nothing to add or exclude. Just start using it.

2

Option A — Configure via application.properties

For simple changes (log level, log file path) you can use application.properties — no XML needed.

3

Option B — Create logback-spring.xml for full control

For file rolling, multiple appenders, or custom patterns, create src/main/resources/logback-spring.xml.

Option A — Configure logging in application.properties (simplest)
src/main/resources/application.properties — logging configproperties
# Set the root log level (everything Spring and Hibernate) to INFO
# This means: show INFO, WARN, ERROR but hide DEBUG and TRACE
logging.level.root=INFO

# Set your own package to DEBUG (very detailed — only for your code)
logging.level.com.example.studentapp=DEBUG

# Set Hibernate SQL level — see actual SQL in the console
logging.level.org.hibernate.SQL=DEBUG

# Write logs to a file as well as the console
logging.file.name=logs/studentapp.log

# Customise the log format in the console
logging.pattern.console=%d{yyyy-MM-dd HH:mm:ss} [%level] %logger{20} - %msg%n

# Customise the log format in the file
logging.pattern.file=%d{yyyy-MM-dd HH:mm:ss} [%level] %logger{36} - %msg%n
Option B — logback-spring.xml for full file rolling control
src/main/resources/logback-spring.xmlxml
<configuration>

  <!-- Console appender: write to terminal -->
  <appender name="Console" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{HH:mm:ss} [%-5level] %logger{30} - %msg%n</pattern>
    </encoder>
  </appender>

  <!-- File appender: write to rolling log file -->
  <appender name="File" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>logs/studentapp.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
      <fileNamePattern>logs/studentapp-%d{yyyy-MM-dd}.log</fileNamePattern>
      <!-- Creates a new file every day: studentapp-2024-01-15.log -->
      <maxHistory>30</maxHistory>
      <!-- Keep 30 days of log files, delete older ones automatically -->
    </rollingPolicy>
    <encoder>
      <pattern>%d{yyyy-MM-dd HH:mm:ss} [%-5level] %logger{36} - %msg%n</pattern>
    </encoder>
  </appender>

  <!-- Your app code: DEBUG level (very detailed) -->
  <logger name="com.example.studentapp" level="DEBUG" additivity="false">
    <appender-ref ref="Console"/>
    <appender-ref ref="File"/>
  </logger>

  <!-- Everything else (Spring, Hibernate): INFO only -->
  <root level="INFO">
    <appender-ref ref="Console"/>
    <appender-ref ref="File"/>
  </root>

</configuration>
Section 6

How to Use Logging in Your Java Classes — Real Examples

Regardless of whether you use Log4j2 or Logback, you always write log messages using SLF4J. Your code looks identical either way. This is the beauty of SLF4J — it is the standard interface.

Example 1 — Add logging to StudentService (basic)
service/StudentService.java — logging every important operationjava
package com.example.studentapp.service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
// These two imports are ALWAYS the same — SLF4J imports
// Whether you use Logback or Log4j2 does not matter — same imports

@Service
public class StudentService {

    private static final Logger log =
        LoggerFactory.getLogger(StudentService.class);
    // Create ONE logger per class
    // LoggerFactory.getLogger(StudentService.class):
    //   - the class name appears in every log message so you know WHERE it came from
    // private static final: one logger shared by all instances, created once

    @Autowired
    private StudentRepository repo;

    public List<Student> findAll() {
        log.debug("findAll() called");
        // DEBUG = detailed developer message, shown only in development
        // Use DEBUG for: method entry points, variable values, loop counts

        List<Student> students = repo.findAll();

        log.info("Returning {} students", students.size());
        // INFO = normal business event worth tracking
        // {} is a placeholder — SLF4J fills it with the variable: "Returning 5 students"
        // Use {} instead of + for concatenation — it is faster (no string building if level not active)

        return students;
    }

    public Student findById(Long id) {
        log.debug("findById() called with id={}", id);
        return repo.findById(id)
            .orElseThrow(() -> {
                log.warn("Student not found with id={}", id);
                // WARN = something unexpected happened but app continues
                // Use WARN for: not-found scenarios, slow operations, retries
                return new RuntimeException("Student not found: " + id);
            });
    }

    public Student save(Student student) {
        log.info("Saving student with name={} email={}", student.getName(), student.getEmail());
        Student saved = repo.save(student);
        log.info("Student saved successfully with id={}", saved.getId());
        return saved;
    }

    public void delete(Long id) {
        log.info("Deleting student with id={}", id);
        repo.deleteById(id);
        log.info("Student {} deleted", id);
    }
}
Example 2 — Logging exceptions and errors in the controller
exception/GlobalExceptionHandler.java — logging errorsjava
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@ControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log =
        LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(RuntimeException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    @ResponseBody
    public Map<String, String> handleNotFound(RuntimeException ex) {
        log.error("RuntimeException caught: {}", ex.getMessage());
        // ERROR = something broke — action may be needed
        // Use ERROR for: caught exceptions, database failures, unexpected states
        return Map.of("error", ex.getMessage());
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    @ResponseBody
    public Map<String, String> handleGeneral(Exception ex) {
        log.error("Unexpected error: {}", ex.getMessage(), ex);
        // The third argument 'ex' prints the full stack trace in the log file
        // ALWAYS log the full exception when it is an unexpected error
        return Map.of("error", "Something went wrong");
    }
}
Example 3 — Logging in REST controller (log every request)
controller/StudentRestController.java — logging every API calljava
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@RestController
@RequestMapping("/api/students")
public class StudentRestController {

    private static final Logger log =
        LoggerFactory.getLogger(StudentRestController.class);

    @Autowired private StudentService service;

    @GetMapping
    public ResponseEntity<List<Student>> getAll() {
        log.info("GET /api/students called");
        List<Student> students = service.findAll();
        log.info("GET /api/students returning {} results", students.size());
        return ResponseEntity.ok(students);
    }

    @PostMapping
    public ResponseEntity<Student> create(@RequestBody @Valid Student student,
                                             BindingResult result) {
        log.info("POST /api/students called with name={}", student.getName());

        if (result.hasErrors()) {
            log.warn("POST /api/students validation failed: {} errors", result.getErrorCount());
            Map<String, String> errors = new HashMap<>();
            result.getFieldErrors().forEach(e -> errors.put(e.getField(), e.getDefaultMessage()));
            return ResponseEntity.badRequest().body(null);
        }

        Student saved = service.save(student);
        log.info("POST /api/students created student id={}", saved.getId());
        return ResponseEntity.status(201).body(saved);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        log.info("DELETE /api/students/{} called", id);
        service.delete(id);
        log.info("DELETE /api/students/{} completed", id);
        return ResponseEntity.noContent().build();
    }
}

The five things to remember

  • REST vs MVC: change @Controller to @RestController. Return data, not a page name. Use ResponseEntity to set the correct HTTP status code.
  • DTO protects your data: without DTO the client sees all entity fields including sensitive ones. With DTO you control exactly what is sent. One DTO per "shape of data" you need.
  • Logging = SLF4J in your code, always: write log.info(), log.error() using SLF4J imports regardless of whether you use Logback or Log4j2 behind the scenes.
  • Logback is default and simpler: it already works in Spring Boot with no pom.xml change. Use application.properties for basic config. Use logback-spring.xml for file rolling.
  • Log4j2 needs setup: exclude spring-boot-starter-logging from every starter, add spring-boot-starter-log4j2, create log4j2.xml. Your actual logging code (log.info()) stays identical.
