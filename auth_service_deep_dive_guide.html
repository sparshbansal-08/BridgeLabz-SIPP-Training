Understand First

Why We Need an Auth Service at All

This guide is a companion to the main microservices reference. There, authentication was introduced last and kept conceptual. Here we slow right down and build it properly, because security is the topic beginners find hardest, and it deserves its own careful, piece-by-piece treatment.

The problem, stated plainly

Right now any caller who knows the gateway address can hit any endpoint. Nothing checks who is calling. A real system must know its caller, to decide what they are allowed to do and to record who did what. So we need a way to (1) prove a user is who they say they are, and (2) carry that proof on every later request.

Why a dedicated service, and not login logic inside every service

Login logic copied into every service
# product-service
user table + password check

# order-service
user table + password check

# every service repeats it,
# and they can DISAGREE about
# who exists or what a role means
Duplicated, inconsistent, and hard to change. Each service owns a copy of "users."
One Auth Service owns it
# auth-service ONLY
owns users + passwords,
issues a signed token.

# every other service simply
# TRUSTS a valid token. No user
# table anywhere else.
One owner of identity. Everyone else just verifies a token. This single responsibility is why the Auth Service exists.
Two words you must not confuse
  • Authentication answers "who are you?" (login, proving identity). This guide is mostly about this.
  • Authorization answers "what are you allowed to do?" (roles, permissions). We touch it with roles, and point you to study it deeper afterward.
Why JWT (JSON Web Token)
  • After login we need to hand the client something it can present on every later request, so it does not resend its password each time.
  • A JWT is a signed token. Anyone can read it, but only the holder of the secret key can create or alter one without detection. That signature is what makes it trustworthy.
  • It is stateless: the token itself carries the username and role, so any instance of any service can verify it with the secret key, without a shared session database. That fits independent, scalable microservices perfectly.

The build order we will follow, and why each piece comes when it does

2
User entity. We cannot authenticate anyone without first knowing what a user is and storing them. So this is first.
3
User repository. We have a user shape, but no way to find a user by username at login. So we add a repository to load them.
4
Password encoder. We must never store raw passwords. Before we save any user, we need a way to hash passwords. So this comes next.
5
DTOs. Endpoints need clean request and response shapes, and we should not expose the entity directly. So we define small request/response objects.
6
Register endpoint. Now we have every piece to create a user: take a DTO, hash the password, save via the repository. So we can build the first endpoint.
7
JWT service. Once a user is verified, we must hand back proof of identity that works on later requests. So we need something that creates a signed token.
8
Login endpoint. Now wire it together: find the user, check the password, issue a token. This is the heart of the service.
9
Validate token. Whoever receives a token later must be able to check it. So we add validation to the JWT service.
10
Security config. The Auth Service must let login/register through but lock down the rest. So we configure Spring Security.
11
Gateway validation. We validate the token once at the front door so each service need not. So the gateway checks every protected request.
12
Forward identity. Downstream services need to know who the caller is. So the gateway passes the identity along.

Create the Project and Prerequisites

Prerequisites
  • JDK 17 or 21, Maven, and an IDE (the same as the main guide).
  • MySQL running locally, for storing users. We use a database named authdb.

Build · Part 2

The User Entity

Why this is the very first piece

Authentication means proving who a user is. We cannot check a user, store a user, or issue a token for a user until we have defined what a user actually is. So before any endpoint, before any token, we define the user and where it is stored.

model/AppUser.javaJava
package com.example.authservice.model;

import jakarta.persistence.*;

// Named AppUser, not "User", to avoid clashing with Spring Security's
// own User class. @Entity maps it to a database table.
@Entity
@Table(name = "users")
public class AppUser {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // auto-increment id
    private Long id;

    // unique = no two users can share a username.
    @Column(unique = true, nullable = false)
    private String username;

    // This stores the HASHED password, never the plain text (see Part 4).
    @Column(nullable = false)
    private String password;

    // A simple role string, e.g. "ROLE_USER" or "ROLE_ADMIN".
    @Column(nullable = false)
    private String role;

    public AppUser() {}   // no-arg constructor required by JPA

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getUsername() { return username; }
    public void setUsername(String u) { this.username = u; }
    public String getPassword() { return password; }
    public void setPassword(String p) { this.password = p; }
    public String getRole() { return role; }
    public void setRole(String r) { this.role = r; }
}
ElementWhat it does and why it is needed
@Entity / @Table(name="users")Maps this class to a users table so each AppUser becomes a row.
@Id + @GeneratedValueThe primary key, auto-generated by the database.
@Column(unique = true) usernameEnforces unique usernames, so login finds exactly one user.
passwordHolds the BCrypt hash, never the plain password. We hash it in Part 4 before saving.
roleA simple role used later for authorization and embedded into the token.
Why we name it AppUser, not User

Spring Security ships its own class called User. Naming your entity User leads to confusing import clashes. AppUser keeps your code unambiguous.

What we have, and what is next

We can describe a user, but we have no way to find one by username, which login needs. That is the next piece: the repository.

Build · Part 3

The User Repository

Why now

The entity defines a row, but login must look a user up by username, and registration must check whether a username already exists. We need a repository that can save and find users. Spring Data builds it from a single interface.

repository/UserRepository.javaJava
package com.example.authservice.repository;

import com.example.authservice.model.AppUser;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

// JpaRepository gives save, findById, findAll, deleteById for free.
public interface UserRepository extends JpaRepository<AppUser, Long> {

    // Spring Data reads this method NAME and writes the query for us:
    // "find an AppUser where username = ?". Returns Optional because the
    // user may not exist. Used at login and during registration.
    Optional<AppUser> findByUsername(String username);
}
ElementWhat it does and why it is needed
extends JpaRepository<AppUser, Long>Full CRUD with no implementation. Type params: the entity and its id type.
findByUsername(String)A derived query: Spring Data turns the method name into a database query. Returns Optional to force handling the missing case.
What we have, and what is next

We can save and find users. But we must never store a password as plain text. Before saving our first user, we need a way to hash passwords. That is next.

Build · Part 4

The Password Encoder

Why now, before saving any user

If we stored raw passwords and the database leaked, every password would be exposed. We store a one-way hash instead. BCrypt is the standard: slow by design (to frustrate attackers) and salted (so identical passwords hash differently). We set this up now because the next step, registration, must hash before it saves.

config/PasswordConfig.javaJava
package com.example.authservice.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@Configuration
public class PasswordConfig {

    // One shared encoder any class can inject. Hashes on register,
    // compares on login.
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
The two methods you will use
  • On register: passwordEncoder.encode(rawPassword) produces the hash you store.
  • On login: passwordEncoder.matches(rawPassword, storedHash) returns true if they correspond. Hashing is one-way, so you never decrypt; you re-hash the input and compare.
What we have, and what is next

We can store users, find them, and hash passwords. But endpoints need clean JSON shapes, and we should not expose the entity. So next we define small DTOs.

Request and Response DTOs

Why now, and why not just use the entity

A register or login request is only a username and password; it should not be the whole AppUser entity (which has an id and a role the client must not set). And the login response returns a token, not the stored hash. DTOs are small classes describing exactly what crosses the wire, keeping the entity private.

What we have, and what is next

Every supporting piece is ready: a user, a way to find users, password hashing, and clean request/response shapes. That is exactly enough to build our first real endpoint, registration.

Build · Part 6

The Register Endpoint

Why register before login

You cannot log in without an account, so we first need a way to create one. Registration uses every piece we built: it takes a RegisterRequest, checks the username is free via the repository, hashes the password with the encoder, and saves an AppUser.

controller/AuthController.java — registration (login added in Part 8)Java
package com.example.authservice.controller;

import com.example.authservice.dto.RegisterRequest;
import com.example.authservice.model.AppUser;
import com.example.authservice.repository.UserRepository;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/auth")     // all auth endpoints live under /auth
public class AuthController {

    private final UserRepository userRepository;   // Part 3
    private final PasswordEncoder passwordEncoder;  // Part 4

    public AuthController(UserRepository userRepository,
                          PasswordEncoder passwordEncoder) {
        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
    }

    @PostMapping("/register")
    public ResponseEntity<String> register(@RequestBody RegisterRequest req) {

        // 1. Reject duplicate usernames (findByUsername from Part 3).
        if (userRepository.findByUsername(req.getUsername()).isPresent()) {
            return ResponseEntity.status(HttpStatus.CONFLICT)
                    .body("Username already taken");
        }

        // 2. Build the user and HASH the password before storing it.
        AppUser user = new AppUser();
        user.setUsername(req.getUsername());
        user.setPassword(passwordEncoder.encode(req.getPassword())); // hash!
        user.setRole("ROLE_USER");   // default role for new sign-ups

        // 3. Save via the repository.
        userRepository.save(user);

        return ResponseEntity.status(HttpStatus.CREATED).body("User registered");
    }
}

@RequestMapping("/auth")All endpoints begin with /auth, so register is /auth/register.
constructor injectionSpring passes the UserRepository (Part 3) and PasswordEncoder (Part 4) beans automatically.

passwordEncoder.encode(...)Turns the raw password into a BCrypt hash. Only the hash is stored.
setRole("ROLE_USER")Gives new accounts a default role, later embedded in the token.
userRepository.save(user)Inserts the new row into the users table.

What we have, and what is next

Users can be created with safely hashed passwords. But logging in successfully must hand back something the client can reuse on later requests without resending the password. That something is a token, which needs a service to create it. That is Part 7.

Build · Part 7

The JWT Service: Creating a Token

Why now

Once login verifies a user, it must return proof of identity the client can present on every later request. Resending the password each time would be insecure and clumsy. Instead we issue a signed token. This part builds the piece that creates that token; login (Part 8) will call it.

What a JWT contains, in plain terms
  • A subject: who the token is about (the username).
  • Claims: extra facts, such as the user's role.
  • An issued-at and an expiry time, so old tokens stop working.
  • A signature: created with the secret key, so the token cannot be forged or altered without detection.
security/JwtService.java — token creationJava
package com.example.authservice.security;

import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;
import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.util.Date;

@Service
public class JwtService {

    // These two values come from application.properties (Step 1):
    //   jwt.secret and jwt.expiration-ms.
    @Value("${jwt.secret}")
    private String secret;

    @Value("${jwt.expiration-ms}")
    private long expirationMs;

    // Build the signing key from the secret text. HS256 needs >= 32 chars.
    private SecretKey key() {
        return Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    }

    // Create a signed token for a user. Called by the login endpoint.
    public String generateToken(String username, String role) {
        Date now = new Date();
        Date expiry = new Date(now.getTime() + expirationMs);

        return Jwts.builder()
                .subject(username)        // who the token is about
                .claim("role", role)       // extra fact: the user's role
                .issuedAt(now)            // when it was created
                .expiration(expiry)       // when it stops being valid
                .signWith(key())          // sign it so it cannot be forged
                .compact();               // produce the final token string
    }
}
LineWhat it does and where values come from
@Value("${jwt.secret}")Injects the signing secret. Source: application.properties, key jwt.secret.
@Value("${jwt.expiration-ms}")Injects how long tokens last. Source: jwt.expiration-ms.
Keys.hmacShaKeyFor(...)Turns the secret text into a cryptographic key. HS256 requires at least 32 characters, which is why the property warns about length.
.subject(username)Stores the username as the token's subject, so verifiers know who it represents.
.claim("role", role)Adds the role as a claim, so services can make authorization decisions from the token alone.
.expiration(expiry)Sets the expiry. After this time the token is rejected, limiting the damage of a stolen token.
.signWith(key())Signs the token with the secret key. This signature is what makes the token trustworthy.
.compact()Serializes everything into the compact token string the client receives.
What we have, and what is next

We can mint a signed token for any user. Now we wire the pieces together in the login endpoint: find the user, verify the password, and issue the token.

Build · Part 8

The Login Endpoint

Why now: this is where everything meets

Login is the heart of the service, and it can only be written now because it needs every earlier piece: the repository to find the user, the encoder to verify the password, and the JWT service to issue the token. We add it to the same AuthController.

controller/AuthController.java — add login and inject JwtServiceJava
// Add these imports:
import com.example.authservice.dto.AuthResponse;
import com.example.authservice.dto.LoginRequest;
import com.example.authservice.security.JwtService;

// The controller now also depends on JwtService (Part 7). Update the
// fields and constructor to include it:
private final UserRepository userRepository;
private final PasswordEncoder passwordEncoder;
private final JwtService jwtService;

public AuthController(UserRepository userRepository,
                      PasswordEncoder passwordEncoder,
                      JwtService jwtService) {
    this.userRepository = userRepository;
    this.passwordEncoder = passwordEncoder;
    this.jwtService = jwtService;
}

@PostMapping("/login")
public ResponseEntity<AuthResponse> login(@RequestBody LoginRequest req) {

    // 1. Find the user by username (Part 3). If absent, credentials fail.
    AppUser user = userRepository.findByUsername(req.getUsername())
            .orElseThrow(() ->
                new RuntimeException("Invalid username or password"));

    // 2. Compare the submitted password against the stored hash (Part 4).
    //    We re-hash the input and compare; we never decrypt.
    if (!passwordEncoder.matches(req.getPassword(), user.getPassword())) {
        throw new RuntimeException("Invalid username or password");
    }

    // 3. Credentials are valid: issue a signed token (Part 7).
    String token = jwtService.generateToken(user.getUsername(), user.getRole());

    // 4. Return the token (plus context) in the AuthResponse DTO (Part 5).
    return ResponseEntity.ok(
        new AuthResponse(token, user.getUsername(), user.getRole()));
}
StepWhat it does and which earlier part it uses
findByUsername(...)Loads the user. Uses the repository from Part 3. A missing user means invalid credentials.
passwordEncoder.matches(...)Verifies the raw password against the stored hash. Uses the encoder from Part 4.
jwtService.generateToken(...)Issues the signed token. Uses the JWT service from Part 7.
new AuthResponse(...)Returns the token in the response DTO from Part 5, never the hash.
Why both failure cases say the same thing

Whether the username does not exist or the password is wrong, we return the same message, "Invalid username or password." Telling an attacker which part was wrong would let them discover valid usernames. Same message for both is a deliberate security choice.

A client can now log in and receive a token. But a token is only useful if someone can later check it is genuine and unexpired. So next we add validation to the JWT service.

Build · Part 9

Validating and Reading the Token

Why now

Issuing a token is only half the story. When the token comes back on a later request, something must confirm its signature is valid and it has not expired, and then read the username and role from it. We add these methods to the same JwtService, so both the Auth Service and (in Part 11) the gateway can use them.

security/JwtService.java — add validation and reading methodsJava
// Add these imports:
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.JwtException;

// Parse and verify a token, returning its claims (the data inside).
// verifyWith(key) checks the signature; parsing also checks expiry.
private Claims parse(String token) {
    return Jwts.parser()
            .verifyWith(key())
            .build()
            .parseSignedClaims(token)
            .getPayload();
}

// True if the token is genuine and unexpired; false otherwise.
public boolean isValid(String token) {
    try {
        parse(token);          // throws if signature is bad or token expired
        return true;
    } catch (JwtException e) {
        return false;          // invalid or expired
    }
}

// Read the username (subject) out of a valid token.
public String extractUsername(String token) {
    return parse(token).getSubject();
}

// Read the role claim out of a valid token.
public String extractRole(String token) {
    return String.valueOf(parse(token).get("role"));
}
MethodWhat it does and why it is needed
parse(token)Verifies the signature with the same key used to sign, and reads the claims. Throws if the signature is wrong or the token has expired.
isValid(token)A safe yes/no wrapper: returns true if parse succeeds, false if it throws. The gateway uses this to accept or reject a request.
extractUsername(token)Reads the subject (username) so it can be forwarded downstream.
extractRole(token)Reads the role claim for authorization decisions.
Why the same key matters

verifyWith(key()) uses the key built from jwt.secret. Verification only succeeds if the verifier's secret matches the signer's secret. That is why, in Part 11, the gateway must be configured with the identical jwt.secret.

What we have, and what is next

We can create, verify, and read tokens. But the Auth Service itself currently has no security rules: it must allow login and register through while blocking everything else. So next we configure Spring Security.

Build · Part 10

Security Configuration for the Auth Service

Why now

Adding the Spring Security dependency locks down every endpoint by default, which would block even login. We need to explicitly allow the public endpoints (register and login) while keeping the service stateless (no server-side sessions, since we use tokens).

config/SecurityConfig.javaJava
package com.example.authservice.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // Disable CSRF: it protects browser form sessions, which we do
            // not use. Our clients are APIs sending tokens.
            .csrf(csrf -> csrf.disable())

            // Allow /auth/** without authentication (register and login must
            // be reachable by users who have no token yet). Everything else
            // requires authentication.
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()
                .anyRequest().authenticated())

            // Stateless: do not create server-side sessions. Identity lives in
            // the token on each request, which is the microservice way.
            .sessionManagement(sm ->
                sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS));

        return http.build();
    }
}
SettingWhat it does and why it is needed
csrf.disable()CSRF protection is for cookie-based browser sessions. We use stateless tokens, so it is not applicable and would otherwise block POSTs.
requestMatchers("/auth/**").permitAll()Lets register and login through without a token, since a new user has none yet.
anyRequest().authenticated()Every other endpoint requires authentication, locking the service down by default.
SessionCreationPolicy.STATELESSTells Spring not to keep server-side sessions. Each request stands alone, carrying its token, which is what lets any instance handle any request.
What we have, and what is next

The Auth Service is complete and testable on its own: register, log in, get a token, and the service is locked down sensibly. Now we connect it to the rest of the system, where the gateway validates the token once for every protected request.

Integrate · Part 11

The Gateway Validates the Token Once

Why validate at the gateway, not in every service

Every request already passes through the API Gateway (the single entry point). If the gateway checks the token once, the Product and Order services never have to. This keeps security in one place and keeps the business services simple. A request with a missing or invalid token is rejected before it ever reaches a service.

The gateway needs the same secret and the JWT library

To verify a token the Auth Service signed, the gateway needs the identical jwt.secret and the same jjwt dependencies in its pom.xml (the three jjwt-api/impl/jackson entries from Step 1). Add jwt.secret to the gateway's configuration with the same value.

Spring Cloud Gateway is reactive, so we write a global filter that runs for every request, checks the token, and either rejects the request or lets it continue.

api-gateway — filter/JwtAuthFilter.javaJava
package com.example.apigateway.filter;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.JwtException;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.cloud.gateway.filter.GatewayFilterChain;
import org.springframework.cloud.gateway.filter.GlobalFilter;
import org.springframework.core.Ordered;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import reactor.core.publisher.Mono;
import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.util.List;

@Component   // a GlobalFilter runs for EVERY request through the gateway
public class JwtAuthFilter implements GlobalFilter, Ordered {

    @Value("${jwt.secret}")   // SAME secret the Auth Service signs with
    private String secret;

    // Paths that do NOT need a token: logging in and registering.
    private static final List<String> OPEN = List.of("/auth/login", "/auth/register");

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();

        // 1. Public paths skip the check entirely.
        if (OPEN.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }

        // 2. Read the Authorization header; it must be "Bearer <token>".
        String authHeader =
            exchange.getRequest().getHeaders().getFirst(HttpHeaders.AUTHORIZATION);
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            return unauthorized(exchange);
        }
        String token = authHeader.substring(7);  // strip "Bearer "

        // 3. Verify the token. If valid, forward identity downstream (Part 12).
        try {
            Claims claims = Jwts.parser()
                    .verifyWith(key())
                    .build()
                    .parseSignedClaims(token)
                    .getPayload();

            ServerWebExchange mutated = exchange.mutate()
                .request(r -> r
                    .header("X-Auth-Username", claims.getSubject())
                    .header("X-Auth-Role", String.valueOf(claims.get("role"))))
                .build();

            return chain.filter(mutated);   // allow, with identity attached
        } catch (JwtException e) {
            return unauthorized(exchange);   // bad or expired token
        }
    }

    private Mono<Void> unauthorized(ServerWebExchange exchange) {
        exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return exchange.getResponse().setComplete();
    }

    private SecretKey key() {
        return Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    }

    @Override
    public int getOrder() { return -1; }  // run early, before routing
}
ElementWhat it does and why it is needed
implements GlobalFilterMakes this filter run for every request passing through the gateway.
OPEN list / path.startsWithLets login and register through without a token, since users need them before they have one.
getFirst(AUTHORIZATION)Reads the Authorization header where the client puts the token.
startsWith("Bearer ") / substring(7)Confirms the standard Bearer <token> format and strips the prefix to get the raw token.
Jwts.parser().verifyWith(key())Verifies the signature and expiry using the shared secret. Throws if invalid.
exchange.mutate().request(... header ...)Adds the verified username and role as headers, so downstream services receive the identity. Covered in Part 12.
unauthorized(...)Returns 401 and stops the request when the token is missing or invalid.
getOrder() = -1Runs the filter early, before the request is routed to a service.
What we have, and what is next

The gateway now blocks any protected request without a valid token, and attaches the caller's identity to the ones it allows. Next, a downstream service reads that identity.

Integrate · Part 12

Downstream Services Read the Forwarded Identity

Why now

The gateway validated the token and attached X-Auth-Username and X-Auth-Role headers. A business service such as the Order Service can now simply read those headers to know who is calling, without doing any token work itself.

order-service — reading the identity the gateway forwardedJava
@GetMapping("/orders/me")
public String whoAmI(
        @RequestHeader("X-Auth-Username") String username,
        @RequestHeader("X-Auth-Role") String role) {

    // These headers were set by the gateway AFTER it validated the token.
    // The service trusts them because the request came through the gateway
    // on the private network, not directly from the public internet.
    return "You are " + username + " with role " + role;
}
ElementWhat it does and why it is needed
@RequestHeader("X-Auth-Username")Reads the username header the gateway attached in Part 11.
@RequestHeader("X-Auth-Role")Reads the role, which the service can use for authorization (for example, allow only ROLE_ADMIN to cancel any order).
Why this trust is safe (and how to keep it safe)

The Order Service trusts these headers because only the gateway sets them, and the business services are not exposed to the public internet, only the gateway is. A caller cannot bypass the gateway to inject fake X-Auth-* headers. In production you enforce this by keeping services on a private network and, ideally, having the gateway strip any incoming X-Auth-* headers from clients before setting its own.

The full chain is now complete

Login issues a token, the client sends it, the gateway validates it once and forwards the identity, and the service reads who is calling. That is end-to-end authentication across the system.

Common pitfalls and how to fix them

SymptomCause and fix
App fails to start: "key byte array must be at least 256 bits"Your jwt.secret is shorter than 32 characters. HS256 needs at least that. Use a longer secret.
Login always returns "Invalid username or password"Either the user was not registered, or the stored value is not a BCrypt hash (you saved a raw password somewhere). Register through the endpoint so the password is hashed.
Protected route returns 401 even with a tokenThe gateway's jwt.secret does not match the Auth Service's, so verification fails. Make them identical. Also check the header is exactly Authorization: Bearer <token>.
401 on every route including loginThe gateway filter is not skipping the open paths, or you are calling login directly without the open-path rule. Confirm /auth/login and /auth/register are in the OPEN list.
Token works, then stops after a whileIt expired. That is expected. Log in again to get a fresh one, or increase jwt.expiration-ms for testing.
Downstream service sees null usernameThe request did not pass through the gateway, or the gateway did not set the headers. Always call through port 8080, not the service port directly.
What to study next, to go from this to production
  • Refresh tokens: a longer-lived token to get new short-lived access tokens without logging in again.
  • Role-based authorization: restrict specific endpoints to specific roles, in the gateway or each service.
  • Asymmetric signing (RS256): the Auth Service signs with a private key and services verify with a public key, so the secret is never shared.
  • Spring Security resource server: the official OAuth2 resource-server support, which replaces hand-written validation in larger systems.
  • Token storage on the client: where and how a real frontend stores tokens safely.

The essential idea

One service owns identity and issues a signed, stateless token. The gateway verifies it once at the front door and passes the caller's identity to the business services, which stay simple and trust it. Build it in this order and each piece arrives already motivated by the one before it. Then deepen each topic (refresh tokens, roles, asymmetric keys) once this foundation is solid.
