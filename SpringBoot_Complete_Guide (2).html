Section 1

Spring MVC Validation with Thymeleaf

Validation means checking that data entered by the user is correct before saving it to the database. Without validation, a user could submit an empty name, a fake email like "abc", or an age of -5. Validation stops bad data at the door.

What happens if you do NOT use validation

Without validation, bad data is saved directly into the database. A user submits an empty name — your database gets a blank row. A user submits "not-an-email" for the email field — your email sending code crashes. SQL injection is possible if you concatenate user input into queries. The app becomes unreliable and insecure.

@Entity
public class Employee {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)

    private BigDecimal salary;

    public Employee() {}
    // getters and setters ...
}
Example 2 — Controller using @Valid and BindingResult
controller/EmployeeController.javajava
@Controller
@RequestMapping("/employees")
public class EmployeeController {

    @Autowired
    private EmployeeService employeeService;

    // GET /employees/new → show blank form
    @GetMapping("/new")
    public String showForm(Model model) {
        model.addAttribute("employee", new Employee());
        return "employees/form";
    }

    // POST /employees/save → validate then save
    @PostMapping("/save")
    public String saveEmployee(
            @Valid @ModelAttribute("employee") Employee employee,
            // @Valid: triggers all annotations (@NotBlank, @Email, @Min etc.)
            BindingResult result,
            // BindingResult: captures all validation errors
            // MUST come immediately after the object being validated
            Model model) {

        if (result.hasErrors()) {
            // Validation failed — re-show the form with error messages
            // The employee object retains what the user typed
            return "employees/form";
        }

        // All validations passed — save to database
        employeeService.save(employee);
        return "redirect:/employees";
    }
}

Example 4 — Custom validation annotation (phone number)
validation/ValidPhone.java + PhoneValidator.javajava
// Step 1: define the annotation
@Documented
@Constraint(validatedBy = PhoneValidator.class)
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidPhone {
    String message() default "Invalid phone number";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// Step 2: implement the validator logic
public class PhoneValidator implements ConstraintValidator<ValidPhone, String> {
    @Override
    public boolean isValid(String phone, ConstraintValidatorContext ctx) {
        if (phone == null) return true; // use @NotNull for null check
        return phone.matches("^[6-9]\\d{9}$");
        // 10-digit Indian mobile: starts with 6-9, followed by 9 digits
    }
}

// Step 3: use it like any other annotation
@ValidPhone(message = "Enter a valid 10-digit Indian mobile number")
private String phone;

Example 6 — Service-level validation (business rule)
service/EmployeeService.java — business validationjava
@Service
public class EmployeeService {

    @Autowired
    private EmployeeRepository repo;

    public Employee save(Employee employee) {
        // Business rule: email must be unique — cannot check this with @Email annotation
        if (repo.existsByEmail(employee.getEmail())) {
            throw new DuplicateEmailException(
                "An employee with email '" + employee.getEmail() + "' already exists");
        }
        // Business rule: department must exist in the allowed list
        List<String> allowedDepts = List.of("Engineering", "HR", "Finance");
        if (!allowedDepts.contains(employee.getDepartment())) {
            throw new InvalidDepartmentException("Invalid department");
        }
        return repo.save(employee);
    }
}

In Spring MVC with Thymeleaf, your controller returns an HTML page name. In a REST API, the controller returns data (JSON or XML) instead of a page. A mobile app or another service calls your URL and receives structured data — not an HTML page it cannot render.

Annotation@Controller@RestController

Form submissionHTML form POSTJSON body in request

Example 1 — Return entity directly (simplest, not recommended for production)
controller/EmployeeRestController.javajava
@RestController
// @RestController = @Controller + @ResponseBody on every method
// Every method returns JSON automatically — no template name
@RequestMapping("/api/employees")
public class EmployeeRestController {

    @Autowired
    private EmployeeService service;

    // GET /api/employees → returns JSON array of all employees
    @GetMapping
    public List<Employee> getAll() {
        return service.findAll();
        // Returns: [{id:1, name:"Ravi", email:"ravi@x.com", ...}, ...]
        // HTTP status: 200 OK (default)
        // Problem: exposes ALL fields including passwordHash, sensitive data
        // Use DTO (Example 4) to control what is exposed
    }

    // GET /api/employees/5 → returns one employee
    @GetMapping("/{id}")
    public Employee getById(@PathVariable Long id) {
        return service.findById(id);
    }
}
Example 2 — Return ResponseEntity (full control over HTTP response)
Using ResponseEntity for proper HTTP status codesjava
@GetMapping("/{id}")
public ResponseEntity<Employee> getById(@PathVariable Long id) {
    return service.findById(id)
        .map(emp -> ResponseEntity.ok(emp))
        // .ok() sets HTTP 200 OK
        .orElse(ResponseEntity.notFound().build());
        // .notFound() sets HTTP 404 Not Found
}

@PostMapping
public ResponseEntity<Employee> create(@RequestBody @Valid Employee emp) {
    Employee saved = service.save(emp);
    return ResponseEntity
        .status(HttpStatus.CREATED)   // HTTP 201 Created
        .body(saved);
}

@DeleteMapping("/{id}")
public ResponseEntity<Void> delete(@PathVariable Long id) {
    service.delete(id);
    return ResponseEntity.noContent().build();
    // HTTP 204 No Content — success, nothing to return
}

// HTTP status cheat sheet:
// 200 OK          → successful GET or PUT
// 201 Created     → successful POST (new resource created)
// 204 No Content  → successful DELETE
// 400 Bad Request → validation failed
// 404 Not Found   → resource does not exist
// 500 Server Error → unexpected exception

@RequestBody + @Valid + error responsejava
@PostMapping
public ResponseEntity<?> createEmployee(
        @RequestBody @Valid EmployeeDTO dto,
        // @RequestBody: parse incoming JSON into EmployeeDTO object
        // @Valid: run all validation annotations on EmployeeDTO
        BindingResult result) {

    if (result.hasErrors()) {

    }

    Employee saved = service.save(mapper.toEntity(dto));
    return ResponseEntity.status(201).body(mapper.toDTO(saved));
}

DTO — Data Transfer Object

A DTO is a plain Java class that carries only the data you want to send to or receive from the outside world. It is NOT a database entity — it has no @Entity or @Id. Think of it as a "custom view" of your data.

The problem without DTO

Your entity class has every field including passwordHash, createdAt, Hibernate proxy objects, and internal audit fields. If you return the entity directly from a REST API, the JSON includes all of these — exposing sensitive data, causing circular reference errors (Employee → Department → employees → Employee...), and leaking internal implementation details.

Without DTOWith DTO
Exposes all entity fields including sensitive onesShows only the fields you choose
Circular reference errors with bidirectional relationshipsFlat structure — no circular references
API breaks when you change the entityAPI stays stable even if the entity changes
Validation annotations mix with persistence concernsSeparate validation rules for API vs database
Cannot combine data from multiple entitiesCan include data from any source
Example 4 — Manual mapping: Entity → DTO → Entity
dto/EmployeeDTO.java + EmployeeMapper.java (manual)java
// EmployeeDTO.java — only fields the API client needs
public class EmployeeDTO {

    private Long   id;

    @NotBlank(message = "Name is required")
    private String name;

    @Email
    private String email;

    @Min(18) @Max(65)
    private int    age;

    private String departmentName; // flattened from Employee.department.name

    // NO passwordHash, NO Hibernate fields, NO sensitive data
    // getters setters ...
}

// EmployeeMapper.java — manual conversion methods
@Component
public class EmployeeMapper {

    // Entity → DTO (used when returning data to client)
    public EmployeeDTO toDTO(Employee emp) {
        EmployeeDTO dto = new EmployeeDTO();
        dto.setId(emp.getId());
        dto.setName(emp.getName());
        dto.setEmail(emp.getEmail());
        dto.setAge(emp.getAge());
        if (emp.getDepartment() != null) {
            dto.setDepartmentName(emp.getDepartment().getName());
        }
        return dto;
    }

    // DTO → Entity (used when saving data from client)
    public Employee toEntity(EmployeeDTO dto) {
        Employee emp = new Employee();
        emp.setName(dto.getName());
        emp.setEmail(dto.getEmail());
        emp.setAge(dto.getAge());
        // departmentName → Department lookup happens in service layer
        return emp;
    }
}

Complete EmployeeRestController.javajava
@RestController
@RequestMapping("/api/employees")
public class EmployeeRestController {

    @Autowired private EmployeeService service;
    @Autowired private EmployeeMapper  mapper;

    @GetMapping
    public ResponseEntity<List<EmployeeDTO>> getAll() {
        return ResponseEntity.ok(mapper.toDTOList(service.findAll()));
    }

    @GetMapping("/{id}")
    public ResponseEntity<EmployeeDTO> getById(@PathVariable Long id) {
        Employee emp = service.findById(id);
        return ResponseEntity.ok(mapper.toDTO(emp));
    }

    @PostMapping
    public ResponseEntity<EmployeeDTO> create(
            @RequestBody @Valid EmployeeDTO dto) {
        Employee emp    = mapper.toEntity(dto);
        Employee saved  = service.save(emp);
        return ResponseEntity.status(HttpStatus.CREATED).body(mapper.toDTO(saved));
    }

    @PutMapping("/{id}")
    public ResponseEntity<EmployeeDTO> update(
            @PathVariable Long id,
            @RequestBody @Valid EmployeeDTO dto) {
        Employee updated = service.update(id, mapper.toEntity(dto));
        return ResponseEntity.ok(mapper.toDTO(updated));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        service.delete(id);
        return ResponseEntity.noContent().build();
    }
}

Simple explanation

JPA is like a job description: "To be an ORM you must support @Entity, findById(), save()..." Hibernate is the employee who does the job. Spring Data JPA is the manager who makes the employee's job even easier by handling transactions, repositories, and boilerplate automatically.

Spring vs Spring Boot

ServerDeploy WAR to Tomcat separatelyEmbedded Tomcat — run as a plain JAR

Simple explanation

Spring Framework is like buying raw ingredients and cooking everything from scratch. Spring Boot is like a meal kit — the ingredients are pre-portioned, the oven is pre-heated, and the recipe has sensible defaults. You still get full control if you want it, but the common cases just work out of the box.

Global Exception Handling with @ControllerAdvice

Without global exception handling, every exception shows an ugly stack trace to the user. With @ControllerAdvice, you catch exceptions from ALL controllers in one place and return clean, structured error responses.

exception/GlobalExceptionHandler.javajava
@ControllerAdvice
// Spring registers this class to intercept exceptions from ALL controllers
public class GlobalExceptionHandler {

    // Handle validation errors (@Valid fails) → HTTP 400
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    @ResponseBody
    public Map<String, String> handleValidationErrors(
            MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(err ->
            errors.put(err.getField(), err.getDefaultMessage()));
        return errors;
        // Returns: {"name":"Name is required","email":"Invalid email"}
    }

    // Handle resource not found → HTTP 404
    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    @ResponseBody
    public Map<String, String> handleNotFound(ResourceNotFoundException ex) {
        return Map.of("error", ex.getMessage());
        // Returns: {"error":"Employee not found with id: 999"}
    }

    // Handle duplicate resource → HTTP 409 Conflict
    @ExceptionHandler(DuplicateEmailException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    @ResponseBody
    public Map<String, String> handleDuplicate(DuplicateEmailException ex) {
        return Map.of("error", ex.getMessage());
    }

    // Catch everything else → HTTP 500
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    @ResponseBody
    public Map<String, String> handleGeneral(Exception ex) {
        return Map.of("error", "An unexpected error occurred");
        // Never expose the real exception message to clients in production
    }
}

Spring Data JPA Repository Basics

A repository is the layer that talks to the database. With Spring Data JPA, you just extend an interface and get 20+ CRUD methods for free — no SQL needed for standard operations.

repository/EmployeeRepository.javajava
@Repository
public interface EmployeeRepository extends JpaRepository<Employee, Long> {
    // JpaRepository<Employee, Long>:
    // Employee = the entity this repository manages
    // Long = the type of the @Id field

    // FREE methods you get without writing anything:
    // save(employee)         → INSERT or UPDATE
    // findById(id)           → SELECT WHERE id=?  returns Optional
    // findAll()              → SELECT * FROM employees
    // deleteById(id)         → DELETE WHERE id=?
    // count()                → SELECT COUNT(*)
    // existsById(id)         → SELECT COUNT(*) WHERE id=?

    // CUSTOM query methods — Spring reads the name and generates SQL
    Optional<Employee> findByEmail(String email);
    // → SELECT * FROM employees WHERE email = ?

    List<Employee> findByDepartment(String department);
    // → SELECT * FROM employees WHERE department = ?

    List<Employee> findByNameContainingIgnoreCase(String keyword);
    // → SELECT * FROM employees WHERE LOWER(name) LIKE %keyword%

    List<Employee> findBySalaryGreaterThan(BigDecimal amount);
    // → SELECT * FROM employees WHERE salary > ?

    boolean existsByEmail(String email);
    // → SELECT COUNT(*) FROM employees WHERE email = ? → used for uniqueness check

    // JPQL custom query when method name is too complex
    @Query("SELECT e FROM Employee e WHERE e.department = :dept AND e.salary > :sal")
    List<Employee> findByDeptAndMinSalary(
        @Param("dept") String dept,
        @Param("sal")  BigDecimal salary);

    // Paging: get page 0 (first 10), page 1 (next 10), etc.
    Page<Employee> findByDepartment(String dept, Pageable pageable);
}
service/EmployeeService.java — using the repositoryjava
@Service
@Transactional
public class EmployeeService {

    @Autowired
    private EmployeeRepository repo;

    @Transactional(readOnly = true)
    public List<Employee> findAll() {
        return repo.findAll();
    }

    @Transactional(readOnly = true)
    public Employee findById(Long id) {
        return repo.findById(id)
            .orElseThrow(() ->
                new ResourceNotFoundException("Employee not found with id: " + id));
    }

    public Employee save(Employee emp) {
        if (repo.existsByEmail(emp.getEmail())) {
            throw new DuplicateEmailException("Email already exists");
        }
        return repo.save(emp);
    }

    public void delete(Long id) {
        if (!repo.existsById(id)) {
            throw new ResourceNotFoundException("Employee not found with id: " + id);
        }
        repo.deleteById(id);
    }

    // Paging example: get page 0 with 10 records, sorted by name
    @Transactional(readOnly = true)
    public Page<Employee> getPage(int pageNo, int size) {
        Pageable pageable = PageRequest.of(pageNo, size, Sort.by("name").ascending());
        return repo.findAll(pageable);
    }
}

QuestionOne-line answer
What is the difference between @Controller and @RestController?@RestController adds @ResponseBody to every method — returns JSON, not a template name
What does @Valid do?Triggers Bean Validation on the annotated method parameter — runs all constraint annotations
Why use DTO instead of returning Entity directly?Hides sensitive fields, prevents circular references, keeps API stable when entity changes
What is the difference between JPA and Hibernate?JPA is the specification (rules). Hibernate is the implementation (does the actual work).
What does @Transactional do?Wraps the method in a DB transaction — all SQL succeeds or all rolls back on exception
What is @ControllerAdvice?A global exception handler — catches exceptions from ALL controllers in one class
What is the difference between save() with and without an ID?id=null → INSERT new row. id set → UPDATE existing row
What does ddl-auto=update do?Hibernate reads @Entity classes and creates/updates matching tables on startup

Complete guide summary

  • Validation: add spring-boot-starter-validation, put @NotBlank/@Email/@Min on entity fields, use @Valid + BindingResult in controller, use th:errors in Thymeleaf for display.
  • REST API: change @Controller to @RestController, return ResponseEntity for full HTTP status control, receive JSON with @RequestBody, use @Valid for API validation.
  • DTO: create a plain class with only the fields you want to expose, write a mapper (manual or MapStruct), always convert Entity → DTO before returning from REST and DTO → Entity before saving.
  • JPA vs Hibernate: JPA is the rules. Hibernate follows the rules. Spring Data JPA builds on both so you write almost no code.
  • Spring vs Spring Boot: Spring is the full framework. Spring Boot wraps it with auto-configuration, embedded Tomcat, and starters to get you running in minutes.
  • Exception handling: @ControllerAdvice + @ExceptionHandler catches all exceptions centrally — no try-catch in every controller.
  • Repositories: extend JpaRepository to get 20+ CRUD methods free. Add method names (findByEmail, findByDepartment) to get custom queries automatically.
